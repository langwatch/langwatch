`GET /api/langy/health` sends one real user turn, "Hi Langy.", through the same path the browser and the API use, waits for the answer, and reports the result in a shape an uptime monitor can alert on. Point any HTTP monitor at it.

## Configure the monitor

| Setting | Value |
| --- | --- |
| Method and URL | `GET https://<your-langwatch-host>/api/langy/health` |
| Header | `X-Auth-Token: <project API key>` |
| Expected status | `200` |
| Request timeout | 60 seconds (the check itself gives up at 55) |
| Check interval | 3 minutes or longer |

The API key must belong to a user who has Langy access, and must carry the `langy:create` permission. The turn runs as that user, so create a dedicated user and key for the monitor rather than reusing a person's. The [Langy API surface flag](/self-hosting/langy/setup#staged-rollout) must be on for the key's project; while it is off, the endpoint answers `404` like any unmounted path.

## What it answers

| Status | Body | Meaning |
| --- | --- | --- |
| `200` | `{ "status": "ok", "conversationId", "turnId", "durationMs" }` | Langy answered with text. |
| `503` | `{ "status": "unhealthy", "reason", ... }` | `timeout`: no answer within 55 seconds. `turn_failed`: the turn failed or stopped. `empty_reply`: the turn completed with no text. |
| `429` | `{ "status": "busy" }` | A check for the same key is still running. Poll less often. |
| `401` / `403` | error envelope | The key is missing, unknown, lacks `langy:create`, or its owner has no Langy access. |

Every response carries `Cache-Control: no-store`.

## What each check costs

Each poll is one real Langy turn: one worker boot and one model call, attributed to the monitor's user in the monitor's project. A 3-minute interval is 480 turns a day.

Langy's first turn on a cold worker is the slowest part of the path, so a `timeout` under load or right after a deploy is worth a second look before it is treated as an outage. Most monitors confirm a failure from a second location before alerting, which covers that.
