## Before You Upgrade

1. **Check release notes** for breaking changes at [github.com/langwatch/langwatch/releases](https://github.com/langwatch/langwatch/releases)
2. **Back up your databases**: see [Backups](/self-hosting/configuration/backups)
3. **Test in a staging environment** before upgrading production

## Complete identity and access migrations first

The identity and access update removes the old RBAC permission checks. Existing
installations must complete their data migrations **before** installing this
update. Do this in two deployments; do not jump straight from an older version.

<Steps>
  <Step title="Run the preparatory release">
    Install the preparatory release named in the release notes, using a pinned
    image or chart version. Keep the app and workers running against your
    existing PostgreSQL, ClickHouse and Redis databases so the migration events
    can be processed and verified.

    Keep your current identity-provider configuration, callback URLs and
    `CREDENTIALS_SECRET`. Moving data does not require replacing your provider.
  </Step>
  <Step title="Check the migration results">
    Sign in with an operator account from `ADMIN_EMAILS` and open
    **Ops > Migrations** (`/ops/migrations`). Check each of these steps:

    | Migration | What must be complete |
    | --- | --- |
    | **Authorization engine** (`authz-engine`) | Every organization's existing roles and access grants are **Finalized**. |
    | **Identifier history backfill** (`identity-d01-identifier-backfill`) | Existing users' sign-in methods are **Finalized**. This step tracks users, so its count is not the organization count. |
    | **Enterprise SSO connection history** (`identity-d04-connection-grandfather`) | Existing organizations have a **Finalized** result, including those with an existing SSO configuration. |

    Read the results for all existing organizations and users. A zero error
    count alone does not prove that every account was included. Where available,
    use **Run for organization…** to run a step for a specific organization and
    inspect its result. For the identifier backfill, this checks that
    organization's members.

    **Held**, **Parked**, **Rolled back**, waiting, or missing results mean the
    upgrade is not ready. Resolve the report and rerun the migration on the
    preparatory release. **Run a pass now** starts work; it does not certify that
    the work finished.

    The recurring **Sign-in credential repair** task is different: it keeps
    credentials synchronized during the transition and has no terminal
    **Finalized** state. Investigate its errors, but do not wait for a completion
    state it cannot reach.
  </Step>
  <Step title="Verify access, then upgrade">
    Before changing versions, test an existing administrator's sign-in, a
    member's team and project access, and an existing SSO sign-in where used.
    If you use SCIM, check that provisioning still reaches the expected
    organization and review any failed requests.

    Once the required migrations are **Finalized**, take a fresh backup and
    install the identity and access update using the deployment steps below.
    Repeat those sign-in and access checks after the upgrade.
  </Step>
</Steps>

<Warning>
If a required migration says **Not yet available for self-hosted installations**,
stop here. That build cannot complete the preparation; restarting it or waiting
longer will not enable the migration. Use a preparatory release that makes all
required steps available, or [contact support](https://langwatch.ai/support)
before upgrading. Do not mark migrations complete by editing database rows.
</Warning>

A healthy app, a completed Prisma schema migration, and an empty work queue do
not replace these checks. The migration must also verify the imported data and
persist its **Finalized** result.

This data migration preserves the existing SSO route. Switching to a replacement
provider is a separate operation with domain verification and a test sign-in;
see [SSO setup](/platform/sso).

## Check SSO connection ownership before upgrading

Before applying the identity schema migrations, run these read-only queries
against the installation's PostgreSQL database. Each must return no rows.
The live connection indexes deliberately refuse duplicate slots rather than
silently choosing a connection. `REJECTED`, `DRAFT`, and `CLAIMED` still occupy
slots; only `DISCARDED` and `TORN_DOWN` release them.

```sql
SELECT "organizationId",
       CASE WHEN "source" = 'legacy-grandfathered' THEN 'legacy' ELSE 'direct' END AS slot,
       count(*) AS connections
FROM "SsoConnection"
WHERE "state" NOT IN ('DISCARDED', 'TORN_DOWN')
GROUP BY "organizationId", slot
HAVING count(*) > 1;

SELECT domains.domain, count(DISTINCT connection."organizationId") AS organizations
FROM "SsoConnection" AS connection
CROSS JOIN LATERAL unnest(connection."verifiedDomains") AS domains(domain)
WHERE connection."state" NOT IN ('DISCARDED', 'TORN_DOWN')
GROUP BY domains.domain
HAVING count(DISTINCT connection."organizationId") > 1;
```

Resolve reported duplicates through the existing connection lifecycle before
upgrading, or contact support. Do not delete the active connection or discard
domain ownership to force the migration through.

When upgrading an installation that already has connection-scoped SCIM data,
also check for directory identities whose connection is missing:

```sql
SELECT DISTINCT identity."connectionId"
FROM "ScimExternalId" AS identity
LEFT JOIN "SsoConnection" AS connection ON connection."id" = identity."connectionId"
WHERE connection."id" IS NULL;
```

If `ScimDirectoryUser` already exists, run the same query with that table as
well. The ownership migration derives `organizationId` from the connection
and refuses missing connections rather than guessing a tenant. It also
backfills verified-domain routing for existing live connections of every source.

SCIM now keeps each organization's directory profile and active state separately
from the shared login account. A directory rename does not change the primary
sign-in email, and deactivation removes access only to that organization.
Inactive directory users remain available through SCIM reads. Group external
identifiers are unique within each directory; legacy groups retain their
organization-wide namespace.

Directory usernames remain unique within each organization, ignoring case and
surrounding whitespace. Deleted resources release their usernames. The migration
refuses conflicting existing usernames rather than merging accounts. If both
directory identity tables already exist, this query must also return no rows:

```sql
WITH claims AS (
  SELECT "connectionId", "userId" FROM "ScimDirectoryUser"
  UNION
  SELECT "connectionId", "userId" FROM "ScimExternalId"
)
SELECT connection."organizationId", lower(btrim(account."email")) AS username,
       count(DISTINCT account."id") AS users
FROM claims
JOIN "SsoConnection" AS connection ON connection."id" = claims."connectionId"
JOIN "User" AS account ON account."id" = claims."userId"
WHERE btrim(account."email") <> ''
GROUP BY connection."organizationId", lower(btrim(account."email"))
HAVING count(DISTINCT account."id") > 1;
```

For an earlier schema containing only `ScimExternalId`, use only that table's
`SELECT` in the `claims` expression. Resolve any conflicts before upgrading.

The migration preserves existing global account disables. It cannot distinguish
an earlier SCIM disable from an administrator's security action, so it does not
automatically reactivate those accounts. Review any historical disable through
the administrator account controls when restoring access.

## Docker Compose

```bash
# Pull latest images
docker compose pull

# Restart with new images
docker compose up -d
```

Database migrations run automatically on startup.

## Helm Chart

```bash
# Update the Helm repository
helm repo update

# Upgrade the release
helm upgrade langwatch langwatch/langwatch \
  --namespace langwatch \
  -f values-production.yaml \
  --wait --timeout 10m
```

### Pin a Specific Version

```bash
# List available versions
helm search repo langwatch/langwatch --versions

# Install a specific chart version
helm upgrade langwatch langwatch/langwatch \
  --namespace langwatch \
  --version 3.17.0 \
  -f values-production.yaml
```

## Database Migrations

### PostgreSQL

Prisma migrations run automatically when the app pod starts. To disable this (e.g., if you run migrations separately):

```yaml
app:
  features:
    skipEnvValidation: false
  extraEnvs:
    - name: SKIP_PRISMA_MIGRATE
      value: "true"
```

### ClickHouse

The application runs schema migrations on startup. No manual intervention is required.

## Rollback

### Helm

```bash
# List release history
helm history langwatch --namespace langwatch

# Rollback to a previous revision
helm rollback langwatch <revision> --namespace langwatch
```

### Docker Compose

Pin image tags to a specific version instead of `latest`:

```yaml
services:
  app:
    image: langwatch/langwatch:<previous-version>  # the release you are rolling back to
```

Then restart:

```bash
docker compose up -d
```

## Breaking Changes

### Dataset Object Storage (Helm)

Datasets moved from PostgreSQL to object storage, with a one-time automatic migration on upgrade. Helm deployments running more than one worker replica with the default local storage must either scale workers to 1 or configure S3-compatible storage before upgrading.

See the **[dataset storage migration guide](/self-hosting/upgrade-dataset-storage)** for the upgrade checklist, storage options, and rollback notes.

### v1.x, v2.x to v3: ClickHouse Migration

LangWatch v3 replaces Elasticsearch/OpenSearch with ClickHouse as the primary data store. This is a zero-downtime migration, Elasticsearch and ClickHouse run side-by-side while you migrate historical data.

See the **[full migration guide](/self-hosting/upgrade-v3)** for step-by-step instructions covering infrastructure setup, data migration, and cleanup.

### Helm Chart Pre-1.0.0 to 1.0.0+

If upgrading from a Helm chart version before 1.0.0, the PostgreSQL PVC naming changed. To preserve your data:

```yaml
postgresql:
  primary:
    persistence:
      existingClaim: "data-langwatch-postgresql-0"  # Your existing PVC name
```

Check your existing PVC name:

```bash
kubectl -n langwatch get pvc
```

## Getting Help

If you encounter issues during an upgrade:

- Check pod logs: `kubectl -n langwatch logs deploy/langwatch-app --tail=100`
- Check the [Troubleshooting guide](/self-hosting/troubleshooting)
- Open an issue at [github.com/langwatch/langwatch/issues](https://github.com/langwatch/langwatch/issues)
- Contact [support](https://langwatch.ai/support)
