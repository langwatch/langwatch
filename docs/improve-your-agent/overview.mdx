## What the improvement loop is

The agent improvement loop is the process of changing an agent and proving that the change did not lower its quality. Quality is a test suite of [scenarios](/agent-testing/scenarios) that pass on the agent you trust today. Turns, tokens, cost and latency are metrics you push down while that suite keeps passing.

The suite is the gate because an agent has no single expected output to compare against. The same request can end well after three turns or after ten, and after one tool call or four. The judge in a scenario reads the whole conversation and the agent's traces, passes or fails each criterion you wrote, and writes the reasoning for the verdict. The turns, the cost and the latency of the same run tell you whether the change paid off.

## The loop

| Step | What you do | Where |
|---|---|---|
| 1. Define quality | Write five to ten scenarios from real conversations, with the criteria the agent must meet. Run them on the model and prompt you trust. Every scenario passes: this is the baseline. | [Scenarios](/agent-testing/scenarios), [Test suites](/agent-testing/test-suites) |
| 2. Measure | Read the pass rate, the cost and the reply latency of the baseline run. Open the longest conversation and count the turns. | [Results](/agent-testing/results) |
| 3. Change one thing | A smaller model, a rewritten tool description, a tool that validates its input, a shorter prompt, a lower iteration cap. One change per run, so the result has one cause. | Your code |
| 4. Compare | Run the same suite against the changed agent, next to the baseline. Keep the change when the pass rate holds and the metric moved. | [Compare agents](/agent-testing/compare-agents) |

Repeat from step 3. Put the suite in CI so a later change cannot undo the gain: see [Run from CI](/agent-testing/run-from-ci).

## Where the changes come from

Start from the results of the last run. For a failed criterion, read the judge's reasoning, which quotes the turn, and open the trace of that turn. For a scenario that passed in ten turns, open the conversation and look for the same tool called twice in a row: that retry is the first hypothesis to test.

Two engines run the loop for you:

- **Guided.** Langy, or your own coding agent with the LangWatch skills, reads the results and the traces, proposes one change and opens it as a pull request. The suite runs in your CI on that pull request, so you review the diff and the result together. See [Prompt optimization with Langy](/langy/prompt-optimization) for the prompt case.
- **Algorithmic.** A DSPy optimizer rewrites the instructions and the tool descriptions and scores every candidate by running the suite. GEPA also reads the judge's reasoning as the feedback for the next candidate. See [Optimize with DSPy](/improve-your-agent/optimize-with-dspy).

Use the guided engine when the change is in code, in a tool or in the harness. Use the algorithmic engine when the change is in text and you have the budget to run the suite fifty times.
