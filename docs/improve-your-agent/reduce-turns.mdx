A turn is one reply from your agent, and behind each reply there are one or more model calls, because every tool call the agent makes is a model call too. That is why a rejected tool call that the agent retries costs you a model call even when the reply count stays at one, and why you count both: the replies you see in the conversation, and the model calls in the trace behind each reply. The causes of extra replies and extra calls are listed below in the order worth checking them.

## What you need

- Your agent [connected to LangWatch](/agent-testing/connect-your-agent), so the suite runs against your real code and the judge reads your traces.
- A [test suite](/agent-testing/test-suites) of five to ten scenarios that pass today. Take the situations from real conversations, and put the long ones in.
- The agent registered with `concurrency` of at least 3 in the `development` environment, or three instances of it, because a run executes three scenarios at once while a development agent takes one call at a time by default, so the other two calls wait and can end as `agent_busy`.

## Step 1: Measure the baseline

Run the suite once against the agent as it runs today and keep that run as the baseline; in the example that is the `production` environment.

```bash
langwatch test-suite run "Returns" --target connected:returns-agent@production --wait
```

The run header shows the pass rate, the total duration and the total cost, and hovering it gives you **Avg Agent Latency** and **Avg Agent Cost** with percentiles. Open the conversations in order of **Time · cost**, and in each one count the agent's replies, press **View trace** on a turn to count the model calls behind that reply, and read the judge's reasoning under the verdict. The two shapes you will see are different problems: a conversation with one reply and six model calls is the retry case, while a conversation with three replies means the customer argued or the agent asked for something.

## Step 2: Find the cause

Read the long conversation against this list, in order. The first match is the hypothesis.

1. **The tool rejects the input and the agent retries with different wording.** The same tool appears two or three times in a row in the trace, each call with an error, because the tool description does not say which values it accepts. See [Fix tool calls](/improve-your-agent/fix-tool-calls).
2. **The agent asks the user for something a tool could answer.** For example, it asks for the order date when `lookup_order` already returns it, because the tool description does not say what the tool returns.
3. **The agent calls tools one per turn**, so three lookups take three turns. Either the model supports parallel tool calls and the harness has them off, or the prompt tells the agent to check one thing at a time.
4. **The agent narrates before it acts.** "Let me check that for you" is a whole turn with no tool call and no answer in it. Tell the agent in the prompt to act first and answer once.
5. **The iteration cap is high**, so after the second failed tool call the agent keeps trying instead of escalating or asking. Cap the iterations in the harness and add a criterion for the escalation.

## Step 3: Change one cause and compare

Make one change, then run the suite again as a comparison against the baseline target, so both sides appear in one run over the same scenarios:

```bash
langwatch test-suite run "Returns" \
  --target connected:returns-agent@production \
  --target connected:returns-agent@development \
  --wait
```

The run detail shows one column per target with its pass rate, total duration and cost, and four charts above them: **Pass rate**, **Total cost**, **Average reply latency** and **Pass rate over runs**. Keep the change when the pass rate holds or rises and the model calls per conversation went down. Be careful with the cost and the latency charts on a single pass: over six scenarios run once, both move more between two runs of the same agent than a removed retry moves them, so read those two from a run with `--repeat 3`. When a criterion fails on the changed side, the judge's reasoning tells you which turn the agent skipped.

To pin the gain, add a criterion that counts, such as `The agent completes the return within four replies`. The judge counts the replies in the conversation and fails the scenario when the agent takes more.

## Step 4: Keep it in CI

Run the suite on every pull request that touches the agent, so a later change cannot bring the turns back:

```bash
langwatch test-suite run "Returns" --target connected:returns-agent@staging --wait
```

The command exits 1 when a scenario fails. `--wait` gives up after ten minutes, and a suite with repeats can take longer than that, so poll the batch yourself for those: see [Run from CI](/agent-testing/run-from-ci).

## Do it with Langy

Ask [Langy](/langy/chat):

```text
Reduce the number of turns of returns-agent on the Returns suite without failing any scenario.
Start from the longest conversation in the last run, tell me the cause, and open a pull request with one change.
```

Langy reads the run and the traces with the `langwatch` CLI, tells you the cause and opens a pull request with the change to the prompt or the tool description. The suite runs in your CI on that pull request, and the result comes back on the pull request card in the chat.

## Do it with your coding agent

Install the skills once, then ask your coding agent the same thing:

```bash
npx skills add langwatch/skills/agent-improve
npx skills add langwatch/skills/scenarios
```

```text
/agent-improve The returns-agent takes eight to ten turns on the Returns suite. Find the cause in the last run and reduce the turns without failing a scenario.
```

The skill gathers the evidence with the `langwatch` CLI, presents ranked hypotheses and waits for you to pick one, then makes the change as a pull request together with the scenario test that proves it.

## Common failures

- **The pass rate dropped.** Revert the change, then read the reasoning of the failed criterion: it points at the turn where the agent stopped doing something it did before, such as confirming the refund method before it created the return.
- **The turns did not move.** The cause is in a tool rather than in the prompt: the agent keeps retrying because the tool still rejects the input, so fix the tool contract first.
- **A criterion about the agent's behaviour is inconclusive, with `no agent spans arrived` in the reasoning.** The judge waits thirty seconds for the trace after the conversation ends, and under load the trace arrives later than that, so the judge read an empty one. Rerun the scenario. If the trace shows `[REDACTED]` for the tool names and contents instead, the data privacy policy of the project hides them from the judge as well: see [Linking your traces](/agent-testing/linking-your-traces).
- **The latency dropped and the cost did not.** The agent takes fewer turns but with longer prompts. Read the token count on the trace and shorten the context: see [Reduce cost and latency](/improve-your-agent/reduce-cost-and-latency).
