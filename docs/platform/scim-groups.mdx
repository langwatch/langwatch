A SCIM group is a group that your identity provider pushes into LangWatch. You bind roles to the group at the organization, team or project scope, and every member of the group holds those roles.

<Info>
  Groups are an **Enterprise** feature, whether they come from SCIM or are created by hand. Set up [SCIM Provisioning](/platform/scim) for users first.
</Info>

---

## How it works

1. Your identity provider pushes groups to the SCIM `/Groups` endpoint
2. The groups appear at **Settings > Groups**
3. You bind roles to each group, for example Member on the Engineering team
4. A user added to the group in the identity provider holds every binding of the group
5. A user removed from the group, or deprovisioned, loses them

---

## View groups

**Settings > Groups** lists every group. Each row shows:

| Column | Description |
|--------|-------------|
| **Group** | The group name from the identity provider |
| **Source** | `SCIM` for a pushed group, `Manual` for a group created in LangWatch |
| **Access** | The role bindings of the group |
| **Members** | The number of users in the group |

Click a row to open the group dialog, where you manage the bindings and, for manual groups, the members.

---

## Bind roles to a group

Open a group. In the **Access granted** section:

1. Select a **role** (Admin, Member, Viewer, or a custom role)
2. Select the **scope**: Organization, Team, or Project
3. Select the team or the project for a Team or Project scope
4. Click **Add**, then **Save**. The binding is written when you save

A group can hold several bindings, for example Member on the organization plus Admin on the Platform team.

### Binding scopes

| Scope | What it grants |
|-------|---------------|
| **Organization** | The role on every team and project in the organization |
| **Team** | The role on one team and all its projects |
| **Project** | The role on one project |

---

## How bindings add up

A user in several groups holds every binding of every group, plus the bindings set on the user directly at **Settings > Members**. Permissions add up: a request is allowed when any binding on the project, its team or the organization grants it, and no binding removes what another one grants.

For example, a user in Group A (Member on the Engineering team) and Group B (Admin on the Engineering team) holds both, and can do everything an Admin can on that team.

**Also check:** [Access Control (RBAC)](/platform/rbac) for how a request is authorized.

## User lifecycle with groups

### When a user is added to a group

The user holds every binding of the group at once. Group membership never creates a user: a member id that is not yet in your organization is skipped, so provision the user through `/Users` first (see [User Provisioning](/platform/scim#provisioning-create)).

### When a user is removed from a group

The group's bindings no longer apply to the user. With no other binding, the user stays in the organization and sees no team or project.

### When a group is deleted

LangWatch removes the group, its memberships and its role bindings.

### When a user is deprovisioned (DELETE)

A `DELETE` on a user removes the organization membership and every role binding, deactivates the account and keeps the user's data. A `PATCH` with `active: false` deactivates the account and keeps the membership and the bindings. Both are described in [SCIM Provisioning](/platform/scim#user-lifecycle).

## Manual groups

You can also create groups manually without an identity provider:

1. At **Settings > Groups**, click **Add manual group** at the bottom of the table
2. Enter a group name
3. Add role bindings and members in the dialog if you want
4. Click **Create group**

Bindings work the same way on manual and SCIM groups. Members must already be in your organization. A manual group is not synced with an identity provider, and the `/Groups` endpoint does not list it.

## SCIM group endpoints

| Endpoint | Methods |
|----------|---------|
| `/api/scim/v2/Groups` | `GET`, `POST` |
| `/api/scim/v2/Groups/{id}` | `GET`, `PUT`, `PATCH`, `DELETE` |

`POST` with the `displayName` of an existing group returns `409 Conflict`. `GET /Groups` returns SCIM groups only, at most 100 per page.

### Supported PATCH operations

| Operation | Example | Effect |
|-----------|---------|--------|
| `add members` | Add users to the group | The users hold the group's bindings |
| `remove members` | Remove users from the group | The group's bindings no longer apply to them |
| `replace displayName` | Rename the group | The name changes in LangWatch |
| `replace members` | Replace the member list | Adds the new members and removes the old ones |

A `replace` clears the membership only when `members` is an empty list or an explicit `null`. A `replace` with no `members` value, a `members` value that is not a list, or a list with entries that have no usable string `value` leaves the membership unchanged, so a malformed payload cannot revoke access. The other attributes in the same operation, such as `displayName`, still apply, and the unapplied part is written to the server log.

### Supported filter

`GET /Groups` filters by `displayName` with a case-insensitive `eq`:

```
GET /api/scim/v2/Groups?filter=displayName eq "Engineering"
```

## Troubleshooting

**Groups do not appear in LangWatch**

- Group push is enabled in the identity provider's application settings
- The provisioning log of the identity provider shows no error on the Groups endpoint
- The bearer token is not revoked

**Users in a group have no access**

- Open the group at **Settings > Groups**. The **Access granted** section needs at least one binding
- The user is in the group's **Members** list. A user who was not in the organization when the identity provider pushed the group was skipped; push the group again after the user is provisioned

**A user has more access than expected**

- The user is in several groups. Bindings add up across groups
- Bindings set on the user at **Settings > Members** add up with the group bindings

**Removing a user from a group in the identity provider has no effect**

- The identity provider pushes group membership changes, not only user changes
- The provisioning log shows no error on the group `PATCH`

## Manage groups through the REST API

The [Groups REST API](/api-reference/groups/overview) creates groups, sets their bindings and members, and deletes them, so you can script provisioning outside SCIM.

<Info>
  The name and the members of a SCIM group belong to the identity provider. The REST API and the settings page refuse to change them.
</Info>
