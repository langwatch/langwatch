# Scenario Run Parameters

A run parameter is a named constant value for one run. You declare the parameter names on the scenario. You supply the values when you start a run. The scenario text and the target under test read the values by name. One scenario can then test different plans, tenants, or regions without a copy for each one.

## Declare the parameters on the scenario

Open the scenario and click **Parameters**, next to **Labels** at the bottom of the editor. The editor shows one row per parameter. A row has a name, an optional description, and an optional default value. The names you declare appear next to **Labels**. Click one to open the editor again.

<img src="/images/simulations/scenario-parameters-form.png" alt="The scenario editor with the parameters dialog open over it, declaring a fixture parameter with a description and a default value, referenced as params.fixture in the situation and criteria" width="100%" />

- **Name** is what every template reads. It starts with a letter or an underscore. It continues with letters, digits and underscores, up to 64 characters. A name outside that grammar is rejected when you save.
- **Description** appears beside the field in the run dialog. Up to 500 characters.
- **Default value** is the value the run uses when you supply no value for that name. Values are typed. `42` is the number, `true` is the boolean, and all other values are text. To keep text that reads as a number or a boolean, put it in quotes, so `"007"` stays the text `007`.

A scenario declares a maximum of 20 parameters. A duplicate name is rejected.

The scenarios API carries the same declarations. `POST /api/scenarios` and `PATCH /api/scenarios/{id}` accept a `parameters` array of `{ name, description, defaultValue }` objects. A read of the scenario returns the array.

<Warning>
  A resolved value is recorded on the run. All users who can open the run can read it. Use parameters for fixture ids, tenants, plans and regions. Never use a parameter for a credential. Put an API key in a project secret. The target reads a secret as `{{ secrets.NAME }}`, and the platform never shows the value back. See [Testing agents behind authentication](/agent-simulations/authenticated-agents).
</Warning>

## Supply the values when a run starts

A supplied value overrides the scenario's default. A name with no supplied value uses the default declared on the scenario.

### From the run confirmation dialog

When you run a suite from the platform, the confirmation dialog opens. It shows one field for every parameter that a scenario in the run declares. Each field is filled in with the declared default. A change in the dialog applies to that run only, and the scenario keeps its declared defaults. Fields are typed like defaults, so `42` is the number and `"007"` is the text.

<img src="/images/simulations/scenario-parameters-run-dialog.png" alt="The suite run confirmation dialog with a Parameters block, the fixture field prefilled from the scenario's default value" width="100%" />

The suite editor has a **Save and Run** button. This button does not open the dialog. It starts the run with the declared defaults. To change a value first, start the run from the suite page.

### From the API

`POST /api/suites/{id}/run` accepts a `parameters` object of names to values. A value is a string, a number or a boolean:

```bash
curl -X POST "https://app.langwatch.ai/api/suites/suite_abc123/run" \
  -H "X-Auth-Token: ${LANGWATCH_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "parameters": {
      "account_tier": "platinum",
      "region": "eu-central",
      "seed_fixtures": true
    }
  }'
```

The response gives the batch id that the scheduled runs share:

```json
{
  "scheduled": true,
  "batchRunId": "batch_xyz789",
  "setId": "set_abc123",
  "jobCount": 6,
  "skippedArchived": { "scenarios": [], "targets": [] },
  "items": []
}
```

See the [suite run endpoint reference](/api-reference/suites/action-run) for the full request and response.

### From the command line

Every run command accepts a repeatable `--param key=value`:

```bash
langwatch suite run <suite-id> --param account_tier=platinum --param region=eu-central
langwatch scenario run <scenario-id> --target http:<agent-id> --param account_tier=platinum
```

The value type follows the text you type. `true` and `false` are booleans. A value that parses as a number and prints back the same is a number. All other values stay text, so `007` and `1.50` stay text. When you repeat a name, the last value wins.

### From the SDKs

<Tabs>
  <Tab title="Python">
```python
import langwatch

langwatch.setup()

result = langwatch.suites.run(
    "suite_abc123",
    parameters={"account_tier": "platinum", "region": "eu-central"},
)
print(result["batchRunId"])
```
  </Tab>
  <Tab title="TypeScript">
```typescript
import { LangWatch } from "langwatch";

const langwatch = new LangWatch();

const result = await langwatch.suites.run("suite_abc123", {
  parameters: { account_tier: "platinum", region: "eu-central" },
});
console.log(result.batchRunId);
```

## Read the values in the scenario's own text

The situation and every criterion read a resolved value as `{{ params.NAME }}`. Both render before the run starts. The simulated user gets the value, and the judge scores against the same value.

```text title="Situation"
A customer on the {{ params.account_tier }} plan asks to move their subscription
to the {{ params.region }} region.
```

```text title="Criterion"
Agent quotes the {{ params.account_tier }} plan's transfer fee
```

A scenario that declares no parameters and receives no values is not read as a template. Its text is not changed. Prose that contains `{{` or `{%` reaches the simulated user and the judge exactly as written. When you declare a parameter, the scenario text becomes a template.

## Deliver the values to the target under test

Each target type reads the same resolved values:

| Target | How it reads a value |
|---|---|
| **HTTP agent** | `{{ params.NAME }}` in the url and in the body template |
| **Prompt** | `{{ params.NAME }}` in the prompt template |
| **Code agent** | `params.NAME` in the Python, keeping its type |
| **Workflow** | One entry input per name |

### HTTP agents

The url and the body template both render against the run's parameters. A value can select the endpoint, a query string, or a field in the request body:

```text title="URL"
https://api.your-company.internal/{{ params.region }}/chat
```

```json title="Body template"
{
  "thread_id": "{{ threadId }}",
  "messages": {{ messages }},
  "account_tier": "{{ params.account_tier }}"
}
```

<img src="/images/simulations/scenario-parameters-body-template.png" alt="The HTTP agent body template editor referencing params.fixture, with the available variables hint listing params.NAME" width="100%" />

Header values and the auth fields read project secrets, not parameters. See [Testing agents behind authentication](/agent-simulations/authenticated-agents#referencing-project-secrets-from-an-http-target).

### Prompt targets

A prompt target renders `{{ params.NAME }}` in its template before the model call. You can then test the same prompt with different plans or regions.

### Code agents

A code agent reads parameters from the injected `params` namespace. It reads project secrets from `secrets` the same way. Values keep their type, so a boolean is a `bool` and a number is a number. You do not parse them out of strings:

```python
import requests


class Code:
    def __call__(self, message: str):
        response = requests.post(
            f"https://api.your-company.internal/{params.region}/chat",
            json={
                "message": message,
                "account_tier": params.account_tier,
                "seed_fixtures": params.seed_fixtures,  # a real bool
            },
            timeout=30,
        )
        response.raise_for_status()
        return {"output": response.json()["reply"]}
```

`params` is injected into the module globals. Do not import a module with that name, and do not assign a name of your own over it. A run that resolved no parameters leaves `params` undefined, the same as `secrets`. In that run, `params.region` raises `NameError`. It does not read an empty value.

### Workflow targets

A workflow target receives the run's parameters as entry inputs. Each parameter name becomes one entry input on the workflow.

<Note>
  A parameter reaches a downstream node only if the entry node has an edge carrying it. Adding a parameter to the run does not add the edge, so open the workflow and connect the new entry field to the node that reads it.
</Note>

Entry inputs arrive as strings. A code node reads `params.NAME` with the original type.

## Limits

| Limit | Value |
|---|---|
| Parameters declared on one scenario | 20 |
| Names one run supplies values for | 50 |
| All of a run's values together | 16 kilobytes |
| One string value | 4096 characters |
| Parameter name | 64 characters |
| Parameter description | 500 characters |

## When a run is rejected

| Error | What happened | What to do |
|---|---|---|
| `scenario_parameter_unknown` | The run supplied a name that no scenario in the run declares. This is usually a spelling error. The message gives the rejected key and the names the run accepts. | Correct the spelling, or declare the parameter on the scenario that reads it. |
| `scenario_parameter_missing` | The situation or a criterion reads a name that resolved to no value. The run supplied no value, and the scenario declares no default. The message gives the parameter and the field that reads it. | Supply a value for this run, or give the parameter a default on the scenario. |
| `scenario_parameter_template_invalid` | A field references a parameter in a form that cannot be rendered. | Write the reference as `{{ params.name }}`. |

All checks run before any job is scheduled. A rejected run starts no jobs.

## Where the resolved values are recorded

The values a run resolved are stored on the run. You can read a result back with the inputs that produced it.

- The run detail drawer shows the values under **Parameters**, one row per name.
- The CSV export writes the values as one JSON object per run. A criteria export puts the object in the `parameters` column. A full export puts it in the `run_parameters` column. One column holds every name, so the header stays the same for every export.
