A refactor, a new lint rule, a `CLAUDE.md` rewrite or a set of skills all claim to make coding agents work better on your code. You can test that claim: give the same task to the same agent on the codebase before and after the change, and compare what each run cost, how long it took, and what it got wrong.

This is a manual experiment. You run both sessions and grade the result yourself; LangWatch records the sessions and gives you the numbers to compare.

## The run we did

We tested a large layout migration of the LangWatch monorepo ([langwatch#7536](https://github.com/langwatch/langwatch/pull/7536)), which splits the code into feature modules with strict lint rules. The question was whether the new layout made an agent faster, cheaper or more correct.

Two Claude Code sessions started 15 seconds apart on 2026-09-08 on the same machine, with the same prompt and models: a Fable 5.1 coordinator that delegated to Opus sub-agents.

The task was a full feature: an upload button for image cells in datasets and the evaluation workbench, a file column type, files delivered to prompts and agents as attachments, browser testing with screenshots, then a pull request driven through review. One session ran on the old layout and opened [langwatch#7964](https://github.com/langwatch/langwatch/pull/7964); the other ran on the new one and opened [langwatch#7972](https://github.com/langwatch/langwatch/pull/7972).

| | Old layout ([#7964](https://github.com/langwatch/langwatch/pull/7964)) | New layout ([#7972](https://github.com/langwatch/langwatch/pull/7972)) |
|---|---|---|
| Wall clock, raw | 3h 52m | 3h 26m |
| Wall clock, confounds removed | 3h 13m | 3h 08m |
| Cost, raw (API-equivalent) | 182.28 USD | 189.58 USD |
| Cost, confounds removed | 167.09 USD | 178.36 USD |
| Model calls | 1,747 | 1,518 |
| Tool calls | 1,480 | 1,310 |
| Mean context of a sub-agent call | 156k tokens | 202k tokens |
| Typecheck runs | 19 whole-repository, median 78 s | 38 scoped, median 5 s |
| Review bot threads on the pull request | 33, over 5 review passes | 11, over 1 review pass |
| Severe defects found by reading the final diff | 0 | 3 |

Each run hit one problem unrelated to the layout, and the adjusted rows remove both. The old-layout machine restarted mid-run (about 102 tool calls and 15 USD of repeated work). The new layout's base branch was missing two files, so the app would not boot until a sub-agent rebuilt them (about 25 minutes and 11 USD).

## What it showed

Speed: about the same. The new layout finished 5 minutes earlier once the confounds were removed, at the same tool-call rate. Its feedback loop was much faster: scoped typechecks took 5 seconds at the median against 78, so the agent checked twice as often for a third of the waiting time.

Cost: about 7% higher on the new layout. It made fewer calls, but each sub-agent carried 29% more context, because one feature now spans several packages and a sub-agent keeps all of them in view. In both runs, the final reports sub-agents write back to the coordinator were about 20% of the cost.

Review: the old-layout pull request drew 33 review bot threads across 5 passes before it merged, about 7 per pass. The new-layout pull request drew 11 threads in its one pass and was closed, so the totals measure how long each stayed in review, not which layout drew fewer findings.

Defects: we read both final diffs and rated each problem. A severe defect is wrong behaviour on a main path of the feature: data lost or delivered wrong, or a request the server should refuse that it accepts. A minor defect is duplication, misplaced code or an inefficiency that does not change what the user gets.

The new layout placed every file where its rules said, and avoided the duplication and one wrong-direction import found in the old run.

The new layout still left the three severe defects, all on the run path: a missing attachment fell back silently and the run succeeded, connected agents received a 27 MB base64 string as message text, and the upload endpoint had no request size cap. The old layout left no severe defect; its findings were all minor: a size limit stated in three places, double buffering, a stray results row, and that import. We merged the old-layout pull request.

With one run per layout, this is a diagnosis, not proof. Agent behaviour varies a lot between runs of the same prompt. The run did show where to look: the layout steered file placement and loop speed, but neither codebase named the connected-agent path or a size cap as required, so the agent skipped them on both. Those belong in a written spec for the feature.

## Run it on your codebase

1. Pick one feature-sized task that touches several parts of the code, and write a single prompt for it that includes testing and opening a pull request.
2. Prepare two branches: the codebase before and after the change you want to test. Make sure both build and pass CI before you start; a broken base costs the run time and money that tell you about the base, not the change.
3. [Connect Claude Code to LangWatch](/coding-agents/claude-code), then start both sessions at the same time, on the same machine, with the same model settings, each in its own worktree.
4. Let both open a pull request and go through the same review bot or reviewer.
5. Compare the two sessions in LangWatch (queries below), and note anything unrelated to the change that cost either run time, so you can subtract it.
6. Grade the defects. Count review threads, then have one reviewer read both diffs without knowing which is which and rate every defect as severe (wrong behaviour on a main path) or minor. Run the feature yourself.
7. Repeat with at least three runs per side before you decide. Use the same prompt each time.

## Read the numbers in LangWatch

The [sessions list](/coding-agents/sessions) shows each session's cost, duration, model calls and peak context, and the [pull requests view](/coding-agents/pull-requests) shows what each pull request cost. To compare branches side by side, run LangWatchQL with the `langwatch` command-line tool:

```bash
langwatch query run "SELECT GitBranch, count() AS sessions, sum(ModelCalls) AS model_calls,
  sum(ToolCalls) AS tool_calls, round(sum(CostUsd), 2) AS cost_usd
  FROM langwatch.coding_sessions
  WHERE GitBranch IN ('before-branch', 'after-branch') GROUP BY GitBranch"
```

For the feedback loop, compare tool durations per branch:

```bash
langwatch query run "SELECT Branch, ToolName, count() AS runs,
  quantileExact(0.5)(DurationMs) AS median_ms, sum(DurationMs) AS total_ms
  FROM langwatch.coding_session_events
  WHERE EventKind = 'tool_result' AND Branch IN ('before-branch', 'after-branch')
  GROUP BY Branch, ToolName ORDER BY total_ms DESC"
```

Your own coding agent can run these too: see [Explore your usage with your own agent](/coding-agents/explore-your-usage-with-your-own-agent).
