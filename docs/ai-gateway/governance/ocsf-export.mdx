## What is exported

LangWatch exports three streams of OCSF 1.9.0 API Activity events (`class_uid` 6003, `category_uid` 6):

| Stream | Route | Contains |
|---|---|---|
| Governance events | `GET /api/governance/ocsf/events` | Traces from [ingestion sources](/ai-governance/ingestion-sources/index), events pulled from provider audit APIs, admin views of a member's or team's workspace, and OCSF events pushed in from other tools |
| Project traces | `GET /api/governance/ocsf/traces` | One event per trace in the organization's projects |
| Audit log | `GET /api/governance/ocsf/audit` | Admin and configuration actions: who did what, on which target, from which address, and whether it failed |

Every event LangWatch builds sets `metadata.version` to `1.9.0`, `metadata.uid` to a stable event id and `metadata.tenant_uid` to the organization id. An LLM call is `activity_id` 99 (Other) with `activity_name` `Invoke`, since OCSF API Activity has no invoke activity.

## AI fields

Each event carries the OCSF 1.9 AI objects when LangWatch knows their values:

| Field | Source |
|---|---|
| `ai_model.name`, `ai_model.ai_provider` | The model the call used. A `provider/model` name is split; an unknown provider is `Unknown` |
| `ai_agent.name`, `ai_agent.uid` | `gen_ai.agent.name` and `gen_ai.agent.id` on the trace |
| `message_context.prompt_tokens`, `completion_tokens`, `total_tokens` | The trace's or the provider event's token counts |
| `message_context.uid`, `metadata.correlation_uid` | The trace id |
| `unmapped.langwatch.cost_usd` | The cost in USD. Provider events priced in another currency carry `cost_amount` and `cost_currency` instead |

Prompt and response text are never exported, and neither is the raw provider payload. `unmapped.langwatch` also carries `source_type`, `source_id`, `trace_id` and `project_id` so you can pivot back to LangWatch.

## Auth

| Requirement | Value |
|---|---|
| Plan | Enterprise |
| Credential | An organization API key, sent as `Authorization: Bearer <key>` |
| Permission | `complianceExport:view` for the three export routes, `governance:manage` for the ingest route |

A key without the permission gets a 403. An organization below Enterprise gets a 402 `enterprise_plan_required`.

## Pulling events

All three routes take the same paging parameters:

| Parameter | Default | Purpose |
|---|---|---|
| `limit` | `500` | Page size, 1 to 1000 |
| `cursor` | none | The `next_cursor` of the previous page |
| `since` | none | ISO 8601 start of the first read. A cursor carries its own position |
| `until` | none | ISO 8601 end bound. The cursor does not carry it, so send it again with every page |

`/events` also takes `source_type` and `source_id`. `/traces` takes `project_id` to read one project. `/audit` returns an entry once it is ten minutes old, so an entry written late is not skipped by a cursor that already passed its time.

Every page answers `next_cursor`, which is always set, and `has_more`. Store `next_cursor` after each page. While `has_more` is true, read again at once; when it is false, wait for your next scheduled run and pass the stored cursor. A trace updated after it was exported is exported again with the same `metadata.uid`, so deduplicate on it.

```bash
curl -s "https://app.langwatch.ai/api/governance/ocsf/events?limit=500" \
  -H "Authorization: Bearer $LANGWATCH_ORG_API_KEY"
```

## Pushing events to your SIEM

Create a [webhook endpoint](/features/webhooks) subscribed to `ocsf.event`, pointing at your SIEM's HTTP collector or a forwarder in front of it:

```bash
curl -s "https://app.langwatch.ai/api/webhooks/v1/endpoints" \
  -H "Authorization: Bearer $LANGWATCH_ORG_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://siem-forwarder.acme.com/langwatch", "enabled_events": ["ocsf.event"]}'
```

LangWatch queues each governance event when it is written. Deliveries use the standard webhook envelope: a POST holds a `batch` of up to `max_batch_size` webhook events (100 by default), each with `type: "ocsf.event"` and one OCSF 1.9.0 event as its `data`:

```json
{
  "batch": [
    {
      "id": "evt_f905578f982aee17650a4616b89ad219",
      "type": "ocsf.event",
      "created": "2026-11-16T16:47:29.124Z",
      "schema_version": "1",
      "data": { "class_uid": 6003, "activity_name": "Invoke", "metadata": { "uid": "47c84f48...", "version": "1.9.0" } }
    }
  ]
}
```

Deliveries are signed with `X-LangWatch-Signature: t=<unix seconds>,v1=<hmac-sha256>`, retried with backoff, and logged per endpoint; see [verifying signatures](/features/webhooks#verifying-signatures). An event written again, for example when a trace is processed twice, keeps its idempotency key, so it is queued once per endpoint. A retry after a lost acknowledgement can deliver it again, so deduplicate on `metadata.uid`.

OCSF events go only to endpoints that name `ocsf.event` or `ocsf.*`. An endpoint subscribed to `*` does not receive them. The push carries the governance events stream. Project traces and the audit log are pulled.

## Pushing OCSF events into LangWatch

`POST /api/governance/ocsf/ingest` stores OCSF events from another tool, such as your identity provider or an AI platform's own audit feed, next to LangWatch's events:

```bash
curl -s "https://app.langwatch.ai/api/governance/ocsf/ingest" \
  -H "Authorization: Bearer $LANGWATCH_ORG_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "source": "okta",
    "events": [
      {
        "class_uid": 3002,
        "activity_id": 1,
        "severity_id": 1,
        "time": 1763114521123,
        "metadata": { "uid": "okta-evt-1", "version": "1.4.0", "product": { "name": "Okta" } },
        "user": { "name": "jane@acme.com" }
      }
    ]
  }'
```

The answer is `{ "accepted": 1 }`. A request holds up to 500 events. Each needs `class_uid`, `severity_id`, `time` (epoch milliseconds) and `metadata.uid` and `metadata.version`, and is at most 64 KiB as JSON. An invalid event is a 422 naming the field.

An event is identified by `source` and `metadata.uid`: sending it again replaces the stored copy. Stored events are read back from `/events` with `source_type=ocsf_push`, exactly as received, and are not pushed to webhook endpoints.

## Session export

The tRPC query `governance.ocsfExport` still returns the governance events in their stored OCSF 1.1 row shape, for the signed-in UI. Use the REST routes above for a SIEM job.
