## What a routing policy is

A routing policy is a named set of routing decisions that virtual keys point at. Edit the policy and every key that uses it follows the change; no key is reissued.

A policy holds:

| Section | What it decides |
|---|---|
| Where it applies | The organization, teams or projects whose keys may select the policy. |
| Providers | The model providers the policy routes through, in order. The gateway tries the first one and moves to the next on a failure that is worth another try. |
| Model tiers | What `complex`, `reasoning` and `fast` resolve to, plus a default model. |
| Model name mapping | Rewrites of the model name a client sends before the request reaches a provider. |
| Restrictions | Regex refuse and allow-only lists for tools, MCP servers, web addresses and models. See [Policy rules](/ai-gateway/policy-rules). |

Manage policies under **AI Gateway, Routing Policies** in the sidebar (`/gateway/routing-policies`). Creating, editing and deleting need the `routingPolicies:manage` permission; viewing needs `routingPolicies:view`.

## Model tiers

A tier is a reserved model name a client sends instead of naming a model. Point each tier at a model on one of the policy's providers.

| Tier | Meant for |
|---|---|
| `complex` | The most capable model. |
| `reasoning` | The model best at step-by-step reasoning. |
| `fast` | A quick and inexpensive model. |

A tier the policy names no target for resolves to the policy's **Default model**. A policy with no default model leaves that tier unset, and a request for it is refused as an unknown model.

```bash
curl https://gateway.langwatch.ai/v1/chat/completions \
  -H "Authorization: Bearer $LANGWATCH_VIRTUAL_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "fast", "messages": [{"role": "user", "content": "Summarize this ticket."}]}'
```

The response reports the model that served the request in `model`. `GET /v1/models` on the key lists the tiers next to the models, so model pickers show them.

Tiers and name mappings are the same mechanism on the wire: an alias the gateway looks up by exact name. See [Model aliases](/ai-gateway/model-aliases).

## Model name mapping

A mapping rewrites one requested name to one served name, for example `gpt-4o` to `openai/gpt-5-mini`. The served name must be reachable through one of the policy's providers; the editor refuses a mapping that names a provider the policy does not route through.

The key's own model allowlist is checked against the served model, so a mapping cannot reach a model the key is not allowed to use.

## Provider order

The providers list is the key's fallback chain. The gateway keeps only the providers that can serve the requested model, then tries them in the listed order. A request for a model that resolves to a provider the policy does not include is refused with `400 model_not_allowed`, and the message names the policy:

```
The "anthropic" provider is not available on this key: its routing policy "Developer default" does not include this provider. Ask the key's owner to add it to the routing policy, or send the request to a provider the policy allows.
```

See [Fallback chains](/ai-gateway/providers/fallback-chains) for what triggers the move to the next provider.

## Attach a policy to a key

<Steps>
  <Step title="Create the policy">
    Click **New policy**, pick where it applies, add the providers in the order you want, set the tiers and the default model.
  </Step>
  <Step title="Point the key at it">
    Open the key under **AI Gateway, Virtual Keys**. Under **Routing**, pick the policy. The other two choices, **Default: no fallback** and **Fall back to all eligible providers**, are the key's own routing when it uses no policy.
  </Step>
  <Step title="Verify">
    Send a request for `fast` through the key and read `model` in the response. Then request a model on a provider the policy does not list and check for `400 model_not_allowed`.
  </Step>
</Steps>

**Make this the default where it applies** marks the policy as the default for its scopes; the policies list shows it with a **Default** badge.

## Propagation

Saving a policy writes a change event. The gateway picks it up on its next change-feed poll and rebuilds the bundles of every key on the policy. Requests already in flight finish on the old configuration.
