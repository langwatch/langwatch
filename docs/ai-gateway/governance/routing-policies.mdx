A routing policy answers one question. When someone calls a model
through your organization, which providers serve it, in what order,
and which models can they ask for?

An admin writes the policy once. Each virtual key points at it. To
change how many keys route, you edit the policy, not the keys.

## Shape

```ts
RoutingPolicy {
  id:               string
  organizationId:   string
  name:             string
  description?:     string

  // The providers this policy routes through. The gateway tries the
  // first one. It moves to the next one when a request fails in a way
  // another provider can answer.
  modelProviderIds: string[]

  // Model name mapping. The key is the name a client sends. The value
  // is the model to use instead. The three reserved tier names live
  // here with every other mapping.
  modelAliases:     Record<string, string>

  // The model a tier uses when this policy names no model for it.
  // Applies to the tier names only.
  defaultModel?:    string

  // What a request may reach. Four groups: tools, mcp, urls, models.
  // Each group has a deny list and an allow list.
  policyRules:      { tools: {...}, mcp: {...}, urls: {...}, models: {...} }

  isDefault:        boolean
  scopes:           { scopeType: 'ORGANIZATION' | 'TEAM' | 'PROJECT', scopeId: string }[]
}
```

A policy can apply at more than one place. Each entry in `scopes`
adds one organization, team, or project it applies to.

## Model tiers

A client can send a tier name in place of a model name. The policy
decides which model the tier means. The client does not change when
you move to a newer model.

Three names are reserved:

| Tier | What it means |
| --- | --- |
| `complex` | The strongest model you have. Use it when quality matters more than cost. |
| `reasoning` | A model that works through a problem before it answers. Use it for planning, analysis, and hard debugging. |
| `fast` | A small model for high volume work. Use it for classification, extraction, routing, and short replies. |

The client sends the tier name in the `model` field:

```json
{
  "model": "complex"
}
```

Set a model for each tier in the policy. A tier you leave empty uses
`defaultModel`. A tier with no model and no `defaultModel` is not a
known name, so a request that sends it gets an error.

`defaultModel` applies to the three tier names only. A model name
that a client gets wrong still gets an error. The gateway does not
send the default model in its place.

Store a real model id, such as `openai/gpt-5-mini`. Do not store a
name that moves, such as `openai/latest`. The gateway reads the name
exactly as you wrote it. It would try to call a model named
`latest`. The product refuses to save a name that moves.

`GET /v1/models` lists a tier that has a model, so it shows in a
model picker with every other name. Set `defaultModel` and all three
tiers are listed. A tier with no model and no `defaultModel` is not
listed, because a request that sends it gets an error.

## Model name mapping

`modelAliases` also maps ordinary names. Use it to send an old name
to its replacement, or to give a model the name your teams already
use.

```json
{
  "gpt-4o": "openai/gpt-5-mini",
  "coding": "anthropic/claude-haiku-4-5"
}
```

A mapping cannot reach a model the key is not allowed to use. The
gateway checks the model the mapping points at, not the name the
client sent.

## Restrictions

`policyRules` holds four groups of patterns. Each group has a deny
list and an allow list.

- `tools`: the name of each tool a request offers the model.
- `mcp`: the name and address of each MCP server a request names.
- `urls`: every address in the request, including messages, system
  prompts, and tool arguments.
- `models`: the model the request resolves to.

A request that matches a deny pattern is refused before it costs
anything. When a group has any allow pattern, a request must match
one of them. Deny wins over allow.

The `models` group is checked after the name mapping runs. A mapping
cannot route around it.

## Provider order

`modelProviderIds` is an ordered list. The gateway tries the first
provider. It moves to the next one when a request fails in a way
another provider can answer.

The gateway skips a provider that cannot serve the model. It does
not call it. So a chain across two vendors only fails over for
models both of them serve. To give a model failover, map its name to
each vendor's own model, or point a tier at each one.

The gateway also drops a provider the key can no longer reach, for
example when an admin removes it from the key's scope.

A model name that gives a provider, such as `openai/gpt-5-mini`, only
runs on that provider. When the key cannot reach it, the request gets
an error. The gateway does not send it to another vendor. A tier or a
mapping that points at a provider you removed behaves the same way,
and `GET /v1/models` stops listing it.

## Defaults

One policy for each scope can be the default. Marking a policy
default clears the flag on any other policy that shares a scope with
it. The change happens in one step, so two policies are never both
default for the same scope.

A key routes through the policy it names. The default is the policy
the product offers first when someone makes a key for that scope.

## Manage in the app

Open **AI Gateway → Routing Policies**. The page lists your policies
by where they apply. Select **New policy**, or open the actions menu
on a policy and select **Edit**.

In the editor you can:

- Name the policy and say what it is for.
- Choose where it applies.
- Choose the providers and put them in order.
- Choose a model for each tier, and a default model.
- Map other model names.
- Add restrictions.

The editor has its own address. A link to a policy opens that policy.

## Manage with tRPC

```ts
// List the policies in an organization.
trpc.routingPolicy.list.useQuery({ organizationId });

// List only the policies a scope can select.
trpc.routingPolicy.list.useQuery({
  organizationId,
  selectableForScope: { scopeType: "TEAM", scopeId: teamId },
});

// Read one policy.
trpc.routingPolicy.get.useQuery({ organizationId, id });

// Suggest models for a tier.
trpc.routingPolicy.tierSuggestions.useQuery({
  organizationId,
  tier: "complex",
  boundProviderTypes: ["openai", "anthropic"],
});

trpc.routingPolicy.create.useMutation();
trpc.routingPolicy.update.useMutation();
trpc.routingPolicy.setDefault.useMutation();
trpc.routingPolicy.delete.useMutation();
```

`create`, `update`, `setDefault`, and `delete` need the
`routingPolicies:manage` permission. `list`, `get`, and
`tierSuggestions` need `routingPolicies:view`.

## Keys that name no policy

A key that names no policy uses its own routing mode. `NONE` sends
the request to one provider and returns the error. `FALLBACK_ALL`
tries the providers the key can reach, in a fixed order.

To move a key to a policy:

1. Make a policy with the providers the key uses.
2. Set the key's routing policy to it.
3. Send a request and check that it reaches the provider you expect.

Point new keys at a policy. It keeps the routing decision in one
place.
