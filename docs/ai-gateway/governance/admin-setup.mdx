## Before you start

Do this once as an organization owner or admin. After it, every member signs in from the LangWatch CLI and gets a personal virtual key that routes through your providers, under your routing policy and your budgets.

You need:

- The owner or admin role on the LangWatch organization.
- One API key or credential set per provider you want to make available. The credential fields per provider are on [Providers](/ai-gateway/providers/overview).

## Add a model provider

<Steps>
  <Step title="Open Settings > Model Providers">
    Go to **Settings > Model Providers** (`/settings/model-providers`), also listed as **Model Providers** in the **AI Gateway** sidebar. Click **Add Model Provider** and pick the provider from the menu.

    {/* screenshot: admin-setup-model-providers.png, the Model Providers table with the Add Model Provider button and one connected provider row */}
  </Step>

  <Step title="Paste the credentials and pick the scope">
    Fill the credential fields for that provider, then pick the scopes the credential serves. A provider is attached to the organization, to a team, to a project, or to several of these at once. A virtual key reaches every provider attached to its own scope and to the scopes above it, so a key on a project reaches that project's providers, its team's and the organization's. Which of them serves a request is the routing policy's order, and the fallback priority below when the key has no policy.

    Scope is fixed after you save. To move a credential to another scope, delete it and create it again.

    Click **Save**, then open the row menu and click **Test Connection** to confirm the credential works.
  </Step>

  <Step title="Set the routing handle and the gateway options">
    Open the row menu again and click **Edit Provider**.

    **Routing handle** names this one provider row in a model string. With a handle of `eu`, a request reaches this row as `eu/<model>`. Without one, the provider family name is the prefix, and a key with two rows of the same family routes by the chain order instead. A handle is lowercase, up to 32 characters, and unique in the organization.

    Expand **Advanced (Gateway)** for the rest:

    | Field | What it does |
    |---|---|
    | Fallback priority | The order used when a virtual key has no routing policy. The lower number is tried first. Rows with the same number are tried in creation order. |
    | Provider config (JSON) | Provider-specific routing hints, such as a Bedrock region or an Azure deployment override. It must be a JSON object. |

    The same section shows the health status, the last health check and the circuit-breaker state for this row, read only.

    {/* screenshot: admin-setup-provider-advanced.png, the provider drawer with the Routing handle field filled and the Advanced (Gateway) section expanded on Fallback priority and Provider config */}
  </Step>
</Steps>

## Create a routing policy

Open **AI Gateway > Routing Policies** (`/gateway/routing-policies`) and create a policy. The policy decides which providers a key routes through and in what order, what the model tiers resolve to, and which models, tools and addresses a request may name. Virtual keys then point at the policy.

  <img src="/images/ai-gateway/routing-policy-editor.png" alt="The New routing policy drawer with the scope, the ordered providers and the model tiers" />
</Frame>

**Also check:** [Routing policies](/ai-gateway/governance/routing-policies) for the sections of a policy and the permissions to manage one.

## Set budgets

Open **AI Gateway > Budgets** (`/gateway/budgets`) and create a budget. A budget caps spend on a scope: the organization, a team, a project, one virtual key, one member, or a group. Every request is checked against every budget that applies to it.

Set at least one budget before you tell members to sign in. A key with no budget still serves traffic, and the gateway has no limit to refuse it at.

{/* screenshot: admin-setup-budget.png, the New budget drawer with the scope, the window and the limit filled */}

**Also check:** [Budgets](/ai-gateway/budgets) for the scopes, the windows and the breach behavior.

## Give members their keys

There is no switch to turn personal keys on. A member runs `langwatch login --device`, approves the device in the browser, and gets a personal virtual key as soon as the organization has one model provider the member can reach. Until then, the first tool run stops with `No personal virtual key on this account` and points at **Settings > Model Providers**.

To choose which coding tools and which providers members see on their portal, open **Governance > Inventory** (`/governance/inventory`) and edit the **Catalog** tab.

**Also check:** [Personal keys](/ai-gateway/governance/personal-keys) for what the member sees.

## Verify with one request

Mint a key for yourself and send one completion through it.

1. Open **Configure** in your personal workspace (`/me/configure`), click **Add a new key**, and copy the secret. It is shown once.
2. Send the request:

```bash
curl https://gateway.langwatch.ai/v1/chat/completions \
  -H "Authorization: Bearer $LANGWATCH_VIRTUAL_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "model": "openai/gpt-5-mini",
        "messages": [{"role": "user", "content": "Say hi in one word"}]
      }'
```

3. Open **AI Gateway > Usage** (`/gateway/usage`) for the request and its cost.

A `200` with an OpenAI-shaped body means the credential, the routing policy and the key all resolve. If the request is refused, [Troubleshooting](/ai-gateway/troubleshooting) maps the error codes to their cause.
