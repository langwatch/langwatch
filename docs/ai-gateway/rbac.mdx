## How gateway permissions work

The LangWatch AI Gateway uses the LangWatch permission model: a permission is `<resource>:<action>`, a role is a set of permissions, and a role binding gives a person a role on an organization, a team or a project. A grant at a higher scope covers the scopes below it: `virtualKeys:manage` on the organization covers every team and project in it.

The gateway adds its own resources to that model. Provider credentials, the audit log and the webhook endpoints are shared with the rest of LangWatch. See [Roles and permissions](/platform/rbac) for the model, custom roles and role bindings.

## Resources

| Resource | Gates | Actions |
|---|---|---|
| `virtualKeys` | The Virtual Keys list, detail and drawers, and `/api/gateway/v1/virtual-keys*`. | `view`, `create`, `update`, `rotate`, `delete`, `manage`, `viewOtherPersonal` |
| `gatewayBudgets` | The Budgets list, detail and drawers, and `/api/gateway/v1/budgets*`. | `view`, `create`, `update`, `delete`, `manage` |
| `gatewayProviders` | The Advanced (Gateway) section on a provider credential under Settings > Model Providers. | `view`, `update`, `manage` |
| `routingPolicies` | Routing policies. | `view`, `manage` |
| `gatewayGuardrails` | Attaching and detaching guardrails on a key. | `view`, `attach`, `detach`, `manage` |
| `gatewayCacheRules` | Cache rules, and `/api/gateway/v1/cache-rules*`. | `view`, `create`, `update`, `delete`, `manage` |
| `gatewayUsage` | The Usage page and `GET /api/gateway/v1/virtual-keys/:id/spend`. | `view` |
| `gatewaySpend` | Spend events and spend summaries under `/api/gateway/v1/spend-events*`, `/api/gateway/v1/spend-summaries` and `/api/gateway/v1/end-users/:id/spend`. Organization tier only. | `view`, `manage` |
| `webhookEndpoints` | Webhook endpoints, their secrets and delivery logs. Organization tier only. | `view`, `manage` |
| `auditLog` | The audit log under Settings. | `view` |

`gatewaySpend` and `webhookEndpoints` come only from an organization role binding. A team or project binding never grants them, even through a custom role that lists them.

`virtualKeys:viewOtherPersonal` lets an administrator see other people's personal keys. Everyone sees their own personal keys without it.

## What the built-in roles hold

Team roles apply on the teams and projects the binding names. Organization roles apply on the whole organization.

| Permission | Team Viewer | Team Member | Team Admin | Organization Admin |
|---|:-:|:-:|:-:|:-:|
| `virtualKeys:view` | yes | yes | yes | |
| `virtualKeys:create`, `update`, `rotate` | | yes | yes | |
| `virtualKeys:delete` | | | yes | |
| `virtualKeys:manage`, `viewOtherPersonal` | | | yes | yes |
| `gatewayBudgets:view` | yes | yes | yes | |
| `gatewayBudgets:create`, `update`, `delete`, `manage` | | | yes | |
| `gatewayProviders:view` | yes | yes | yes | |
| `gatewayProviders:update`, `manage` | | | yes | |
| `routingPolicies:view` | yes | yes | yes | |
| `routingPolicies:manage` | | | yes | |
| `gatewayGuardrails:view` | yes | yes | yes | |
| `gatewayGuardrails:attach`, `detach`, `manage` | | | yes | |
| `gatewayCacheRules:view` | yes | yes | yes | |
| `gatewayCacheRules:create`, `update`, `delete`, `manage` | | | yes | |
| `gatewayUsage:view` | yes | yes | yes | |
| `auditLog:view` | yes | yes | yes | |
| `gatewaySpend:view`, `manage` | | | | yes |
| `webhookEndpoints:view`, `manage` | | | | yes |

The Organization Admin column lists what the organization role grants on its own. An organization admin gets the team permissions through the team role bindings they hold, like everyone else.

Organization Member and External hold no gateway permission on their own. They get gateway access through a team role binding.

A custom role starts with no permission. Add the ones you want from the table above.

## Creating keys at a scope

Creating a key with an organization, team or project scope needs `virtualKeys:manage` at every scope the key names. The same rule applies when you re-scope a key with `PATCH`. Naming a trace project on a team or organization key needs `virtualKeys:manage` on that project.

A personal key needs only membership of the organization. See [Virtual keys](/ai-gateway/virtual-keys#ownership-and-scopes).

## Permission per REST route

| Route | Permission |
|---|---|
| `GET /api/gateway/v1/virtual-keys`, `GET .../:id` | `virtualKeys:view` |
| `POST /api/gateway/v1/virtual-keys` | `virtualKeys:create`, plus `virtualKeys:manage` at every scope named |
| `PATCH /api/gateway/v1/virtual-keys/:id` | `virtualKeys:update` |
| `POST .../:id/rotate` | `virtualKeys:rotate` |
| `POST .../:id/disable`, `POST .../:id/enable` | `virtualKeys:update` |
| `POST .../:id/revoke` | `virtualKeys:delete` |
| `GET .../:id/spend` | `gatewayUsage:view` |
| `GET /api/gateway/v1/budgets`, `GET .../:id` | `gatewayBudgets:view` |
| `POST /api/gateway/v1/budgets` | `gatewayBudgets:create` |
| `PATCH .../:id`, `POST .../:id/reset` | `gatewayBudgets:update` |
| `DELETE .../:id` | `gatewayBudgets:delete` |
| `GET /api/gateway/v1/cache-rules` | `gatewayCacheRules:view` |
| `POST /api/gateway/v1/cache-rules` | `gatewayCacheRules:create` |
| `PATCH .../:id` | `gatewayCacheRules:update` |
| `DELETE .../:id` | `gatewayCacheRules:delete` |
| `GET /api/gateway/v1/spend-events`, `GET .../spend-summaries`, `GET .../end-users/:id/spend` | `gatewaySpend:view` |
| `POST /api/gateway/v1/spend-events/replay` | `gatewaySpend:manage` |

A call with an API key that lacks the permission gets HTTP 403 `api_key_permission_denied`. The permission is in `error.meta.permission`:

```json
{
  "error": {
    "code": "api_key_permission_denied",
    "message": "API Key does not grant required permission: virtualKeys:manage",
    "meta": { "permission": "virtualKeys:manage" }
  }
}
```
