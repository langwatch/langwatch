## What is a scenario suite

A scenario suite is the full set of scenarios that tells you whether your agent is safe to ship. It covers the flows that would hurt most if they broke, it runs on every change in a small form and on a schedule in a broad form, and every production failure you fix adds a scenario to it, so the same failure cannot come back unnoticed.

This page covers how to organise, run and maintain that set. For which cases to write and when the suite is complete, see [Scenario Suite Design](/agent-testing/designing-a-suite). For checking the data the agent changed, see [Check the World, Not the Words](/agent-testing/check-the-world). The single pieces have their own pages: [Scenarios](/agent-testing/scenarios), [Test suites](/agent-testing/test-suites), [Run plans](/agent-testing/run-plans), [Run parameters](/agent-testing/run-parameters), [Run from CI](/agent-testing/run-from-ci) and [Results](/agent-testing/results).

## How to organise scenarios

Use test suites for the areas of the agent and labels for the cuts that cross them. A scenario belongs to exactly one test suite, and it can have any number of labels, so a test suite works as the folder and a label as the tag.

A small agent can start with one suite. Split by area when the fields or the owners differ. Never copy a suite per environment or per cadence, because copies drift: point a run plan at another target, or scope it by label, instead.

| Use               | For                                                            | Example                                   |
| ----------------- | -------------------------------------------------------------- | ----------------------------------------- |
| **Test suite**    | One area of the agent, owned by one team                       | `Refunds`, `Billing`                      |
| **Label**         | A cut across suites: speed, risk, or the kind of failure       | `smoke`, `safety`, `regression`           |
| **Target**        | Which environment: `support-agent` in `production` and in `development` are separate targets | `connected:support-agent@staging`         |
| **Run parameter** | One scenario under several setups, instead of copies of it     | `amount=49.95`, `plan=pro`                |
| **Run plan name** | One history on the Results tab for one way you run the suite   | `PR smoke`, `Refunds nightly`             |

Name a scenario after the behaviour it checks, with a short id in front if you track the rows elsewhere: `A1: double charge, refunds one charge`. The name shows on every result row, so a failing name should already tell you what broke.

A run plan scoped by labels is dynamic: a scenario that gets the `smoke` label is in the next run of every plan scoped to `smoke`. See [Run plans](/agent-testing/run-plans#where-a-run-starts) for the scopes.

## Run a smoke set on every change and the full suite on a schedule

Split the suite into two run plans. The smoke plan runs a handful of fast, high-risk scenarios on every pull request, so a broken change fails the check before review. The full plan runs every scenario of a test suite, often with a repeat count above one to catch flaky behaviour, on a schedule or before a release.

```bash
# On every pull request: the scenarios labelled smoke
langwatch run-plan run --label smoke --target connected:support-agent@staging \
  --name "PR smoke" --wait

# On a schedule: every scenario of one suite, three times each
langwatch run-plan run --test-suite Refunds --target connected:support-agent@staging \
  --name "Refunds nightly" --repeat 3 --wait
```

A run plan is a name and a configuration: the scope (test suites, labels or specific scenarios), the targets, the repeat count from 1 to 5 (for how many to use, see [How many times to repeat a scenario](/agent-testing/designing-a-suite#how-many-times-to-repeat-a-scenario)), and the simulator and judge models. Every run under the same name joins one pass rate history on [Results](/agent-testing/results). For the refund agent:

| Run plan | Scope | Target | Repeats | When | Pass bar |
|---|---|---|---|---|---|
| **PR smoke** | Label `smoke` | Staging | 1 | Every PR that changes the prompt or tools. | All pass. |
| **Refunds nightly** | Suite `Refunds` | Staging | 3 | On a cron schedule. | All pass, or a failure you can explain. |
| **Critical** | Label `critical` | Staging | 5 | Before a release. | Every repetition passes, strong judge. |
| **Refunds pre-release** | Suite `Refunds` | Staging | 3 | Before a release. | Happy paths and critical scenarios pass every repetition, the rest a majority. |
| **Production canary** | Label `canary` | Production | 1 | After each deploy. | All pass. |

Give every other test suite your releases rely on its own scheduled plan, such as `Order lookup nightly`, or name several with a repeated `--test-suite`. Leave out a [suite of candidates](#how-do-scenarios-move-from-draft-to-production).

LangWatch does not apply a pass threshold for you. `--wait` exits non-zero when any run failed, so use the exit code as a gate only on a plan whose bar is all pass. For any other bar, such as `Refunds nightly`, replace that command with this form, which fails the job only when the batch did not finish:

```bash
RESULT=$(langwatch run-plan run --test-suite Refunds --target connected:support-agent@staging \
  --name "Refunds nightly" --repeat 3 --wait --format json) || true
echo "$RESULT" | jq -es '.[0].outcome == "passed" or .[0].outcome == "failed"'
```

The job then stays green on `failed`, so your team reads the pass bar on Results. `failed` also counts a run that ended without success and with no verdict, such as one that errored or was cancelled, so read those there too. A run that succeeded with no verdict counts as passed.

This form does not gate a release. For a plan such as `Refunds pre-release`, have the job check `results` in the JSON against your bar. Each row gives the `scenarioId` and no labels, so match the rows to your labels yourself.

```bash
# Critical: 5 repetitions and a strong judge.
langwatch run-plan run --label critical --target connected:support-agent@staging \
  --name "Critical" --repeat 5 --judge-model openai/gpt-5 --wait

# Production canary: only the read-only scenarios, against production.
langwatch run-plan run --label canary --target connected:support-agent@production \
  --name "Production canary" --wait
```

Give the `canary` label only to scenarios that only read data, because a canary runs on real data. A refund scenario must never run in production. Do not declare setup or teardown hooks in the production process, and remove per-conversation seeding from it, because they run for every scenario, whatever its label. The production process must also be connected for the canary to reach it.

Add a plan evaluator with `--evaluator <id-or-slug>`, repeated for each one. The commands above leave it out to stay short.

LangWatch does not schedule runs itself: a run plan has no schedule or cron setting, and the API refuses one. Start the scheduled run from your CI's own scheduler, for example a GitHub Actions `schedule` trigger. See [Run from CI](/agent-testing/run-from-ci) for the batch id, the poll and the exit code.

## Isolate scenarios with setup and teardown hooks

A scenario that reads or writes real data needs that data to exist before the first turn and to be gone after the last, or one run changes what the next one sees. Setup and teardown hooks on a connected agent create the test data for each run and remove it afterwards.

You declare them on the connected agent in the SDK. For the arguments, what happens when a hook fails and the limits, see [Setup and teardown hooks](/agent-testing/setup-and-teardown-hooks).

Give each run its own names for the data it makes, such as a trace name or an order reference with the run id in it. Runs of one plan share a project, so counting "every trace named `checkout`" includes what other runs left behind. Traces have no delete route, so teardown cannot remove them; give each run its own trace name so counts stay exact.

## How much will a suite cost to run

A run plan starts one run per scenario, per target, per repeat: 20 scenarios against 2 targets with a repeat count of 3 is 120 runs.

Use cheaper models for the user simulator and the judge on routine scenarios, with the simulator and judge models of the run plan, and give critical scenarios a strong judge with **Override models** on the scenario. Each run is a conversation of up to the scenario's maximum turns, and you pay for your agent's model calls plus those of the user simulator and the judge.

To estimate the cost, run the plan once with a repeat count of 1 and read the **Total cost** in the run header. Divide it by the number of runs for the cost of one run, then multiply by the runs a schedule adds up to. For example, a 20-scenario plan that costs $0.80 per run and runs nightly against one target costs about $16 a night.

What the platform shows, per run and per plan:

| Where                                    | What it shows                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------ |
| Run header, hover                        | **Total duration**, **Total cost**, **Avg agent latency** and **Avg agent cost**, the averages with a p95 |
| Result row                               | **Time · cost** for that conversation                                          |
| Results tab, **Charts**                  | **Cost** for the period, next to **Executions** and **Pass rate**              |
| A turn, **View trace**                   | The trace of that turn, with its spans                                         |

What it does not show: a cost estimate before a run starts, a token count on a run, and a cost budget or cap on a run plan. LangWatch adds up the cost of the spans in each run's trace that have a cost, and **Avg agent cost** counts only the spans of your agent. A run whose trace never arrives shows no cost.

Runtime follows the same arithmetic. The scenario workers run a fixed number of conversations at a time, so a plan of many long conversations queues behind itself and takes longer than its slowest run. `langwatch run-plan run --wait` waits up to 45 minutes by default; pass `--wait 90` for a longer suite.

## How do scenarios move from draft to production

A scenario goes through three stages: a candidate someone proposed, a scenario that passes against the fixed agent, and a scenario in the suite your releases run. LangWatch has no lifecycle field for this. A scenario has no draft or candidate status, and the only state the platform tracks is archived, which leaves it out of runs. Promotion is a step your team takes, not something the platform does.

Keep the stages apart by where you store the scenario file. If your scenarios are files in your repository that a script syncs to LangWatch, keep proposals outside the synced directory until a person reviews them, and promote a scenario by moving its file in, in a reviewed pull request. A label such as `candidate` does not stop a sync: any scope that includes the scenario runs it.

If you write scenarios on the platform, keep proposals in a test suite of their own, such as `Candidates`, and promote one with **Move to suite**. Run plans still reach a candidate through a label or `--all`, so give it no label and scope no plan with `--all`.

Keep one such suite per destination, with the fields and evaluators of the destination suite, so the runs below exercise the real check. After the move, confirm the field values and run the scenario again: a blank value skips the evaluator that reads it.

Promote a scenario when all of these hold:

- It failed against the agent before the fix, so you know it can catch the failure.
- It passes against the fixed agent several times in a row (use **Run multiple times**), so it is not flaky.
- Its criteria check behaviour, not exact wording, so a harmless rephrase does not fail it.
- Its setup and teardown leave the project as they found it.

Removing a scenario is a promotion in reverse. If a sync script manages your scenarios, removing a file does not delete the scenario in LangWatch, and renaming a scenario in a script that matches by name creates a new one. Archive the old scenario in LangWatch after a rename or a removal.

## How local, platform and CI runs fit together

Scenarios run from three places, and every run reports to the same project, so you read the results of all three in LangWatch.

| Where           | Use it to                                                              | Page                                                        |
| --------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------- |
| Your machine    | Write a scenario and run it against a local agent while you work       | [Write scenarios in code](/agent-testing/scenarios-in-code) |
| The platform    | Let product and domain experts write, run and read scenarios           | [Test from the platform](/agent-testing/test-from-the-platform) |
| CI              | Run the smoke plan on each pull request and the full plan on a schedule | [Run from CI](/agent-testing/run-from-ci)                   |

A connected agent can be online in several environments at once, so one plan can run against `development` on your machine and against `staging` in CI. Against `production`, run only read-only scenarios. See [Environments](/agent-testing/environments).

## Turn production failures into regression scenarios

Every failure you find in production can become a scenario that keeps it fixed. LangWatch does not do this for you: there is no automatic step that turns a trace into a scenario.

1. **Trace.** Find the conversation that went wrong in your traces, from a user report, a low score or a review of recent traffic.
2. **Finding.** Write down what the agent did wrong, in one sentence that a judge could check: "issued the refund before it checked that the second charge existed".
3. **Validate.** Confirm the failure happens again with the same input, so you are fixing a behaviour and not a one-off.
4. **Failing scenario.** Write a scenario that acts out the conversation and has the finding as a criterion. Run it against the current agent and keep it out of the promoted suite while it fails, in the proposals directory or the `Candidates` suite.
5. **Review.** A person reads the scenario and its failing run and agrees that the criterion is the right one.
6. **Fix.** Open the pull request that fixes the agent, with the scenario moved into the suite in the same pull request, or moved with **Move to suite** when the fix ships. The run that passes against the fix is the proof, and the scenario stays in the suite as the regression test.
