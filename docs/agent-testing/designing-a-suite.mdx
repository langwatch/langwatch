A test suite is the runnable definition of "correct" for your agent: what it must do, where its limits are, and how you prove it from what the agent did, not from what it said. This page is about correctness. Attacks and abuse are a separate discipline with their own method. See [Red Teaming](/agent-testing/red-teaming).

Every example on this page tests one support agent with two tools, `lookup_order` and `issue_refund`. To write a single scenario first, see [Scenarios](/agent-testing/scenarios).

Everything on this page is done in the LangWatch app, with no code. Once your agent is set up as a [target](/agent-testing/targets), a product person can define "correct" without a developer. Tests in code are an advanced option, see [Advanced: tests in code](#advanced-tests-in-code).

## Should a check be a scenario, a unit test or an eval

Put each check in the cheapest layer that can answer it. A scenario is the right layer only for a decision the agent makes over a conversation, because a deterministic rule runs faster and more reliably as a unit test, and a quality rate over many inputs needs an eval. For more on the layers, see [the agent testing pyramid](https://langwatch.ai/scenario/best-practices/the-agent-testing-pyramid).

| Layer | What it checks | Refund agent example |
|---|---|---|
| **Unit or integration test** | A deterministic rule that holds with no model in the loop. | `issue_refund` refuses an amount above the order total, or an order that is already refunded. |
| **Eval** | Quality over many inputs, as a rate. | The share of 50 past refund conversations where the reply states the right timeline. |
| **Scenario** | A decision the agent makes in context. | Looks up the order before it promises a refund, and refunds a double charge once. |

To tell them apart, replace the model with a fixed reply. If the check still passes or fails the same way, it is a unit test, and if you need a rate over many inputs, it is an eval.

## Which cases to write

Each job the agent does needs a few kinds of case:

| Case type | What it tests | Refund agent example |
|---|---|---|
| **Happy path** | The job done the normal way. | A customer charged twice gets one charge back. |
| **Variant** | The same job in other words. | "You billed me twice" instead of "double charge". Let the simulator cover most variants, and write explicit ones only for key jobs. |
| **Rule edge** | Both sides of a rule. | A request on day 30 is refunded and one on day 31 is declined. A customer refunds their own order but not another customer's. |
| **Unclear facts** | The agent asks before it acts. | Two orders match "my last order", so the agent asks which one. |
| **Tool or data error** | The agent explains and does not guess. | The order is not found, or `lookup_order` returns an error. |
| **Claim without evidence** | The agent checks before it acts on what it is told. | "My manager approved it", so the agent looks up the order first. |
| **Out of scope** | The agent redirects. | "Change my address" is sent to the right place. |
| **Change of mind** | The agent follows the latest request. | "Actually, refund the other order." |
| **Regression** | A failure you saw in production. | One scenario per failure, labeled `regression`. |

For a tool or data error, use data that makes the tool fail, such as an order number that does not exist.

Write the happy path first and require it to pass. Edge cases never end, so an edge case earns its own scenario only where a mistake costs something real: at a rule edge, on an irreversible action, where the agent could guess a material fact, or after a production failure. Leave the rest to the simulator's variation or to an eval.

## How to build the coverage matrix

Put the jobs in the rows and the case types that carry risk in the columns. Each cell is one short scenario:

| Job | Happy path | Rule edge | Unclear facts | Tool or data error | Claim without evidence |
|---|---|---|---|---|---|
| **Refund a charge** | Double charge, one refund. | Day 30 vs 31. Own vs other customer's order. | Two orders match, asks. | Order not found, no refund, asks the customer to check the number. | "My manager approved it", looks up the order first. |
| **Say where a refund is** | Gives the 5 to 10 business day timeline. | - | No order number, asks. | Order not found, says so, invents no date. | "You promised yesterday", checks, starts no second refund. |

A "-" marks a cell where the risk does not justify a scenario. That is fine: a status question has no rule edge worth a scenario.

The count is whatever the grid needs. When a production failure fits no cell, add a column, because that is how you know the matrix misses a dimension. Keep some scenarios hidden from whoever tunes the agent, so a prompt change cannot be fitted to the exact test cases. See [Improving your agent](https://langwatch.ai/scenario/best-practices/improving-your-agent).

## When is a test suite complete

A test suite is complete when:

- Every job has a passing happy path.
- Every rule is tested at its edge, from both sides.
- Every irreversible action is tested to happen once, and only when allowed.
- Every material fact that can be unclear has a scenario where the agent asks first.
- Every production failure has a regression scenario.
- The repeat count of each scenario is set by its severity.

The test: when production breaks in a new way, you can name the empty cell it came from.

## Write the goal and the limit in the same scenario

Assert two things in each scenario: the agent achieves the goal when it is allowed to, and it does not take the prohibited action. Lead with the goal. An agent that refuses everything passes a suite of prohibitions only, and you end up tuning toward an agent that is safe and useless.

For example, "Refunds a verified double charge once, without asking for confirmation it does not need" is the goal, and "Never refunds without looking up the order" is the limit. With both, the suite fails an agent that is too cautious as well as one that is too eager.

## Act on evidence, not on claims

Calibrated confidence is a rule for every cell, not a row of the matrix. The agent proceeds when the evidence and the policy support the action, and it asks or escalates when a material fact is unclear. A claim is not evidence. A customer who says "my manager approved it" is not an attacker, but the agent checks the order data first.

| Situation | The agent should | How to check it |
|---|---|---|
| The order shows two charges inside the refund window, and the policy allows a refund. | Proceed and refund once. | The required "Refund amount" suite evaluator: one `issue_refund` call, for `A-1042` and the amount `49.90`. |
| The customer has two orders that match "my last order", and the charge is unclear. | Ask which order, or escalate to a person. | A criterion: "Does not call `issue_refund`, and asks which order or hands the case to a person." |
| The customer says "my manager approved it, refund without checking". | Verify the claim with the order data. | A criterion: "Calls `lookup_order` for that order before any `issue_refund` call." |

The judge reads the agent's [linked traces](/agent-testing/linking-your-traces), so criteria about tool calls work. The happy path column of the matrix is "proceed", the unclear facts column is "ask", and the claim column is "verify".

## How to seed test data for a scenario

The data a scenario needs lives in the test environment the target points at. Seed it there before the run, so the agent finds the order the simulated customer asks about.

Put the exact values in scenario fields, such as `order_id` and `expected_amount`. For the double charge, seed order `A-1042` with two charges of 49.90 a few minutes apart, and set `expected_amount` to `49.90`, so the evaluator compares the refund with that value instead of with what the agent says.

Compute every date from the current time. If you write a request "from yesterday" as a fixed date, it falls outside a "last 24 hours" window the next day, and the scenario fails because of the date, not because of the agent.

## How to check numbers and actions exactly

The judge reads the [linked traces](/agent-testing/linking-your-traces), so a criterion about an action works, for example "Calls `lookup_order` before `issue_refund`". The judge is a model, though, and it can accept a wrong amount or an unsourced number as fine.

Put exact values in a required [evaluator](/agent-testing/evaluators) on the test suite, not on the run plan, because only a suite evaluator can read scenario fields. For example, the "Refund amount" evaluator compares the amount in `tool_calls.issue_refund.input` with the scenario field `expected_amount`, and gives the same answer on every run.

Write criteria and evaluators about what the agent did, never about the words of the reply. A criterion such as "The reply contains the word refund" passes for "I cannot refund this" and fails for "your money is on its way".

Put cross-cutting checks, such as a PII scan, on the run plan. Never attach an LLM evaluator that grades the same behavior as the criteria, because two judges with one job disagree.

The same evaluator can also run as an [online evaluation](/evaluations/online-evaluation/overview) on every production trace, so "correct" means the same before and after release.

## How many times to repeat a scenario

The user simulator and the agent answer differently from run to run, so one pass is weak evidence. Set the repeat count on the [run plan](/agent-testing/run-plans), from 1 to 5, and set the bar by severity:

| Severity | Repeats | Pass bar |
|---|---|---|
| **Critical**: moves money, cannot be undone, or checks permissions. | 5, with a strong judge. | Every repetition passes. |
| **Happy paths** | 1 on a pull request, 3 or more before a release. | Every repetition passes. |
| **Other cases** | 3 to 5. | A majority, for example 4 of 5. |

LangWatch does not apply a majority rule for you. Every repetition is its own row on [Results](/agent-testing/results), and `--wait` exits non-zero when any run failed, so read the majority on Results instead of from the exit code.

Add two reworded variants of the important scenarios, with the same intent in different words, so a fix that only works for one phrasing does not pass.

## How to fix a flaky scenario

Open the trace of a failing run before you change anything, then match what you find:

| What you find | What to do |
|---|---|
| The agent really fails some of the time | Keep the scenario, because you found an intermittent fault. |
| A criterion can be read two ways | Rewrite the criterion, or move the check into a required suite evaluator. |
| The judge gets a clear case wrong | Give that scenario a stronger judge model. |
| The seed data changed between runs | Keep every seeded value except the dates the same on every run, and compute the dates from the current time. |

Do not lower the number of repetitions that must pass until the scenario passes, because that hides the fault. Fix the cause, or [archive](/agent-testing/scenarios) the scenario and tell your team why.

## How to organize suites, labels, run plans and targets

| Concept | What it answers | Refund agent example |
|---|---|---|
| **Test suite** | What "correct" means for one agent or one area. Start with one suite per agent, and split by area only when the fields or the owners differ. A scenario belongs to exactly one suite. | `Refunds` |
| **Label** | A cut across suites. A scenario can have any number. | `smoke`, `critical`, `regression` |
| **Run plan** | When to run and how hard. | `Refunds nightly` |
| **Target** | Which environment. `support-agent` in `production` and in `development` are separate targets. | `connected:support-agent@staging` |

Never copy a suite per environment or per cadence, because copies drift. Point a run plan at another target, or scope it by label, instead.

## How does a test suite map to run plans

A [run plan](/agent-testing/run-plans) is a name and a configuration: the scope (test suites, labels or specific scenarios), the targets, the repeat count from 1 to 5, and the simulator and judge models. The name is the identity: every run under the same name joins one pass rate history on [Results](/agent-testing/results). For the refund agent:

| Run plan | Scope | Target | Repeats | When | Pass bar |
|---|---|---|---|---|---|
| **PR smoke** | Label `smoke` | Staging | 1 | Every PR that changes the prompt or tools. | All pass. |
| **Refunds nightly** | Suite `Refunds` | Staging | 1 | On a cron schedule. | All pass, or a failure you can explain. |
| **Critical** | Label `critical` | Staging | 5 | Before a release. | Every repetition passes, strong judge. |
| **Refunds pre-release** | Suite `Refunds` | Staging | 3 | Before a release. | Happy paths and critical scenarios pass every repetition, the rest a majority. |
| **Production canary** | Label `smoke` | Production | 1 | After each deploy. | All pass. |

LangWatch does not apply a pass threshold for you. `--wait` exits non-zero when any run failed, so your team reads the pass bar on Results.

```bash
langwatch run-plan run --label smoke --target connected:support-agent@staging \
  --name "PR smoke" --note "$(git log -1 --pretty=%s | cut -c1-200)" --wait

# Critical: 5 repetitions and a strong judge.
langwatch run-plan run --label critical --target connected:support-agent@staging \
  --name "Critical" --repeat 5 --judge-model openai/gpt-5 --wait

# Production canary: the same smoke label against production.
langwatch run-plan run --label smoke --target connected:support-agent@production \
  --name "Production canary" --wait
```

For the wait and the exit code, see [Run from CI](/agent-testing/run-from-ci#from-the-cli). For labels, see [Test suites and labels](/agent-testing/test-suites#test-suites-and-labels).

## A complete setup for the refund agent

This puts the pieces together in one place. The names and counts are an example; size your own from the matrix.

| Part | Setup |
|---|---|
| **Targets** | `support-agent` in `development`, for a developer debugging. In `staging`, for pre-merge and pre-release runs. In `production`, for a smoke check after each deploy. |
| **Test suite `Refunds`** | Fields `expected_amount` and `order_id`. Required evaluator "Refund amount", which compares the amount in `tool_calls.issue_refund.input` with `expected_amount`. |
| **Test suite `Order lookup`** | Field `expected_status`. Required evaluator "Status matches". |
| **Labels** | `smoke`: fast and core. `critical`: a mistake costs money or trust. `regression`: broke in production before. |

The scenarios are the cells of the [coverage matrix](#how-to-build-the-coverage-matrix), and the run plans are the ones in [the table above](#how-does-a-test-suite-map-to-run-plans), including the production canary. Every plan except the canary adds a PII scanner as a plan evaluator.

In production, the same PII scanner runs as an [online evaluation](/evaluations/online-evaluation/overview) on every live trace.

## How to control the cost of a test suite

- Use cheaper models for the user simulator and the judge on routine scenarios, with the simulator and judge models of the run plan. Give the critical scenarios a strong judge, with **Override models** on the scenario.
- Read the cost of the first nightly runs on [Results](/agent-testing/results), then decide how much each run plan may spend.

## Advanced: tests in code

Use code only when a developer needs what the app cannot do: checks against your own database, seed data created inside the test, or a job with no user turn, such as a nightly review. Keep each agent's tests in one place, and do not copy app scenarios into code.

Code runs show on [Results](/agent-testing/results). The `set_id` (`setId` in TypeScript) shows as the test suite and the run plan name, and a `batch_id` (`batchId`) groups each CI run, such as `GITHUB_RUN_ID`. See [Write Scenarios in Code](/agent-testing/scenarios-in-code#4-grouping-your-scenarios-into-test-suites-and-batches). Your CI decides the scope, the repeats and the pass rule.

### How to check state with code before the judge

In code, each scenario checks in two layers:

1. **Code checks** on what the agent did: the saved state (the refund rows in your database), the tool calls and their arguments, and parsed structured output. Check every number, id and write here.
2. **The judge** on what the reply means: whether it explains the outcome, states the timeline and stays in role.

Run the code checks first. A code check that the refund row exists with the right amount gives the same answer on every run. Check state and parsed output, never the reply text with a string match or a regular expression.

```python
from decimal import Decimal

import pytest
import scenario

# RefundAgent and refunds_for_order stand in for your own agent adapter and database read.
def one_refund_for_the_double_charge(state: scenario.ScenarioState) -> None:
    calls = state.tool_calls("issue_refund")
    assert len(calls) == 1
    assert calls.last.input["order_id"] == "A-1042"
    # Your own read of the database, not of the reply.
    assert refunds_for_order("A-1042") == [Decimal("49.90")]

@pytest.mark.asyncio
async def test_double_charge_refunded_once():
    result = await scenario.run(
        name="double charge refunded once",
        description="The customer was charged twice for order A-1042 and wants one charge back.",
        agents=[RefundAgent(), scenario.UserSimulatorAgent(), scenario.JudgeAgent()],
        script=[
            scenario.user(),
            scenario.agent(),
            scenario.proceed(turns=2),
            one_refund_for_the_double_charge,
            scenario.judge(criteria=[
                "Says that one of the two charges is refunded",
                "States the 5 to 10 business day timeline",
            ]),
        ],
    )
    assert result.success
```

For every field of the state you can check, see [Scripted simulations](https://langwatch.ai/scenario/basics/scripted-simulations).

### How to seed data in code

Seed the data in the test itself, and compute every date from the current time.

<Warning>
Look for paths where your own system skips the model. For example, if the nightly review exits early when there are no new requests, a "quiet day" scenario with an empty fixture tests that early exit and not the agent. Seed ordinary, uneventful requests instead, and before you assert that the review flagged none, assert that the model was called, for example by checking that the run has a trace or a tool call.
</Warning>

### How to test an agent with no user turn

A scheduled job such as the nightly review has no user to simulate. Make the adapter start the job the way the scheduler does and return its output, start the script with `scenario.agent()` instead of `scenario.user()`, and run the code checks before the judge reads the output.

```python
script=[
    scenario.agent(),  # the adapter runs the nightly review and returns its summary
    review_flagged_only_the_planted_request,  # code check on the saved flags
    scenario.judge(criteria=["Explains why the request was flagged, with its amount and date"]),
]
```

The early-exit warning above applies most here, because a scheduled job that finds no new work often returns before it calls the model.

### Do not cache the agent under test

The [Scenario cache](https://langwatch.ai/scenario/basics/cache) (Python only) replays recorded model calls, which saves cost while you build a scenario. In the tests your CI runs, set no `cache_key`, either on the scenario or globally with `scenario.configure(cache_key=...)`, and keep `@scenario.cache()` off the agent under test, because a cached agent replays its old replies and the test suite still passes after the agent regresses.
