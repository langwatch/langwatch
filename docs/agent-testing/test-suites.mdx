## The rail

The **Scenarios** tab lists the test suites of the project under **Test Suites** in the rail on the left. Press one to open its scenarios in the table. **New Test Suite** asks for a name only.

<Frame>
<img className="block" src="/images/agent-testing/test-suite-rail-menu.png" alt="The test suite rail with the row menu of the Refunds test suite open" />
</Frame>

The row menu of a test suite offers:

| Action | What it does |
|---|---|
| **New scenario** | Opens the editor with this test suite preselected. |
| **Run suite** | Opens the run dialog with every scenario of the test suite in scope. |
| **Edit** | Opens the suite editor: the name, the fields and the evaluators. Past runs keep the old name. |
| **Open recent runs** | Lists the latest runs of this test suite. |
| **Archive suite** | Archives the test suite and the scenarios in it. Test runs are preserved. |

Every project has a **Default** test suite. A scenario saved with **No test suite** goes there.

Under the suite name, the header shows a chip per field and a chip per evaluator, and the count line `N scenarios · N fields · N evaluators`.

## Fields

A test suite reads like a dataset. Beyond the situation and the criteria, it declares typed fields, and a scenario in it may carry a value for each. A blank value skips the evaluators that read it. A field holds what an [evaluator](/agent-testing/evaluators) compares against: the golden SQL query, the reference answer, the tables the answer had to be written against.

**Edit suite** opens the suite editor. Under **Customize test suite**, **Add fields** opens the field rows: an identifier and a type each, with **Add field** for the next one and the arrows to reorder them.

| Setting | Rule |
|---|---|
| **Identifier** | Lowercase letters, digits and underscores, starting with a letter, up to 64 characters, for example `golden_sql`. `situation`, `criteria`, `name`, `input` and `output` are reserved. |
| **Type** | `text`, `number` or `boolean`. A text value is a growing text box on the scenario; a number a number input; a boolean a switch. |

A suite declares up to 30 fields. A field an attached evaluator still reads cannot be removed: detach the evaluator or change its mapping first. Removing a field keeps the values scenarios hold for it; the scenario editor lists them under **Not in this suite** until they are removed.

## Evaluators

The evaluators attached to a suite run after every scenario run and report beside the judge's verdict. A required one that fails fails the scenario. See [Evaluators](/agent-testing/evaluators) for the mappings, the gate and what each run reports.

## Run a test suite

**Run suite**, in the rail menu or at the top of the table, opens the [run dialog](/agent-testing/run-plans#the-run-dialog). The run goes under the run plan named after the test suite and the agent, for example `Refunds checkout-prod`, so every run of the same test suite against the same agent joins one history on the Results tab.

## Move scenarios between test suites

**Move to suite...** in the row menu of a scenario opens **Move to test suite**, which lists the test suites of the project. Select several rows and press **Move to suite** in the bar that appears to move them together. A scenario belongs to exactly one test suite.

## Test suites and labels

A test suite is the group you run before a release. A label is a tag on a scenario, and a scenario can have any number of them. A run plan can scope by labels across every test suite, for example every scenario labelled `smoke`, so use labels for a cut that crosses the test suites and a test suite for the group that ships together.

## From Code

Scenarios written with the Scenario SDK and run from your own test runner report to the project and appear under **From Code** in the rail, one entry per `setId`. Their table is read-only and shows each scenario with its last run. Edit them in your repository. The platform lists them so their results appear next to the test suites written here.

## From the CLI and the API

```bash
langwatch test-suite create "Case lookups" --field golden_sql:text --field table_schema:text
langwatch test-suite update "Case lookups" --field golden_sql:text --field table_schema:text --field row_limit:number
langwatch test-suite get "Case lookups" --format json
```

`--field identifier:type` repeats, and on `update` the flags together replace the list the suite declares. The same list travels as `fields` on `POST /api/v1/test-suites` and `PATCH /api/v1/test-suites/{id}`; see the [Test Suites API reference](/api-reference/test-suites/overview). The Python and TypeScript SDKs take `fields` on `test_suites.create` / `testSuites.create` and `test_suites.update` / `testSuites.update`; the MCP tools `platform_create_test_suite` and `platform_update_test_suite` take the same.
