This guide sets up the test suite of a text-to-SQL agent in the LangWatch interface: two fields, `golden_sql` and `table_schema`, a required **SQL Query Equivalence** evaluator that reads the query the agent ran from its `run_sql` tool call, and a score judge that reports without gating. By the end, every run of the suite shows one verdict per evaluator beside the judge's, and a wrong query fails the run.

## Before you start

- A project with a [connected agent](/agent-testing/connect-your-agent), so the run dialog has an agent to test.
- [Linked traces](/agent-testing/linking-your-traces) when a mapping reads a tool call, the contexts or the spans. The evaluator reads them from the run's traces, so without them such an input fails with the reason `no run_sql call in the trace`.
- The evaluator itself. **Add evaluator** in the suite editor lists the [evaluators](/evaluations/evaluators/overview) of the project and lets you create one there.

  </Step>
  <Step title="Give each scenario its values">
    Open a scenario with **Edit** in its row menu, or press **New scenario**. After the criteria, the editor shows one box per field. Paste the query the agent's own query has to be equivalent to into `golden_sql` and the `CREATE TABLE` statements into `table_schema`, then **Save**. A scenario you leave blank is not failed: the evaluators that read the blank field are skipped for it.

  </Step>
  <Step title="Attach the evaluator and confirm its mappings">
    Back in the suite editor, under **Add evaluators**, press **Add evaluator** and pick **SQL Query Equivalence**. The evaluator drawer opens on the attachment, because the evaluator reads expected values, with two mappings inferred from the names of the fields: `expected_output` reads `Scenario.fields.golden_sql` and `expected_contexts` reads `Scenario.fields.table_schema`.

    `output` is inferred as the last agent message, which is the reply and not the query the agent ran. Change it to the **Trace** source, tool call `run_sql`, `input`, so the evaluator reads the exact query the agent sent to the database. A tool call is never inferred, so this is the one mapping you set by hand.

## How to verify it worked

- The header of the run shows a pill per evaluator, and the table has an **Evaluators** column.
- A scenario whose golden query asks for something the agent did not query, for example a count over the last 7 days against an agent that filtered on status only, reads `Failed` in the **Result** column with `Criteria 1/1` in its drawer: the judge passed the conversation, the evaluator failed the run.
- `langwatch simulation-run get <scenarioRunId> --format json` returns `results.evaluations`, one entry per evaluator with its `status`.

## Troubleshooting

### The evaluator was skipped

The scenario has no value for a field the mapping reads. The row reads `Skipped` with the reason `no golden_sql on this scenario`, and the run keeps the judge's verdict, because a skipped evaluator never gates. Fill the field on the scenario, then **Rerun this scenario** from the row menu.

<img className="block" src="/images/agent-testing/run-drawer-evaluator-rows-skipped.png" alt="The run drawer of a passed run, with SQL Query Equivalence skipped and the reason no golden_sql on this scenario, while the other two evaluators report" />
</Frame>

The skipped row names the blank field. The verdict stays `PASSED`.

### Run suite opens the evaluator drawer instead of running

A required input of an attached evaluator has no mapping, for example after the mapping was cleared in the drawer. The chip shows an amber alert in the suite editor and in the run dialog, and **Run** opens the drawer on that evaluator with `Please map all required fields: expected_output` instead of starting the run. Map the input, press **Save Changes**, then run again. The API refuses the same run with `suite_evaluator_mappings_missing`.

### The evaluator failed with a reason about the trace

`no run_sql call in the trace`, `no retrieved contexts in the trace` or `no spans in the trace` means the run's traces did not hold what the mapping reads. The platform waits for the traces and retries, and on the last attempt records the evaluator as `failed` with that reason, so a required one fails the run.

Check that the agent's traces reach the project and join the run, see [Linking your traces](/agent-testing/linking-your-traces), and that the tool name in the mapping is the span name the agent reports.

### The run stays on evaluating

The evaluators have not reported yet. The status settles as soon as their results are recorded, and a grading job that is lost is recorded as errored evaluators once its deadline passes, so a required evaluator that never ran fails the run instead of leaving it pending.

## From the CLI

```bash
langwatch test-suite create "Case lookups" \
  --field golden_sql:text --field table_schema:text \
  --evaluator sql-query-equivalence --required

langwatch scenario create "Open cases count" \
  --situation "The user is a support lead who wants to know how many support cases are currently open." \
  --criteria "Gives a number of open cases" \
  --test-suite "Case lookups" \
  --field golden_sql="SELECT COUNT(*) FROM cases WHERE status = 'open'" \
  --field table_schema="CREATE TABLE cases (id INT, account_name TEXT, status TEXT, priority TEXT, created_at TIMESTAMP)"

langwatch test-suite update "Case lookups" --evaluators-json evaluators.json

langwatch test-suite run "Case lookups" --target http:agent_abc123 --wait

langwatch simulation-run get <scenarioRunId> --format json   # results.evaluations
```

`--evaluator` infers the mappings the way the suite editor does, so `output` reads the last agent message. The tool call mapping goes through `--evaluators-json`, whose shape is on the [Evaluators](/agent-testing/evaluators#from-the-cli-and-the-api) page.
