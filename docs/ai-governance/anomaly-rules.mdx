<Info>**Pairs with:** [AI Gateway → Budgets](/ai-gateway/budgets). Budgets enforce hard spend limits; anomaly rules detect patterns *before* a budget breach, starting with spend spikes.</Info>

<Note>**Available on Enterprise plans.** Non-enterprise organizations see an upgrade card on `/settings/governance/anomaly-rules` instead of the composer. See [Open-core licensing](/ai-governance/overview#open-core-licensing) for the full Apache 2.0, Enterprise split.</Note>

Anomaly rules are the "Detect" layer of the [governance control plane](/ai-governance/control-plane#tier-3--audit-log-ingest). The composer at `/settings/governance/anomaly-rules` accepts a rule definition and persists it; LangWatch then evaluates each rule against the [governance activity it has recorded](/ai-gateway/governance/activity-monitor-event-sourcing) and produces an `AnomalyAlert` row when a violation is detected.

<Note>**Detection runs on a recurring sweep, not on every request.** Rules are re-evaluated every few minutes, so expect an alert to appear within minutes of the traffic that triggered it rather than the instant it lands.</Note>

This page documents what LangWatch actually evaluates today vs what's preview-only, so you don't author rules that look "active" in the list but never fire.

## Rule-type coverage

These are the rule types a rule can be saved with; only one of them is evaluated today. Any other value is rejected when you save.

| Rule type | Detection coverage | What it detects | Threshold config keys |
|-----------|------------------|------------------|------------------------|
| **`spend_spike`** | ✅ Live | Spend in a rolling window rising sharply above the spend that came before it | `windowSec`, `ratioVsBaseline`, `minBaselineUsd` |
| `rate_limit` | ⏳ Preview | Volume of activity per actor per window | (config schema TBD) |
| `after_hours` | ⏳ Preview | Activity outside your business-hours window | (config schema TBD) |
| `model_drift` | ⏳ Preview | A shift in which models your org is using | (config schema TBD) |
| `error_rate` | ⏳ Preview | A rise in failed requests | (config schema TBD) |

**⏳ Preview** rules can be created and the row will show `active` in the list, but they are skipped at evaluation time and no AnomalyAlert is produced. Until detection for each ships, treat them as "save the rule for the future, don't expect alerts."

If you need detection beyond `spend_spike` today, the recommended shape is one of:

- Stand up Prometheus + Grafana against the gateway metrics endpoint, see [Cookbook · Prometheus alerts](/ai-gateway/cookbooks/prometheus-alerts) for the alert ruleset.
- Hook your SIEM to the OTel trace stream LangWatch already emits per project.

## Writing a working `spend_spike` rule

Open `/settings/governance/anomaly-rules` → click **New anomaly rule**.

Fields that shape detection:

| Field | Typical value | What it does |
|-------|---------------|---------------|
| **Name** | `Spend spike on Cowork prod` | Free-text label; surfaces in `recentAnomalies` and the alert dispatch payload. |
| **Severity** | `warning`, `critical` | Drives the `/governance` KPI breakdown (`anomalyBreakdown.{critical,warning,info}`) and downstream dispatch routing once C3 ships. |
| **Rule type** | `spend_spike` | Pick exactly this, see coverage table above. |
| **Scope** | `organization`, `source_type`, `source` | Filters which IngestionSources the rule applies to (see Scope coverage below). |
| **Scope ID** | (cuid) | Required when scope is `source_type` or `source`. The IngestionSource ID can be copied from `/settings/governance/ingestion-sources/<id>` or the URL of the per-source detail page. |
| **Threshold config** | (JSON object, see below) | Per-rule-type tuning knobs. |
| **Destination config** | `{}` (today) | Reserved for future Slack, PagerDuty, SIEM dispatch, see Dispatch coverage below. |

### Threshold config: `spend_spike`

```json
{
  "windowSec": 86400,
  "ratioVsBaseline": 2.0,
  "minBaselineUsd": 1.0
}
```

All three keys are required, and they are the only ones the rule reads. `windowSec` is the single time knob: the baseline follows from it.

| Key | Starter value | Meaning |
|-----|---------------|---------|
| `windowSec` | `86400` (24 h) | The "current" window spend is summed across, ending at the moment the detection sweep runs. |
| `ratioVsBaseline` | `2.0` | Multiplier, the rule fires when current spend ≥ baseline × ratio. `2.0` means "double the recent norm." |
| `minBaselineUsd` | `1.0` | Floor, evaluation is skipped when the baseline is below this value. Prevents trivial alerts on cold sources where the recent norm was ~$0.01 and a 2× rise is meaningless. |

**The baseline is the recent past, not a fixed point in history.** It is the average spend across the six windows immediately before the current one, so with `windowSec: 86400` today's spend is measured against the average of the previous six days. Nothing to configure: widen or narrow `windowSec` and the baseline moves with it, and it keeps tracking your traffic as it grows rather than drifting out of date.

Sensible starting values for most orgs:

| Goal | `windowSec` | `ratioVsBaseline` | `minBaselineUsd` |
|------|---------------|----------------------|---------------------|
| Today vs the previous six days (default) | 86400 | 2.0 | 1.0 |
| This hour vs the previous six hours (tighter, fastest to react) | 3600 | 3.0 | 0.10 |
| This week vs the previous six weeks (looser, least noisy) | 604800 | 1.5 | 5.0 |

## Scope coverage

| Scope | Detection coverage | Notes |
|-------|------------------|-------|
| `organization` | ✅ Evaluated | Fires on any IngestionSource in the org. Best default. |
| `source_type` | ✅ Evaluated | Fires on every source whose `sourceType` matches (e.g. all `otel_generic` sources). |
| `source` | ✅ Evaluated | Fires on a single named IngestionSource. |
| `team` | ⏳ Preview | Persisted but not applied as a filter today. Don't rely on it. |
| `project` | ⏳ Preview | Same. |

## Dispatch coverage (C3 in flight)

The composer's **Destination config** field accepts a JSON object describing where to push the alert. Today the dispatch path is **log-only**: alerts surface on the `/governance` dashboard's "Recent anomalies" section but no Slack message, PagerDuty page, SIEM event is generated.

C3 (in flight on the [governance platform](https://github.com/langwatch/langwatch/pull/3524) branch) wires `triggerActionDispatch` so the destinationConfig values below start working:

```json
{
  "slack":     { "webhookUrl": "https://hooks.slack.com/services/..." },
  "pagerduty": { "routingKey": "..." },
  "webhook":   { "url": "https://your-siem.example.com/ingest", "secret": "..." },
  "email":     { "addresses": ["sec-on-call@your-company.com"] }
}
```

Until C3 lands, leave destinationConfig empty (`{}`) and rely on the dashboard to surface alerts. Setting a real Slack webhook today does **nothing**: you'll think alerts are wired and they aren't.

## Verify a rule is firing

Two angles, same data:

**Web**: open `/governance` and look for the rule's name in the "Recent anomalies" section. Each fire creates one row keyed by `(ruleId, triggerWindowStart)` so a single window doesn't produce duplicate alerts.

**CLI**: `langwatch governance status` shows `hasAnomalyRules: true` once at least one rule exists. The `recentAnomalies` query is wired into the same `api.activityMonitor.recentAnomalies` tRPC procedure the dashboard reads.

For a dogfood loop you can drive yourself:

1. Create a `spend_spike` rule scoped to your test IngestionSource with `minBaselineUsd: 0.001` (tiny floor) and `ratioVsBaseline: 1.5`.
2. Send one OTel event with `gen_ai.usage.cost_usd: 0.05` (baseline seed), see [otel-generic, Test it now](/ai-gateway/governance/ingestion-sources/otel-generic#test-it-now--copy-paste-curl).
3. Wait long enough for the seed to fall out of the current window and into the baseline behind it (a `windowSec` of 86400 means 24h, so use the tighter values from the table above for fast iteration).
4. Send a second event with `gen_ai.usage.cost_usd: 2.00` (the spike).
5. Give the next detection sweep a few minutes, then reload `/governance`, the alert should appear in "Recent anomalies" with `state: open` and a populated `detail.ratio`.

## What's persisted vs what's evaluated

A rule that's persisted but unevaluated is intentional, admins can pre-stage rules so when detection for that rule type ships, no rework. But it's a real failure mode if you don't know which is which. The two coverage tables above are the source of truth: **only `spend_spike` + (`organization` | `source_type` | `source`) actually fires today**. Everything else is preview state.
