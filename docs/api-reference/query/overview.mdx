title: "Overview"
description: "Run a read-only LangWatchQL SELECT over your project's analytics views, or discover which views and columns your key can query."
---

The Query API runs read-only LangWatchQL `SELECT` statements over your project's analytics views. `POST /api/v1/query` runs one statement. `GET /api/v1/query/schema` lists the views, columns, and function names your key can query.

The request body is the query itself, and a `200` is the result itself: no envelope, no wrapper object around it. A failure answers with the standard LangWatch error envelope and a real HTTP status, so one parser reads every response.

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/v1/query` | Run one LangWatchQL statement. |
| `GET` | `/api/v1/query/schema` | List queryable views, columns, permission gates, and function names. |

## Authentication

Send your LangWatch API key in any one of these forms:

| Form | Header |
|------|--------|
| Token header | `X-Auth-Token: <token>` |
| Bearer | `Authorization: Bearer <token>` |
| Basic | `Authorization: Basic base64(projectId:token)` |

Any LangWatch API key works here: project, organization, or personal. Rows come from every project the key holds the `analytics:view` permission on: a project key reaches its one project, an organization or personal key reaches every project it can read. No project header is required. To narrow the result to one project, filter inside the statement itself with `WHERE TenantId = '<project id>'`.

A result that mixes rows from more than one project carries the `MULTI_PROJECT_RESULT` diagnostic, so a caller who expected a single project can tell.

## Errors

Both endpoints answer with the standard LangWatch error envelope and a real HTTP status. No wrapper sits around it. See [Error Envelope](/ai-gateway/api/errors). Where a failure has a fix, the envelope's `meta` carries the corrective fields for it. For example, `FUNCTION_NOT_ALLOWED` lists `allowedFunctions`.

| Status | `code` | When |
|--------|--------|------|
| `400` | `validation_error` | The request body failed validation. |
| `400` | `lwql_unparseable` | The statement is not valid LangWatchQL. |
| `400` | `lwql_not_permitted` | The statement is valid but calls something the policy withholds, for example a function outside the allowlist, or a `LIMIT` above 10,000 rows (`meta.violations` names it `LIMIT_TOO_HIGH` or `LIMIT_REQUIRED_PER_BRANCH`). |
| `401` | `missing_credentials` | No supported authentication credential was sent. |
| `401` | `invalid_credentials` | The API key is unknown, revoked, or has the wrong secret. |
| `403` | `api_key_permission_denied` | The key lacks the `analytics:view` permission on any project. |
| `413` | `lwql_result_too_large` | The result body exceeds about 8,000,000 bytes. |
| `422` | `query_scan_limit_exceeded` | The statement is valid but would scan more data than the key allows. |

## Response ceilings

A statement that names no `LIMIT` is capped at 10,000 rows: that `LIMIT` is appended before the query runs, so a large answer comes back as one page rather than a stream. To read the rest, page with `LIMIT`/`OFFSET` and an `ORDER BY`.

A statement whose own `LIMIT` asks for more than 10,000 rows is refused with `LIMIT_TOO_HIGH` before it runs. When using `UNION`, every top-level branch must carry its own `LIMIT` clause of 10,000 rows or fewer, or the query is refused with `LIMIT_REQUIRED_PER_BRANCH`. A result whose body exceeds about 8,000,000 bytes is refused outright with `lwql_result_too_large`. Select fewer columns or a smaller `LIMIT` to bring it under the cap.
