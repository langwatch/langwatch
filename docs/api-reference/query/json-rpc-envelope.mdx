## Why one endpoint, two methods

`POST /api/v1/query` is the LangWatchQL door: one path, dispatching on a JSON-RPC
2.0 `method` field rather than the URL. That is unusual for this API: every
other family is one path per operation. So this page exists to carry the
explanation the generated endpoint page cannot: the envelope shape, the two
methods it dispatches to, and the one error-shape gotcha a client must code for
before it can trust a failure response.

## The envelope

Every request body is a JSON-RPC 2.0 envelope:

```jsonc
{
  "jsonrpc": "2.0",
  "id": 1,                  // string, number, or null: echoed back on the response
  "method": "query.run",    // or "query.schema"
  "params": { /* method-specific, see below */ }
}
```

This door is **pragmatic JSON-RPC, not strict**. Two departures from the spec,
both deliberate:

- **Real HTTP status per outcome.** A refused query answers `422`, not `200`
  with an `error` field: the transport status always tells you whether the
  call was refused, so you never have to parse the body first to find out.
- **No batch support.** Send one envelope per request. An array body is not a
  batch call.

## The two methods

### `query.run`

Executes one read-only LangWatchQL `SELECT` over the analytics datasets your
project can see.

**`params`:**

| Field | Type | Description |
|-------|------|-------------|
| `sql` | `string` | The LangWatchQL statement to run. |
| `parameters` | `Record<string, string \| number \| boolean \| null>` | Optional. Bound values for named parameters in `sql`. |
| `timeWindow` | `{ start: string; end: string }` | Optional. Fills the statement's reserved `period_start` / `period_end` parameters. |
| `granularitySeconds` | `number` | Optional. The datapoint step, for a statement that declares `{period_granularity_seconds:UInt32}`. |

**`result`:**

| Field | Type | Description |
|-------|------|-------------|
| `columns` | `{ name: string; type: string }[]` | The result's column names and types. |
| `rows` | `Record<string, unknown>[]` | The result rows. |
| `statistics` | `{ elapsedMs, rowsRead, bytesRead, rowsReturned }` | Execution statistics for this run. |
| `truncated` | `boolean` | Whether a response ceiling cut the result short. |
| `followsTimeWindow` | `boolean` | Whether the statement declared the reserved time-window parameters. |
| `followsGranularity` | `boolean` | Whether the statement declared the reserved granularity parameter. |
| `granularitySeconds` | `number` | Optional. The step this run was bucketed at, when one applied. |
| `diagnostics` | `Diagnostic[]` | Advisory notes about the result. See below. |

```bash
curl -X POST https://app.langwatch.ai/api/v1/query \
  -H "X-Auth-Token: $LANGWATCH_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "query.run",
    "params": {
      "sql": "SELECT trace_id, total_cost FROM traces WHERE started_at BETWEEN {period_start:DateTime64} AND {period_end:DateTime64} LIMIT 100",
      "timeWindow": { "start": "2026-08-01T00:00:00Z", "end": "2026-08-25T00:00:00Z" }
    }
  }'
```

```jsonc
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "columns": [
      { "name": "trace_id", "type": "String" },
      { "name": "total_cost", "type": "Float64" }
    ],
    "rows": [
      { "trace_id": "abc123…", "total_cost": 0.0031 }
    ],
    "statistics": { "elapsedMs": 42, "rowsRead": 8192, "bytesRead": 524288, "rowsReturned": 100 },
    "truncated": false,
    "followsTimeWindow": true,
    "followsGranularity": false,
    "diagnostics": []
  }
}
```

<Info>
**Diagnostics are advisory and never reject a query.** An empty `diagnostics`
list means no known issue was detected. It is **not** proof that the answer is
the one you meant. A statement can declare the reserved time-window parameters
and never actually compare against them; `followsTimeWindow: true` only tells
you the parameters were declared and filled, not that they bounded the rows
returned. Read the statement, don't just read the flag.
</Info>

### `query.schema`

Lists the datasets your key can query: names, descriptions, grain, join keys,
the time column each one prunes on, freshness, and every column's type,
description, unit, and the permission gates it requires, plus a runnable
example statement per dataset.

**`params`:** none. Sending `params` is not an error; it is ignored.

**`result`:**

| Field | Type | Description |
|-------|------|-------------|
| `database` | `string` | The database name these datasets live in. |
| `datasets` | `Dataset[]` | The datasets this key may query. |

Each `Dataset`:

| Field | Type | Description |
|-------|------|-------------|
| `name` | `string` | Dataset name, as used in `FROM`. |
| `description` | `string` | What the dataset contains. |
| `grain` | `string` | What one row represents. |
| `joinKeys` | `string[]` | Columns other datasets join to this one on. |
| `timeColumn` | `string` | The column that prunes this dataset by time. |
| `freshness` | `string` | How current the data is. |
| `columns` | `Column[]` | Every column, with `name`, `type`, `description`, `unit` (`ms` \| `USD` \| `tokens` \| `tokens/s` \| `null`), `gates` (`input` \| `output` \| `costs`), and `available` (whether *this* caller currently holds the gates it needs). |
| `exampleSql` | `string` | A runnable statement against this dataset. |

```bash
curl -X POST https://app.langwatch.ai/api/v1/query \
  -H "X-Auth-Token: $LANGWATCH_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc": "2.0", "id": 1, "method": "query.schema"}'
```

```jsonc
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "database": "langwatch_analytics",
    "datasets": [
      {
        "name": "traces",
        "description": "One row per trace.",
        "grain": "trace",
        "joinKeys": ["trace_id"],
        "timeColumn": "started_at",
        "freshness": "near real-time",
        "columns": [
          {
            "name": "total_cost",
            "type": "Float64",
            "description": "Total cost of the trace, in USD.",
            "unit": "USD",
            "gates": ["costs"],
            "available": true
          }
        ],
        "exampleSql": "SELECT trace_id, total_cost FROM traces WHERE started_at BETWEEN {period_start:DateTime64} AND {period_end:DateTime64} LIMIT 100"
      }
    ]
  }
}
```

## The critical gotcha: not every failure carries the JSON-RPC wrapper

**Only authentication and authorization failures (401, 403) answer with the
canonical error envelope alone, never wrapped in a JSON-RPC `error`.**
Everything else this endpoint answers with, including a refused query (400,
422) or even an unexpected server failure (500), is wrapped, because those are
all raised from inside the endpoint's own handler, which installs a JSON-RPC
error handler around itself. 401/403 are the one exception: they are raised by
auth middleware *before* the request reaches that handler, so there is no
JSON-RPC layer around them yet.

**Branch on the HTTP status first, then read `error.code`.** A client that
assumes every failure carries a JSON-RPC envelope will misread a refused
credential: it will look for `error.data.code`, which is absent, because on a
401/403 the code is at `error.code` directly.

<Warning>
This is the one thing to get right before you write a query client against
this endpoint. Get the branch order backwards and a refused API key silently
falls through to a generic error path instead of surfacing `invalid_api_key`.
</Warning>

Compare the two shapes side by side. A **refused query** (400/422): the
request reached this endpoint's handler, which wraps its refusal in JSON-RPC:

```jsonc
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32000,
    "message": "Query refused.",
    "data": {
      "type": "unprocessable_entity",
      "code": "query_scan_limit_exceeded",
      "message": "This query would scan more data than this key allows.",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
    }
  }
}
```

The canonical envelope (`type`, `code`, `message`, `trace_id`) rides as
`error.data`. `error.code` at the outer level (`-32000`) is the JSON-RPC
protocol code, not the application code; the code your logic should branch on
is one level deeper, at `error.data.code`.

A **refused credential** (401/403), raised before this endpoint's handler and
never wrapped:

```jsonc
{
  "error": {
    "type": "unauthorized",
    "code": "invalid_api_key",
    "message": "The API key provided is invalid or has been revoked.",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
  }
}
```

No `jsonrpc` key at all. The canonical envelope is the whole body, at the top
level: the same shape every other LangWatch API family answers with.

| HTTP status | Body shape | Where the canonical `code` lives |
|-------------|------------|-----------------------------------|
| 200 | JSON-RPC success | (no error) |
| 400, 422, 500 | JSON-RPC error | `error.data.code` |
| 401, 403 | Canonical envelope, unwrapped | `error.code` |

## Using the SDK instead

The `langwatch` TypeScript SDK handles the envelope and this exact branching
for you: call it and read a result or a typed error, never a raw JSON-RPC
body:

```typescript
import { LangWatch } from "langwatch";

const langwatch = new LangWatch();

// query.run
const result = await langwatch.query.query({
  sql: "SELECT trace_id, total_cost FROM traces WHERE started_at BETWEEN {period_start:DateTime64} AND {period_end:DateTime64} LIMIT 100",
  timeWindow: { start: "2026-08-01T00:00:00Z", end: "2026-08-25T00:00:00Z" },
});
console.log(result.rows, result.diagnostics);

// query.schema
const schema = await langwatch.query.schema();
console.log(schema.datasets.map((d) => d.name));
```

On failure the SDK throws `LangWatchHandledError` (or `QueryApiError` when the
platform did not name the cause). Unwrapping applies whether the failure was
JSON-RPC-wrapped (400/422) or bare (401/403), so `error.code` reads the same
canonical code either way and you never branch on transport shape yourself:

```typescript
import { isLangWatchHandledError } from "langwatch";

try {
  await langwatch.query.query({ sql: "SELECT * FROM traces" });
} catch (err) {
  if (isLangWatchHandledError(err)) {
    console.error(err.code, err.message); // e.g. "query_scan_limit_exceeded"
  }
  throw err;
}
```
