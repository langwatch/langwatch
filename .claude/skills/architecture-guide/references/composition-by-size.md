# The composition root, at three sizes

Owned by the `architecture-guide` skill. `config-composition.md` says what the
pieces are; this file shows them assembled. The ruling design is ADR-147 plus
the 2026-09-17 decisions in `.claude/coordinator/ARCHITECTURE-LAW.md`: the
supply is a fluent chain whose required calls are computed from the installed
modules, `boot()` takes no arguments, and it is callable only when everything
the modules declared has been supplied. An absent supply is a compile refusal
(`MissingSupply<...>`), never a runtime fallback.

The point to take away first: **the composition root does not grow with the
system.** Installing the next module edits `modules/catalogue.json`, never a
root. There is one entry point, `createApp({ role })` from `@langwatch/kernel`,
for tests and production alike. `createProcess`, `withProvided`,
`withMemoryRepositories`, `membersFrom`, `reads(...)` statics and the
`members:` option are deleted spellings — a file still carrying one is
conversion debt, not a shape to copy.

## Size 1 - one module, nothing around it

An installation test. Storage is declared, not wired: the process supplies
`relational` as memory and the module's registry runs its memory tier.

```ts
const runtime = await createApp({ role: "api" })
  .withModules([secretServer])
  .withConfig({ secret: {} })
  .withRelational(memoryDatabase())
  .boot();
```

A supply token is provided by name — `.provide({ licenseSource })` — and a
peer arrives by its `*Api` token, never by importing the peer's service or
repository. The installation-test spelling for peer doubles is being settled
by the l7 lane; do not copy an old test's `withProvided`, it is deleted.

## Size 2 - one process role, every module

The whole api. This is the shape, and it is the only shape:

```ts
// apps/api/src/app/api-production.composition.ts (the shape, abridged)
await createApp({ role: "api" })
  .withModules(serverModules)
  .withConfig(apiModuleConfig(config))   // one slice per module name
  .withSecrets(secrets)
  .withEncryption(cipher)
  .withRelational(prisma)
  .withAnalytical(clickhouse)
  .withKeyvalue(redis)
  .withEventing(eventing)
  .withObservability((o) => o.withLogging(pino).withTracing(otel()).withMetrics(otel()))
  .withTransportAuth((a) => a
    .withStaticTokens({ cron, langyInternal, instanceAdmin })
    .withBrowserSession(session))
  .boot();
```

`serverModules` comes from `@langwatch/installed-modules/server`, generated by
`pnpm generate:modules` from `modules/catalogue.json`. Transport hosting (REST,
tRPC, SSE), static serving, error formatting, lifecycle and the HTTP listener
are the kernel's job, opened by `boot()` from what the modules declared —
never per-process host files.

## Size 3 - the process around the composition

A process is an entrypoint plus ONE composition file. The process boundary —
signals, fatal handlers, shutdown phases — is `Server` from
`@langwatch/process-server`; telemetry and config are resolved before it so a
config parse failure is logged and traced.

```ts
// the whole main
const secrets = await SecretEnvironmentService.create({ source: process.env }).resolve();
const config = resolveApiConfig(secrets.environment);
configureLogger({ ...loggerConfigurationFrom(config), redactPaths: secretLogRedactPaths() });
const server = Server.create({ name: config.serviceName, logger, shutdownDeadlineMs });
const runtime = await createApp({ role: "api" })/* …the chain above… */.boot();
server.host({ name: "api runtime", start: () => runtime.start(), stop: () => runtime.stop() });
await server.listen();
```

The worker is the same shape with `role: "worker"` and its runtime hosted with
`drain: true`; a module declares its jobs and subscriptions on its own
declaration, and the worker's per-domain composition files are gone.

## What makes a root grow, and what to do instead

A root that is getting longer is a symptom. The three causes, and their answers:

- **Constructing a collaborator in the root.** It belongs in the module - a
  repository, a channel, or a service. If the root builds it, the root owns
  knowledge of the module's internals.
- **A bespoke requirement handed to one module.** Each field is a closed-vocabulary
  supply, a peer `*Api`, a repository, a channel, or something the module derives
  itself from what it is already supplied.
- **A conditional.** `if (config.x) install(...)` in the root means the module
  should refuse by name at boot instead, which the compile-time supply already does.

The root never grows. A change that needs it to grow has found a gap in the
primitives, and the honest move is to report the gap rather than widen the root.
