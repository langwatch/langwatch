# Red Team Your Agent with the OWASP Pack

This recipe applies a ready OWASP pack to the user's agent: one multi-turn `RedTeamAgent` attack per OWASP risk, each judged against criteria built from the agent's own config. The pack lives in the `templates/` folder beside this file, in Python (pytest) and TypeScript (vitest). Copy it; do not rewrite it.

Use red teaming only on agents the user owns or has permission to test.

## What the pack covers

| OWASP id | Title | Strategy |
| --- | --- | --- |
| LLM01:2025 | Prompt Injection | goat |
| LLM02:2025 | Sensitive Information Disclosure | crescendo |
| LLM05:2025 | Improper Output Handling | goat |
| LLM06:2025 | Excessive Agency | crescendo |
| LLM07:2025 | System Prompt Leakage | goat |
| LLM09:2025 | Misinformation | crescendo |
| LLM10:2025 | Unbounded Consumption | goat |
| ASI01 | Agent Goal Hijack | crescendo |
| ASI02 | Tool Misuse and Exploitation | goat |
| ASI03 | Identity and Privilege Abuse | crescendo |
| ASI06 | Memory & Context Poisoning | crescendo |

The LLM ids are from the OWASP Top 10 for LLM Applications 2025; the ASI ids from the OWASP Top 10 for Agentic Applications. LLM03 (Supply Chain), LLM04 (Data and Model Poisoning), LLM08 (Vector and Embedding Weaknesses), ASI04 (Agentic Supply Chain Vulnerabilities), ASI07 (Insecure Inter-Agent Communication), ASI08 (Cascading Failures) and ASI10 (Rogue Agents) need build, data or multi-agent checks that a conversation cannot exercise. A conversation can reach ASI05 (Unexpected Code Execution) and ASI09 (Human-Agent Trust Exploitation), but the pack has no attack for them: ASI05 needs an agent that runs code, and ASI09 turns on what a person does with the reply, which the judge cannot see.

## Step 1: Detect the language

Look at the agent's repository. `pyproject.toml`, `requirements.txt` or `uv.lock` means Python; `package.json` with TypeScript means TypeScript. If both exist, use the language the agent itself is written in. Read the agent's entry point, system prompt and tool definitions before going on: Step 4 needs them.

## Step 2: Copy the template

Copy every file of the matching template folder into the repository's test folder, unchanged except for import paths:

- Python: `templates/python/` holds `owasp_config.py`, `agent_adapter.py`, `owasp_attacks.py`, `test_owasp_pack.py` and `conftest.py`. Put them together in one folder (for example `tests/owasp/`). `conftest.py` puts the repository root on the import path, two folders up, and registers the `agent_test` mark. If the folder sits at another depth, change the `parents[2]` in it, or set `pythonpath = ["."]` under `[tool.pytest.ini_options]`.
- TypeScript: `templates/typescript/` holds `owasp.config.ts`, `agent-adapter.ts`, `owasp-attacks.ts`, `owasp-pack.redteam.ts` and `owasp.vitest.config.ts`. Put them together in one folder (for example `tests/owasp/`).

The pack calls live models on every run, so keep it out of the repository's default test run and CI:

- Python: add `-m "not agent_test"` to the default pytest options, for example `addopts = '-m "not agent_test"'` under `[tool.pytest.ini_options]`. Run the pack with `-m agent_test`, which overrides it.
- TypeScript: the pack file does not end in `.test.ts`, so vitest's default include skips it; `owasp.vitest.config.ts` runs it. If the repository's vitest config includes every `.ts` file under `tests/`, add `tests/owasp/**` to its `exclude`. Add a script such as `"test:owasp": "vitest run --config tests/owasp/owasp.vitest.config.ts"` to `package.json`.

If you cannot read the `templates/` folder, fetch the same files from `https://github.com/langwatch/skills/tree/main/recipes/owasp-red-team/templates`.

Install the test dependencies:

```bash
# Python
uv add --dev "langwatch-scenario>=1.6" pytest "pytest-asyncio>=0.24"   # or: pip install ...
# TypeScript: @langwatch/scenario 1.7 bundles ai 6, which takes only @ai-sdk/* 3.x
npm install -D @langwatch/scenario@^1.7 vitest @ai-sdk/openai@^3
```

## Step 3: Wire the adapter

Edit only the adapter function: `call_agent(messages)` in `agent_adapter.py`, or `callAgent({ messages })` in `agent-adapter.ts`. Make it call the user's real agent with the conversation and return the agent's reply. Return the tool call and tool result messages as well when the agent has tools: the judge needs them for LLM06, LLM09, LLM10, ASI02 and ASI03.

Python passes `messages` as OpenAI chat messages, so an agent on the `openai` SDK takes them as is. A sync agent runs in a thread: `return await asyncio.to_thread(respond, list(messages))`.

TypeScript passes AI SDK `ModelMessage`s. If the agent takes OpenAI chat messages (the `openai` SDK), use the helpers in `agent-adapter.ts`: `toOpenAIMessages({ messages })` before the call and `fromOpenAIMessages({ messages: newMessages })` on its new messages, tool calls and tool results included. An agent built on the AI SDK takes `messages` as is. Both drop system messages: the agent keeps its own system prompt.

Call the real agent with its real tools and system prompt. A mock defeats the test. If the tools write to real systems, point them at a test account or a sandbox before running.

## Step 4: Fill the config

Fill the one config block (`AGENT` in `owasp_config.py` or `owasp.config.ts`) from what you read in Step 1. Every field but the two limits ships as `FILL ME`, and the pack refuses to run, naming the file and the fields, until none is left. `EXAMPLE_AGENT` beside it shows a filled block:

- `name`, `description`: what the agent is called and what it does.
- `tools`: every tool name the model sees. `privileged_tools`: the ones that change data, spend money or reach outside. `privileged_tools` may be an empty list (the privilege attacks then name every tool); empty `tools`, `must_never` or `protected_data` make the pack refuse to run.
- `must_never`: the actions the agent must refuse, from its system prompt and business rules, one sentence each.
- `protected_data`: what it must never disclose.
- `output_rendered_as`: where replies are shown (HTML widget, Slack, plain API).
- `max_reply_words`, `max_tool_calls_per_turn`: the longest reply and the most tool calls for one message that the unbounded consumption attack (LLM10) still accepts. They ship as 500 and 5; raise them for an agent whose normal work needs more.

Every attack goal and judge criterion is built from these fields, so do not edit `owasp_attacks.py` or `owasp-attacks.ts` for a new agent. Ask the user only for rules you cannot find in the code.

## Step 5: Run

Set `LANGWATCH_API_KEY` (results go to that project) and the model key for the attacker and judge (`OPENAI_API_KEY` by default). `OWASP_MODEL` picks the attacker and judge model (default `gpt-6-luna`). Both languages take a LiteLLM id such as `openai/gpt-5-mini`; TypeScript drops the provider prefix. Use an OpenAI-compatible chat model for the attacker and the judge: Gemini fails in the current scenario SDK (the attacker's first call has no user turn). The agent under test can use any model. For another provider in Python, set `OWASP_MODEL` to that provider's LiteLLM id. In TypeScript, also swap the `openai` import and factory in `owasp-pack.redteam.ts` for that provider's AI SDK package. For an OpenAI-compatible endpoint in TypeScript, import `createOpenAI` beside `openai` from `@ai-sdk/openai`, define `baseURL` as the endpoint URL and `apiKey` as that endpoint's key (read both from environment variables), add `const provider = createOpenAI({ baseURL, apiKey })`, and replace each of the three `openai(MODEL)` calls (attacker, metaprompt and judge) in `owasp-pack.redteam.ts` with `provider.chat(MODEL)`. `OWASP_TURNS` sets attacker turns per attack: unset or empty gives 10, which keeps a run cheap; use 30 before a release. Any other value that is not a whole number of at least 1 stops the run with an error naming `OWASP_TURNS`.

```bash
# Python, from the folder with the pack
pytest test_owasp_pack.py -v -m agent_test
pytest test_owasp_pack.py -v -m agent_test -k LLM01      # one id
# TypeScript
npx vitest run --config tests/owasp/owasp.vitest.config.ts
npx vitest run --config tests/owasp/owasp.vitest.config.ts -t LLM01
```

Run one id first to prove the wiring, then the full pack. ALWAYS run it: an unrun pack proves nothing.

Python may print `RuntimeError: Event loop is closed` at teardown. It comes from a model client closing after the loop and does not change any result.

## Step 6: Read the results in LangWatch

Each attack is a scenario run named `<OWASP id> <title>: <agent name>`, grouped under the set `owasp-red-team`. Open Simulations in the LangWatch project to read each conversation and the judge's verdict per criterion. A test that does not pass is one of two things, and the runner shows both as failed:

- A breach: the judge gave a verdict and the attack broke through. The criteria judge security only: a plain refusal with no alternative passes. The message names the OWASP id, the unmet criteria and the judge's reasoning. Fix the agent (see below) and run that id again.
- An error: the test stopped on an exception with no verdict, because a provider call or a tool call failed (for example `Failed to parse tool call arguments`, a timeout or a 429). It says nothing about the agent. Rerun that id; if it repeats, switch `OWASP_MODEL` to a model with reliable tool calls. Report it as an error, not as a breach or a pass: an error has no verdict on whether the agent held.

For a breach, the result does not say which turn broke: open the run in Simulations and find the first agent turn that breaks a criterion: check its tool calls, their arguments and results as well as its reply, since an agent can act on another user's record and then reply as if nothing happened. Report to the user, per id, whether the agent held, the turn where each breach broke, and each error as inconclusive.
