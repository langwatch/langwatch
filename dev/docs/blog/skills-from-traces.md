# Rewriting my coding agents with LangWatch

I've been doing a fairly large refactor of LangWatch, with Claude Code doing much of the work. The first usage report on one pull request came back with 43.7 billion tokens and a value of $28,654.10. That's the recorded usage priced at model rates, which needs separating from what actually gets paid under a subscription, but it was enough to make me go back and look at what on earth we'd been doing.

Claude Code was already instrumented through our [LangWatch plugin](https://github.com/langwatch/agent-plugin). I had the prompts, model calls, tool calls, timings and token usage, with the repository and branch attached. The plugin also gives Claude a skill for querying LangWatch through the CLI, so I could ask it to pull its own traces and work through them with me, in the same conversation where I was asking it to change the code.

We started with that PR and ended up looking at a month of my usage: 16,980 traces across 240 sessions. Long-running conversations were carrying old context into every new call. Commands were going through wrappers and getting refused by guards. I'd been watching this from the other end, telling an agent what I wanted, correcting it when it wandered off, and occasionally wondering why a supposedly small job was still going. Now we could follow the calls that had happened between my messages.

My first instinct was to use that to fix my skills. I already had a set that took an idea through a plan, a spec, implementation and review. They covered quite a lot, and I'd put a fair amount of thought into them, but in use they were too interested in the technical process. I wanted to explain what I was trying to achieve and have the agent help me get there. It would get busy organising the work, and I'd still have to pull it back to whether the thing we were building was any good.

We used those sessions to work out what to change in the instructions, then used the revised skills for the next bit of work. Claude kept emitting traces while we did this, so we could run the same comparisons against the new activity as we went. I wanted to know if the changes were helping before I'd spent another week using them.

Some of the investigation needed correcting first. We'd counted the cost of carrying instructions once per user turn, even though a turn can involve dozens of model calls, each reading context again. We'd also treated Bash commands returning a nonzero exit code as failures without properly accounting for what the command was doing. Writing a failing test and then fixing the code is quite a normal afternoon; an efficiency measure that marks the first half as wasted work is going to give you some fairly poor advice.

I had four models go through the research independently. They found contradictions, arithmetic mistakes and a claimed improvement that predated the instructions supposedly responsible for it. We could return to the underlying traces and correct the analysis. We also put the aggregate calculations into a [versioned script](https://github.com/langwatch/langwatch/blob/aaaf952f60742ab9abd15528ab2aaf04bcb266d9/dev/scripts/agent-usage-probe.mjs), because letting each agent redefine a measurement every time it runs makes the comparison fairly useless.

The working draft for my [skills repository](https://github.com/0xdeafcafe/skills) has a coordinator responsible for the overall job, with separate agents for shaping the idea, building it and reviewing it. They use the skills for the parts they need. The coordinator is meant to keep referring back to what I asked for, what we've agreed good looks like, and what still needs resolving before we can sensibly build it.

I want it doing that during the build too. Getting the tests green doesn't settle whether we've delivered the thing I wanted.

We changed how much context they carry as well. References can be loaded when they're relevant, workers get a bounded assignment, and handoffs preserve the decisions and unfinished work that someone will actually need to continue. For a request like “read through all this”, I'd like the coordinator to split substantial reading across Haiku or Sonnet where that makes sense, keep track of which sources have been covered, and check the important claims itself. I don't need the most expensive model reading every line, but I do need it to notice if one of the summaries has quietly missed the document that changes the answer.

I also wanted to deal with an irritating habit of agents: you're halfway through something complicated, they spot an unrelated UX problem, and suddenly that's what you're doing. In the revised skills, they can record the observation, give me a small nudge if it warrants one, and carry on. Those observations come back at review, where they need to be resolved or explicitly carried forward. A required part of the work can't be relabelled as a follow-up just because the agent would like to finish.

During this work, Claude spotted that the coordinator told workers to collect their changes by committing a slice, while the merge skill knew that doing so during an active merge was unsafe. Both instructions existed in the same setup, giving the agent contradictory advice about an operation that could damage the merge.

We reproduced the helper's behaviour in a disposable repository. It moved `HEAD` to a one-parent commit and removed the selected file's conflict stages, while other merge state remained. We fixed the coordinator and the helper together: check what Git is actually doing, stage an intermediate resolution, and use a separate snapshot through a temporary index when a checkpoint is needed. The handoff also had to say which state existed only on that machine, so the next agent wouldn't assume a commit contained everything it needed.

The tasks were changing while we changed the skills, so I don't have a controlled percentage saving to put here. I also forgot to enable Codex capture for its part of the work, leaving us with the conversation and Git history for that portion. We could inspect the fresh Claude traces during the rewrite, but there's more work to do before making a before-and-after cost claim.

You can take the same approach to recommendations about tooling. RTK filters verbose command output before the agent reads it. If LangWatch shows an agent running eligible operations without it, there's enough of a starting point to investigate a saving: take those operations, measure the reduction on comparable output, and work out what carrying the smaller result through later calls would have cost. For directly billed usage, that can become an estimate of what you could have saved on the bill, tied to work you actually did.

Our own analysis managed to apply a reduction to output that was already filtered, effectively counting it twice. The command-rewriting hook was also involved in the guard refusals we'd been looking at elsewhere. Once we put those together, the recommendation changed. You'd want to do the same check after introducing it: confirm that the commands are using it, see whether the output shrinks, and look for retries or missing information that undo the benefit. This is where I want the usage advisor to go, with recommendations checked against your traces as you use them. Each of those detectors still needs validating.

I wanted tests for these behaviours so we could keep changing the skills without having to discover the same problems again. We used [LangWatch Scenario](https://langwatch.ai/scenario/) with its Claude Code adapter to give a real Claude process a task, a temporary repository and the revised skills.

For the merge case, we create an actual conflict, leave another worker's file unresolved, and give the agent an old handoff that tells it to make an ordinary commit. We then inspect the repository it leaves behind. It has to collect its own resolution while preserving the merge and the other worker's work.

We added cases for the other behaviours too: working through an ambiguous request before implementing it, retaining observations until review, and covering a set of documents that disagree with each other. These run the agent through the situation, which turns up things you miss when you're reading a skill and thinking it sounds reasonable. One reading test initially insisted on delegation, but Claude had noticed that the documents were repetitive and read the distinctive material directly. We had to correct our test. The case intended to exercise delegation now asks for workers explicitly, and we kept the earlier response as an example of our own bad assumption.

We saved actual responses from Opus, Sonnet and Haiku, including failed and incomplete runs, with the model and instruction versions attached. The fixtures use synthetic tasks, so my private conversations don't need to be distributed with the skills.

Those recordings also let us test the evaluation code locally. If we change how it recognises tool errors or completion, we can run that logic over responses we've already inspected, without paying for another agent run. When the next model comes out, I'll run the same merge, review and reading cases against it and compare what it does with the runs we've kept.
