## 0. The answer in one picture

```
                      ┌────────────────────── tools/seedgen (Go, one deterministic generator) ──────────────────────┐
 haven seed ─────────►│ plan: persona × tier × seed × anchor × days ─► lazy action stream (never materialised)      │
 haven up (auto) ────►│ draws: sha256(recipe, seed, kind, n)   curves: diurnal × weekday × growth × incidents     │
 cmd/seedgen (CI) ───►│ telemetry chunks: services/telemetrysim Build(BatchSpec{Start}) ≤ 500 spans, whole traces│
 upgradelab cell ────►│ guard: AIMD window ◄── worker backlog · ClickHouse memory/parts · Redis · host pressure   │
                      └───────┬──────────────────────────────┬──────────────────────────────┬─────────────────────┘
                              │ route "task" (HEAD only)     │ route "door" (any release)   │ after drain
                              ▼                              ▼                              ▼
       pnpm task seed:apply  (NDJSON over stdin/stdout)    REST · tRPC · OTLP · gateway    coverage (static + run-time)
       tools/seedgen/runner: a LANGWATCH_TASK_MODULES      SCIM/SSO via idpsim             isolation check (hybrid)
       plugin; createTasks(app) calls installed *Api ops   Stripe-signed webhooks          report.md / report.json
                              │                              │                              snapshot cache (capture)
                              └──────────────┬───────────────┘
                                             ▼
                         commands ──► Redis group queues ──► the real worker ──► Postgres · ClickHouse (shared +
                         private targets) · storagesim (shared + private buckets) · llmsim · nlpgo · langevals ·
                         mailsim · outboundsim · analyticssim
```

Five lines:

1. **One generator, two executors.** `tools/seedgen` plans every action deterministically; the
   `task` executor calls installed module `*Api` operations in the tasks process (HEAD), the `door`
   executor calls public doors (HEAD slice, live mode, external-origin kinds, old releases).
2. **Alex's hybrid path holds without deviation**: config and lifecycle through module APIs and
   commands, bulk telemetry through batched ingest operations, a slice through the public doors.
   Old releases (upgradelab) take the door route for the subset of kinds they hold (§3.3).
3. **Memory is guarded by flow control, not by tiers**: a bounded window of in-flight chunks
   that halves on worker backlog, ClickHouse memory or part pressure, Redis memory or host memory
   pressure, and stops with a resumable checkpoint when it stalls (§5).
4. **Business time is backdated; machine time is not.** Spans, logs, metric points and session
   events carry history; command `occurredAt`, event ids and queue scores stay real (§6).
5. **Coverage reports, never blocks**: a static inventory check and a run-time "every covered item
   has rows" check run in the nightly and on demand (§10, §11).

Nothing in `modules/`, `packages/` or `apps/` gains seeding code, except the one product change Q1
asks for (the backdated trace input) and the two evaluation inputs Q2 asks for. No new `*Api`

or an exemption, never a new operation (§4 ruling, 2026-09-27).

The runner is loaded only where haven or CI sets `LANGWATCH_TASK_MODULES=@langwatch/seedgen-runner`;
a production image never names it. It runs in the tasks role, producer-only: every command it sends
is executed by the stack's real worker.

## 2. The protocol between seedgen and the runner

NDJSON, one line per message, seedgen → runner on stdin, runner → seedgen on stdout. The Go structs
are the source; the runner's Zod schemas mirror them; `tools/seedgen/testdata/protocol/*.ndjson` is
read by both test suites so the two cannot drift.

```
action  {"id":"<run>/<seq>","kind":"prompt.create","org":"$org:startup-1","project":"$project:startup-1/support",
         "as":"$user:startup-1/owner","key":"support-bot","input":{...},"at":"2026-09-20T10:14:00Z"}
ack     {"id":"<run>/<seq>","ok":true,"refs":{"$prompt:startup-1/support-bot":"<minted id>"}}
refusal {"id":"<run>/<seq>","ok":false,"code":"<HandledError code>","retryable":false}
```

- `$refs` are symbolic: the product mints every id (ids are strict KSUIDs; nothing is derived).
  seedgen substitutes known refs before sending and records new ones from acks in the checkpoint.
- `key` is the action's natural key (handle, slug, name). On resume the runner reads by natural key
  through the owner's `find*` operation before creating, so a replayed action is a no-op.
- Telemetry actions (`trace.otlp`, `log.otlp`, `metric.otlp`) carry one OTLP JSON export request.
- `retryable` refusals are retried by seedgen with back-off; others are recorded and the run
  continues (a fault cohort expects some, §7.6).

Where an op takes an `Authorization` the runner cannot obtain without fabricating one, the kind
takes the door route as the persona owner's session. The runner never builds an access object.

### 3.2 Why the ruling stands against the throughput finding

Opus found doors and in-process sends cost the same worker drain. Both routes are bounded by the
worker, so the task route is chosen for what it removes, not for speed: the 31-day door refusal
(with Q1), the per-request usage allowance (`otlpUsageLimit`) that would refuse large seeds on a
plan cap, the HTTP body cap on chunk size, and the session plumbing of ~60 config kinds. The door
route keeps what only it proves: credentials, permissions and the wire.

### 3.3 Old releases (upgradelab)

The `*Api` of an old release is not HEAD's, so upgradelab uses the door route only, for the subset
of kinds its cells feed (`tools/upgradelab/seed/coverage.json`): the same plan, draws, telemetry
chunks and guard, its own release-specific tenancy SQL (plan-upgrade R7), and today's
`seed/product.go` tRPC calls reshaped as door-route actions. The trace ids that `product.go`
draws from `crypto/rand` become plan draws (SG15).

## 4. Tiers

Tiers are presets over the flags. `--spans N` overrides telemetry volume (1 to ~2,000,000); logs
and metric points follow in proportion (logs ≈ 1 × spans, metric points ≈ 2 × spans). Counts below
are the defaults per run, all personas selected unless noted. Durations are targets to be measured
in SG5 (est. 500-1,500 spans/s laptop, 2-5k CI, Opus §3).

| Tier | Orgs / projects / users | Traces / spans | Logs / metric points | Config and runs | Default use | Target |
| --- | --- | --- | --- | --- | --- | --- |
| `tiny` | 4 / 6 / 12 (one org per persona, no hybrid) | 300 / 1,500 | 1,500 / 3,000 | every kind once; 1 scenario run, 1 experiment (5 rows), 20 evaluations | `haven up` auto-seed | ≤ 60 s to ready |
| `small` | 6 / 16 / 60 (+1 private org) | 10,000 / 50,000 | 50,000 / 100,000 | every kind in every state; 20 runs per run kind | `haven seed` default | ≤ 5 min |
| `medium` | 12 / 48 / 400 (+2 private orgs) | 60,000 / 300,000 | 300,000 / 600,000 | 100 runs per run kind; 2,000 dataset rows | nightly | ≤ 30 min CI |
| `large` | 24 / 120 / 1,200 (+2 private orgs) | 400,000 / 2,000,000 | 2,000,000 / 4,000,000 | 400 runs per run kind; 20,000 dataset rows | opt-in, laptop ceiling | ≤ 90 min |

Every tier keeps the rare-state cohort (every enum value, every lifecycle column null and set, the
fault cohort of §7.6). Larger volumes than `large` are upgradelab's L and XL (plan-upgrade §2.2),
never a haven seed. Default `--days 30`.

## 5. The memory guard

1. **Streaming.** The plan is a lazy iterator over (persona, org, project, day, hour) cells. A
   telemetry chunk is built when the window has room and dropped once acked. seedgen holds at most
   `window × chunk` payloads: its RSS stays under 256 MB at any tier (asserted by a test).
2. **Batching.** A chunk is ≤ 500 spans and ≤ 4 MB encoded, made of whole traces (so the trace
   lane's 64-span coalescing works), interleaving tenants so one tenant's queue group never holds
   the run. Logs and metrics chunk at 1,000 records.
3. **Window (AIMD).** In-flight chunks start at 4, floor 1, ceiling 32. Every 2 s the guard reads:

   | Signal | Read | Halve at | Pause at, resume below |
   | --- | --- | --- | --- |
   | Worker backlog | `ops.getDashboardSnapshot` as the stack operator (workerrun precedent): queued jobs, oldest age, dead letters | 20,000 jobs or oldest 60 s | 50,000 jobs or 180 s; resume < 10,000 |
   | ClickHouse memory | `system.metrics` `MemoryTracking` over haven's `max_server_memory_usage` (`tools/thuishaven/domain/clickhouse.go:66`) | 70 % | 85 %; resume < 60 % |
   | ClickHouse parts | max active parts per partition (`system.parts`), running merges (`system.merges`) | 150 parts | 300 parts; resume < 100 |
   | Redis | `INFO memory` used over `maxmemory` (`HAVEN_REDIS_MAXMEMORY_MB`) | 70 % | 85 %; resume < 60 % |
   | Host | macOS `kern.memorystatus_vm_pressure_level`; Linux `/proc/pressure/memory` | warn | critical |
   | Refusals | ClickHouse codes 241 (memory) and 252 (parts), HTTP 429/503, retryable acks | any | 3 in a row |

   Three clean reads in a row add 1. Each change is logged once with the signal that caused it.
4. **Stall.** Paused for 10 minutes, the run stops with exit 4 `stalled`, naming the signal and
   value, after writing its checkpoint; `haven seed --resume` continues from it.
5. **Preflight.** Before the first action seedgen estimates rows and bytes per store for the plan
   and refuses (exit 2, nothing written) when the estimate exceeds free disk, or the ClickHouse cap
   is below the tier's floor (`large` needs 6 GB), naming the haven limit that raises it.
6. **Checkpoint.** After each acked action: the plan cursor, the ref table and the counters, in
   `<stack home>/seed/run.json` (CI: the run directory). Resume replays from the cursor; natural keys
   (§2) and the trace lane's `(tenant, trace, span)` idempotency keys make the overlap a no-op.

## 6. Time and retention

### 6.1 Four clocks, one moved

| Clock | Seeded value |
| --- | --- |
| Business time: span start and end, log time, metric point time, session and scenario event times | backdated across `[anchor − days, anchor]` with the curves |
| Command `occurredAt` | now (the receipt time the door would stamp) |
| Event `createdAt` and KSUID | now (minted by the worker) |
| Queue ready score, leases, schedules | now |

Only business time moves. Backdating `occurredAt` would hide events from `EventLogReadSeat`'s
±2-day window around the event id's time (Codex §2) and needs a clock seam the product does not
have (~1,089 `nowInstant()` calls). Config objects (prompts, workflows, members) are dated now;
the UI shows their history as versions, not as dates. Time-relative lifecycle states (expired keys,
invites, shares) use the operation's own expiry input where it accepts a past instant; otherwise they
are exemptions with the reason "needs a clock" in `coverage.json`.

Anchor: `--anchor`, default now truncated to the hour, stamped in the run manifest. Curves: weekday
× hour-of-day × growth trend × named incidents (an outage day, a model rollout, a prompt regression),
deterministic per seed.

### 6.2 Retention first

Every ClickHouse row stamps `_retention_days` at write time, and haven pins a 7-day platform default
(`tools/thuishaven/domain/overlay.go:34-44`). So before the first data action in an org the seed sets
retention to the smallest value ≥ `days + 14` that the org's plan accepts: the paid presets 35 and
63, or any whole week ≥ 49 on an enterprise plan
(`modules/data-retention/contract/src/data-retention.ts:87-89`); 30 days gives 49 or 63. A plan
that refuses the value stops the seed for that org, before any data, naming org, plan and value.
How the free-plan cohort keeps more than 7 days is Q4.

### 6.3 Past 31 days

Spans older than 31 days take the backdated input of Q1 on the task route; the door route never
sends them (seedgen refuses a door-route trace chunk older than 31 days). The backdated input is
capped by the project's retention: a span older than retention is a seed bug and refuses. Logs and
metrics have no past limit. Evaluation results are dated now unless Q2 rules otherwise.

## 7. Personas

### 7.1 startup

One org, one team, one project (ruling), 3 users (owner, one invited and accepted, one pending).
A RAG support bot: OTLP traces with retrieval, tool and LLM spans, a prompt with 3 versions and a
`production` tag, 1 dataset, 2 evaluators with monitors (ON_MESSAGE, AS_GUARDRAIL), 1 dashboard, an
alert trigger to outboundsim. SaaS paid team plan (Q4). Onboarding milestones fire.

### 7.2 enterprise SSO/SCIM

4 teams, 10 projects, 50+ users. SSO via idpsim (OIDC and SAML connections through every
`SsoConnection` state the doors reach), SCIM provisioning and churn from idpsim (create, deactivate,
reactivate, group moves), custom roles, grants at org, team and project scope (revoked and expired),
API keys in every state, break-glass, join requests, audit log entries, varied retention and privacy
policies, enterprise subscription (SaaS) or the test-suite licence (self-hosted shape).

### 7.3 gateway-heavy

Virtual keys in every state (ACTIVE, DISABLED, REVOKED, expired; USER, LANGY, CONNECT), budgets on
every scope × window × BLOCK/WARN, gateway traffic through aigateway to llmsim with success, provider
error, blocked by guardrail and cancelled outcomes, a budget breach, governance ingest sources,
anomaly rules and alerts, cost rollups, webhooks to outboundsim with retryable and terminal faults.

### 7.4 agent/eval-heavy

Agents and workflows with versions (nlpgo), scenarios and suites with runs (success, failed, error,
cancelled, cut at limit; voice when voicesim is up), experiments (batch evaluation and workbench
v3, an aborted run, a failed cell), datasets with object-storage content, evaluators of every kind,
annotations with every score type and queues, coding-agent sessions (Claude Code and Codex presets).

### 7.5 hybrid tenancy (a mix, not a fifth persona)

`--private N` (default 1 in `small`, 2 in `medium` and `large`, 0 in `tiny`) places N extra orgs,
each a reduced copy of one of the four personas, on private stores while Postgres stays shared:

1. haven creates a private ClickHouse database per private org on the stack's ClickHouse server
   (`<stack db>_private_<n>`) and a private bucket on storagesim (`<stack>-private-<n>`);
2. the seed creates the org shell through `OrganizationApi` (the org id is minted);
3. haven writes `CLICKHOUSE_URL__seed__<orgId>` and `DATAPLANE_S3__seed__<orgId>` into the stack's
   secrets overlay (never printed), runs the upgrade pass (every ClickHouse target is migrated), and
   restarts api and worker with the reloaded env (routes are parsed once at boot, §7);
4. the seed creates the org's projects and all its data;
5. the **isolation check** proves: every telemetry, evaluation and analytics row of a private org's
   tenants is on its private target and none on shared; no shared tenant's row is on any private
   target; private buckets hold only the private org's objects and shared buckets none of them.
   Rows written in step 2, before the route existed, are listed as an expected exemption by event
   type and time (Q3).

The hybrid mix is skipped by auto-seed (it restarts the stack) and runs in `small` and above.

### 7.6 Edges in every persona

A fault cohort, labelled so a healthy run never ends with unexplained dead letters: llmsim forced
errors, outboundsim 5xx, a PII trace that redacts, a dead-lettered span, a spooled (large) span,
multimodal content, a wide trace (5,000 spans), an erased user, an archived and a revived project.
The run report counts expected dead letters by cohort; any other dead letter is a failure.

### 7.7 Deployment shapes

haven stacks run SaaS. `--shape saas|sh-licensed|sh-free` exists for the harness and the nightly; it
switches persona details (subscription versus licence, SSO entitlement) and never the env, which the
caller (upgradelab's shape files, the nightly's compose env) owns.

## 8. Content

The corpus (`tools/seedgen/corpus/`) is committed, small and authored: per persona domain, question
templates, answer bodies, RAG passages, tool-call shapes, prompt texts, dataset rows and scenario
scripts, with slots filled by draws. It supplies bulk telemetry text without a model call. llmsim
answers every model call the seed actually runs (workflows, scenarios, evaluations, gateway
traffic, experiments); haven points model providers at llmsim for seeded orgs. Names are invented
(`Northwind Support`, `user17@seed.test`), never a person or company.

## 9. Triggers and the CLI

### 9.1 `haven up`

On a stack whose stores hold nothing beyond the fixed identity, after `storage-seed`, haven runs the
`tiny` seed: from the snapshot cache when a matching entry exists (seconds), generated otherwise.
`haven up` waits at most 60 s, then reports ready and lets the seed finish in the background;
`haven status` shows its progress and result. `haven up --no-seed` or `HAVEN_AUTO_SEED=0` skips it.

### 9.2 `haven seed`

```
haven seed [--size tiny|small|medium|large] [--spans N] [--days D] [--persona startup,enterprise,gateway,agent-eval|all]
           [--private N] [--seed S] [--anchor RFC3339] [--shape saas|sh-licensed|sh-free]
           [--reset] [--resume] [--strict] [--no-cache] [--dry-run]
haven seed --live [--rate traces-per-minute] | haven seed --live --stop
haven seed coverage | haven seed isolation | haven seed status
```

- Additive on a non-empty stack: the same seed again is a no-op by natural keys; a different
  `--seed` adds a second population. `--reset` empties the stack's stores first (asks, or `--yes`).
- `--dry-run` prints the plan's counts, estimated rows and bytes per store and the expected duration.
- Exit codes: 0 done; 1 a check failed (coverage gap with `--strict`, isolation leak, unexpected
  dead letter); 2 refused before writing (bad flags, preflight, stack not up); 4 stalled (resumable).
- A missing optional service (nlpgo, langevals, langyagent, voicesim) skips the kinds that need it,
  names them in the report as `unavailable`, and fails only under `--strict`.
- `haven db seed <preset>` stays: `bare`, `onboarding`, `post-onboarding` keep their storage-seed
  switches; `demo` runs `haven seed --size tiny --persona startup`.

### 9.3 Live mode

`haven seed --live` runs a supervised haven lane (`seed-live`, visible in `haven status` and
`haven logs seed-live`) that streams through the door route into the orgs of the last seed: by
default 30 traces a minute with logs and metrics in proportion, a gateway call a minute, a new prompt
version and an evaluation run an hour. It obeys the guard, refuses when no seed manifest exists,
and stops with the stack or `--stop`.

## 10. Snapshot cache

- **Key**: `sha256(code version, size, spans, days, personas, private, shape, seed)`. **Code version**
  is the schema fingerprint, not the commit: Prisma migration folder names, goose migration file
  names per target, the seedgen recipe version and the coverage inventory hash (§11.1). A commit that
  changes none of these hits the cache; a schema or inventory change misses and re-seeds.
- **Capture**: after a seed passes its checks, haven captures the stack's stores with the
  `tools/upgradelab/snapshot` library (Postgres, every ClickHouse target, Redis, every bucket) into
  `${XDG_CACHE_HOME:-~/.cache}/langwatch/seed-snapshots/<key>/`, with the run manifest.
- **Restore**: only into the stack's own stores when they are empty; haven passes its own name
  check to the library and keeps the library's emptiness check (upgradelab's `upgradelab_` name
  refusal, D7, is unchanged for upgradelab). Private targets are recreated first.
- **Ageing**: a restored entry whose anchor is older than now is topped up: the generator runs the
  window `(anchor, now]` with the same seed, so the history ends today. An entry older than its
  retention margin is evicted, not restored.
- **Eviction**: at most 3 entries per (size, personas), and a total cap (default 20 GB, haven limit).
- `--no-cache` bypasses both read and write.

## 11. Coverage

### 11.1 Static inventory (no stack)

`seedgen coverage --static` builds the inventory from the tree and compares sets, never counts:

| Source | Items |
| --- | --- |
| process manifests (the readmegen parse, `tools/readmegen/process_manifest.go`) | pipelines, commands, event types, projections, subscribers, process managers |
| `schema.prisma` | models, enum values, lifecycle columns (`archivedAt`, `deletedAt`, `revokedAt`, `expiresAt`, `disabledAt`, `deactivatedAt`, `erasedAt`) |
| goose migrations and the `clickhouse-table-ownership` policy | ClickHouse tables and materialised views |
| `code-step-ids.generated.ts` | upgrade code steps (shared with upgradelab's coverage.json) |

`tools/seedgen/coverage.json` maps each item to the action kinds that produce it, or to an exemption
with a reason (`needs a clock`, `unheld`, `enterprise shape only`, `fault cohort`). The check reports
items with neither (gaps) and entries naming items that no longer exist (stale). It is a command, not
a `go test`, so it never gates a PR (ruling).

### 11.2 Run-time (after drain)

`seedgen coverage` (`haven seed coverage`) reads the stores directly, as tooling, after the drain:
event counts by `(AggregateType, EventType)` per target, row counts per ClickHouse table per target and
per Prisma model, each enum value present, each lifecycle column both null and set, process manager
instances, outbox statuses, dead letters by cohort, and the sims' evidence (mailsim messages,
outboundsim deliveries, analyticssim calls, idpsim pushes). Each covered item is `covered`, `gap`
(expected, zero rows), `unavailable` (its service is down) or `exempt`. Output: `coverage.json` and
`coverage.md` in the run directory.

Drain means: the planned actions are acked, the worker backlog is zero outside the labelled
"running" cohort (open suite runs, scheduled reports), and no count moved for 30 s; capped at 15
minutes, after which the report says `not drained` and names the oldest lane.

## 12. The nightly

`.github/workflows/seed-nightly.yml`, scheduled at 02:30 UTC and on `workflow_dispatch` (inputs: ref,
size, personas). Scheduled workflows run from the default branch, so the schedule lives on `main` and
checks out the configured ref (Q5).

1. `ubuntu-latest` (4 cores, 16 GB), timeout 120 min; never a required check.
2. Stores by `docker compose` (`dev/compose.dev.yml`, as `apidiff -no-haven`): Postgres 16,

## 13. Determinism

Deterministic means the same logical content: same plan, natural keys, payload fields, business
times and counts for the same (recipe version, seed, anchor, flags). Product-minted ids, event ids,
`createdAt`, password hashes and queue metadata differ between runs and are excluded from
comparisons. Every draw is `sha256(recipe, seed, kind, n, purpose)`; no `crypto/rand`, no
`time.Now()` outside the anchor default.

## 17. Ten-line summary

1. One Go generator, `tools/seedgen`, plans every action; haven, the nightly and upgradelab share it.
2. A `seed:apply` task plugin calls installed module APIs in the tasks process; the real worker runs every command.
3. Config, lifecycle and bulk telemetry go in-process (ruling); external-origin kinds, a 2 % slice and live mode use the doors.
4. Old releases take the door route only, for the kinds their upgrade cells need.
5. Tiers tiny, small, medium, large reach 2M spans; `--spans` sets any size from 1.
6. The guard halves or pauses on worker backlog, ClickHouse memory and parts, Redis and host pressure, and resumes from a checkpoint.
7. Only business time is backdated; retention is set first; past 31 days needs Q1's in-process input.
8. Four personas plus a hybrid mix whose private ClickHouse and bucket are provisioned locally and checked for leaks.
9. A snapshot cache keyed by the schema fingerprint restores in seconds and tops up to today.
10. Coverage runs static and after drain, nightly on medium with all personas, and never blocks a PR.

### 18.1 The dev licence guard (ruling 1)

- The verifying key already splits on the build: `isReleaseBuild` (`packages/config/src/release-build.ts`) is rewritten to `true` only in the release image's builder stage, and a release build ignores `LANGWATCH_LICENSE_PUBLIC_KEY` (`license-verifying-key.rules.ts`). Haven sets that variable to the stack's dev public key; the private key stays in haven's home and only seedgen reads it.
- Second lock: a dev-signed licence carries a `devStack` claim; licence verification refuses any licence with that claim when `isReleaseBuild` is true, whatever key signed it. So the shipped image, or haven pointed at it, refuses it even if a dev public key were embedded by mistake.
- To verify before S6: that the npx server build (`apps/server`) takes the same release rewrite; if it does not, it needs it.
