The task: prove the restructured application boots and can be used end to end —
first under plain `pnpm dev`, then under haven, then through a browser walk from
sign-up to signing back in.

**Verdict: it boots, and it cannot be used.** All three Node applications start

### Stage 1 — plain `pnpm dev`

Two things had to be true before the stack could work, and neither was:

* **ClickHouse was not running.** It is a host LaunchAgent here
  (`com.langwatch.clickhouse`, `RunAtLoad=false`), started with
  `launchctl start com.langwatch.clickhouse`. Not a repository defect — noted so
  the next person does not read the resulting worker errors as code.
* **Postgres had no schema**, because `pnpm prisma:migrate` fails every time.
  This was a branch defect and is fixed — see F1.

With those settled, `PORT=5570 pnpm dev` brought all three Node lanes up in about
25 seconds and the log carried no ERROR lines. Three absences are announced by
name at WARN, which is the intended discipline rather than a fault:

* no operator runtime (`{"capability":"operator-runtime"}`)
* no `/api/copilotkit` (`{"family":"copilotkit"}`)
* Better Auth composed over stock Prisma storage — no identity-storage routing,
  ceremonies, pending invitations, sign-in-router shadow or SSO providers

### Stage 2 — haven

`make haven up` produced a live stack. `make haven status` showed app, gateway,
nlp, idp, postgres and redis all `●`, and `haven status --json` reported the
three lanes as `ui` (listening), `api` (not listening) and `workers` (not
listening). `https://app.feat-strict-feature-layout-v0.langwatch.localhost/`
served the SPA (200); `/api/health` on the same hostname answered **502**,
because nothing was behind it.

`haven logs api` gave the cause: F9, a missing `@openrouter/sdk`. A root
`pnpm install` fixed that. After it, the lane still never bound — for F10, the
environmental reason: this worktree is shared with nine other agents whose edits
land every 3 to 30 seconds, and `tsx watch` restarts the lane on each one. A cold
boot of the api takes about two minutes (measured in stage 3, below), so the lane
was killed and restarted long before it could finish, every time. An 8½-minute
quiet window was not long enough either, because the churn resumed inside it.

Two haven-side gaps, neither branch code: `clickhouse — provisioned on :51748
but not answering` (the stack falls through to `.env`'s ClickHouse on `:8123`,
which is why it worked at all), and `observability — not answering on
http://127.0.0.1:3000`.

## Findings fixed

**F1 — `prisma-migrate` could never apply a migration.** `pnpm prisma:migrate`
failed with:

```
Error: The datasource.url property is required in your Prisma config file when using prisma migrate deploy.
```

`PrismaMigrateTask` spawned `prisma migrate deploy --config
packages/prisma-client/prisma.config.ts`, and that config deliberately carries no
datasource ("Generation needs no database"). Prisma 7 will not run `migrate
deploy` without `datasource.url` in the config file, so the command failed every
time — including on the API image's boot chain, which
`apps/api/prisma.config.ts` documents as running this task against exactly that
config. `origin/main` did not have the problem: `platform/app/prisma.config.ts`
attached `datasource.url` from `process.env.DATABASE_URL` conditionally. The
attachment was dropped when the config moved into the package.

Fixed by giving the tasks process its own config, which is where
`PrismaMigrationService`'s own doc says the URL belongs — the process supplies
it, the package stays environment-free:

* `apps/tasks/prisma.config.ts` (new) — points at the package's schema and
  migration history, attaches `DATABASE_URL` only when it is set
* `apps/tasks/src/tasks/prisma-migrate.task.ts` — spawns against that config

`pnpm prisma:migrate` then applied the full history, and `pnpm clickhouse:migrate`
reported current at version 88.

**F9 — `@openrouter/sdk` was declared but not installed.** The api lane crashed
on boot under haven with:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@openrouter/sdk' imported from
  packages/features/model-provider/server/src/tasks/model-registry-sync.task.ts
```

The dependency is declared in `@langwatch/model-provider-server`'s
`package.json`; `node_modules` was simply behind it. A root `pnpm install` fixed
it — no code change. (An earlier boot in the same session failed the same way on
`@langwatch/task` from `packages/enterprise/features/billing/server`, which
another agent's install resolved.) Worth knowing that install drift presents as a
lane that crashloops with no other symptom.

## Findings open

**F2 — the `/api/auth` REST family is mounted by nobody. This is the blocker.**

`createAuthRestApp` builds the whole family — the Better Auth catch-all,
`GET /api/auth/session`, `/api/auth/logout`, `/api/auth/validate` — at
`packages/features/auth/server/src/transport/api-rest/auth.api.ts:109`. Its only
consumer in the repository is the barrel that re-exports it,
`packages/features/auth/server/src/index.ts:86`. No process calls it.

On the process side there is nowhere for it to go: `ApiProcessRestPorts`
(`apps/api/src/app-rest/app-rest.process-features.ts:328`) has slots for
`otlpIngest`, `collector`, `bugReports`, `unsubscribe`, `langy`, `github`,
`authCliDeviceFlow`, `governanceCli` and `governanceIngest` — and no `auth`. The
comment at `apps/api/src/app-rest/app-rest.process-features.ts:699-703` states
the situation as a decision:

> Both must be registered BEFORE any `/api/auth/*` catch-all, which swallows
> every `/auth/*` sibling after it — **this process mounts none**, and that is
> what keeps them reachable.

The composition does build Better Auth (`ApiAuthComposition`,
`apps/api/src/app/api-auth.composition.ts:233`, which logs its own absences at
boot), so the instance exists and has no door. Every `/api/auth/*` path 404s:
`session`, `get-session`, `ok`, `sign-in/email` — verified by direct request
against `:6570`.

Not fixed here deliberately. It needs an `auth` slot on `ApiProcessRestPorts`,
the eight `AuthRestPorts` members supplied from `ApiAuthComposition` in
`api-production.composition.ts`, and the registration placed after the
`/api/auth/cli` families — and both of those files were being edited by other
agents throughout this session (`app-rest.packaged-families.ts`,
`api-trpc-features.composition.ts`, `api-production.composition.ts` all changed
while the walk ran). Writing into them would have clobbered live work.

**F3 — sign-up half-completes, and reports the wrong cause.** The registration
succeeds and the sign-in that follows it 404s, so the user is left with an
account they cannot use and a message that blames their password:

* `POST /api/trpc/user.register?batch=1` → 200
* `POST /api/auth/sign-in/email` → 404
* inline: "Invalid email or password." · toast: "Couldn't sign you in — We've
  been notified. Try again in a moment."

The rows are real. In `langwatch_dev`, both attempts left a `User` and a matching
`Account` with `provider=credential`, `issuer=local:credential` and a stored
password — so these accounts would work the moment F2 is fixed, and meanwhile
they are orphans. Two of them exist (`walk-1788474636431@example.test`,
`walk-1788474681666@example.test`).

Two distinct problems: registration is not atomic with the session it needs, and
a 404 on a route is presented to the customer as a credential failure. The second
is the one that costs support time — per `error-handling.md`, a missing route is
not something the caller can act on and must not be dressed up as one.

**F4 — a 404 on the session route blanks the page instead of degrading.** `/`
and `/auth/signin` both render nothing at all while `GET /api/auth/session`
404s. Intercepting that one request in the browser and answering `null` — the
signed-out answer — makes `/auth/signin` render its form correctly and
immediately. So the session fetch has no failure path: anything but a well-formed
answer leaves the shell suspended forever, with no error, no console exception
and no console message. That will outlive F2 as a defect: any future session
outage blanks the application rather than showing a sign-in screen.

**F5 — a signed-out visitor is sent to onboarding, and onboarding is blank.**
With the session stubbed to `null`, `/` redirects to `/onboarding/welcome`
rather than to `/auth/signin`, and `/onboarding/welcome` then renders an empty
body. Whether the redirect target is right is a question for whoever owns the
root route; the blank page is a defect either way.

**F6 — the worker starves its own Postgres pool from the moment it boots.**
`apps/worker` starts **19** `ProcessOutboxWorker`s, each polling on a 1000 ms
interval and each opening an interactive transaction, against a connection pool
whose committed default is `connection_limit=5` (`.env.example:144`). The result,
from the first second of every boot:

```
PrismaClientKnownRequestError: Transaction API error: Unable to start a transaction in the given time.
  code: P2028
  at PrismaProcessStore.leaseDueMessages (packages/eventing/src/server/adapters/postgres/prisma-process-store.ts:443)
  at OutboxDispatcherService.runOnce (packages/eventing/src/process-manager/outbox/outboxDispatcherService.ts:214)
  at ProcessOutboxWorker.runDrain (packages/eventing/src/process-manager/outbox/processOutboxWorker.ts:188)
```

744 occurrences in roughly thirteen minutes of idle running, the first at log
line 63. Each is logged at WARN as "drain failed; the next poll will retry", so
nothing escalates — but the outbox never drains, which means no process-manager
work happens at all on a default local stack, and the log is unreadable. This is
a direct consequence of the split: the fleet that used to share a process with
everything else now has a process of its own and the same five connections.

**F7 — scoped product routes render blank without a session.** `/demo/messages`,
`/demo/prompts`, `/demo/evaluations`, `/demo/simulations` and `/demo/agents` all
render an empty body rather than sending the visitor to sign in. Same shape as
F4 and probably the same cause; recorded separately because it is the product
surface rather than the shell. The settings routes tried
(`/demo/settings`, `/settings/members`, `/settings/authorized-apps`,
`/settings/model-providers`) render the application's own 404 screen, so their
real paths differ — not chased, because confirming them needs a session.

**F8 — `pnpm dev`'s ui lane is not isolated from a stale haven overlay.**
`apps/ui/vite.config.ts:35` loads `.env.portless` with `override: true`, so a
leftover overlay beats the launcher's own exported values. With one present from
an earlier haven run, `PORT=5570 pnpm dev` gave:

* ui bound **60694** (`LANGWATCH_APP_PORT` from the overlay), not 5570
* `LANGWATCH_PORTLESS=1` from the overlay, so the vite `/api` proxy targeted
  `127.0.0.1:60699` while the api lane bound 6570 — every API call from the SPA
  would have failed

The api and worker lanes are immune, because they load the same files through
`--env-file-if-exists`, which never overwrites a variable already in the process
environment. So two lanes of three honour the launcher and one does not.
`make haven down` does **not** remove `.env.portless`, so the overlay outlives
the stack that wrote it. The lines are identical on
`origin/main:platform/app/vite.config.ts:18-25`, so this is pre-existing rather
than a regression — but it only became consequential when the ports stopped being
one process's. Worked around for this walk by moving the file aside; not fixed,
because the fix is a decision about which of the two owns the file's lifecycle.

**F10 — watch-mode lanes cannot boot in a worktree several agents are editing.**
Nine agents share this worktree. `haven logs api` shows `tsx watch` restarting on
`apps/api/src/api.application.ts`, `api.process.ts`,
`app/api-production.composition.ts`, `app-trpc/app-trpc.features.ts`,
`packages/features/scenario/server/**`, `packages/features/suite/server/**` and
more, at intervals of 3 to 30 seconds. A cold api boot takes about two minutes
(measured: `pnpm install` invalidates the tsx transform cache, after which the
process sat at 4% CPU and 333 MB RSS for ~110 seconds before "API HTTP listener
started"). The lane is therefore killed and restarted well before it can bind,
indefinitely. Nothing to fix in the repository; it means haven and `pnpm dev`
cannot be validated in a worktree under concurrent editing, and the non-watch
`start` scripts are the way to get a stable stack there.
