## How it was read

`tools/lane-diff` (shell `cmd/lanediff`) reads both trees from git (no checkout), blanks comments,
and reads every pipeline declaration statically: `.withName(...)` on `origin/main`,
`definePipeline({ name })` on head, then each builder call in the same file (`withCommand`,
`withFoldProjection`, `withClickHouseMapProjection`, `withEventSubscriber`, `withSubscriber`,
`withProjectionSubscriber`, `withProcessManager`, the peer and global lanes, main's `registerJob`
and `projectionRegistry.registerMap*`). A name is resolved from a literal, a constant, a template,
an object's `name`, or a class's `name` field reached through a `create(...)` factory. What it
cannot resolve it lists, never guesses. The classification file
(`tools/lane-diff/classification.json`) attributes anchorless files, expands loops over command
tables and subscriber lists, and classifies each item. Every entry cites the code it rests on.

Facts the classification rests on, read on both trees:

- **One queue, same name.** Main's queue is `{event-sourcing/jobs}` (`makeQueueName`,
  `eventSourcing.ts:53-54`). Head uses the same name, wrapped by the group queue
  (`packages/group-queue/src/definition.ts:42`, used as the name at `capabilities.ts:54`).
- **Same lookup key.** Both route a job by `__pipelineName:__jobType:__jobName` (main
  `eventSourcing.ts:404-417`; head `packages/eventing/src/eventSourcing.ts:815-829`). A lane is lost
  exactly when that key is absent on head and no `.withUpcasts` drain maps it
  (`eventSourcing.ts:772-805`). The only drain on head is entitlement's former `usage` pipeline.
- **A lost job blocks rather than vanishes.** Head rejects an unroutable job for retry
  (`eventSourcing.ts:874-886`). A main-queued envelope has no `__routing`, so when its retries
  run out it falls back to `block` (`eventSourcing.ts:986`). Main's group keys are per lane
  (`tenant/jobPath/aggregate`, main `queueManager.ts:182-204`), so a blocked job stalls only its own
  lane's group. Commands with `serializeByAggregate` share one group per aggregate, but **no removed
  lane below is a command**, so none can stall a live lane. The blocked groups show in ops and are
  what F phase 2 counts.
- **Process managers.** A process manager with event types runs on a `pm:<name>` subscriber lane of
  its pipeline. One with none (wake-only) has no lane at all (main `processRuntime.ts:207`, head
  `packages/eventing/src/process-manager/processRuntime.ts:348`). Its state, scheduled wakes and
  outbox intents are rows keyed by process name, not pipeline:
  `ProcessManagerInstance @@unique([processName, projectId, processKey])`, and the outbox is keyed
  by `(processName, projectId, messageKey)` on both trees. Head's wake worker and outbox claim
  them by name (`processRuntime.ts:456,490`). So **a process manager that keeps its name on another
  pipeline keeps its state, wakes and intents**. Only event jobs queued on its old `pm:` lane at the
  cut are lost, and only for event-driven ones.

Limits: the `pm:` lanes are listed for every process manager, wake-only or not; the rules say which
are wake-only. Head-only rebuild lanes (`projectionRebuild`, `stateProjectionRebuild`) are derived
and not listed; they carry no main jobs. Langy's subscriber loop has the same key on both trees, so
its expansion (main's five names) also stands for head and hides head's added `langyWebPush`. Four
head-only declarations stay unresolved (a dynamic read-hint lane, two peer folds, `runFrames`); no
main job can be queued on a head-only lane.

   head's definitions keep the same intent names and state shape was not read.

   the pruning (`webhook-delivery.service.ts:348-350`), but main's instance rows and any pending
   `prune` intents are never claimed (`tombstone`). The other two that looked gone,
   `gatewayDebits` and `simulation_run_execution`, are on the same pipelines on head, declared
   through deps.
4. **Lanes the plan did not list, all Q02's kind (`pending` E4):** evaluation's `triggerMatch`,
   `graphTriggerActivity` and `customerIoEvaluationSync`. Simulation's `customerIoSimulationSync`,
   `scenarioRunMilestones`, `suiteRunSync` and `scenarioEvaluations` (a subscriber and a delayed
   job, now a process manager). Its `deferredComputeRunMetrics` job (now command `computeRunMetrics`).
   Trace's `datasetNormalize` job (now `dataset_normalization`). The three coding-agent fact
   dispatchers on log, metric and trace (now coding-agent peer subscribers). And **cloud's billing
   meter dispatch**, `global:reactor:billingMeterDispatch`, renamed `usageMeterCount` in
   entitlement. No plan row covers it, and a lost job there is a usage report not sent.

   `trace_processing:job:deferredOriginResolution`. Head has a reactor of that name, so the job
   type differs, and no drain maps either one.
