# Id indexes: one exact read for any lookup by id (2026-10-10, build plan 2026-10-11)

Status: build plan. Ruled (Alex, 2026-10-11): one index per table. Scenarios: `specs/clickhouse/id-index-reads.feature`. Lands in the refactor PR as
new ClickHouse migrations plus one background upgrade step per owning module. The "Implementation plan
(2026-10-11)" section at the end is authoritative where it differs: readiness is a marker row in each index
(Alex, 2026-10-11, after a day on feature flags),
the backfill walks (partition, tenant range) batches with a cursor, the table list is narrowed by an audit,
and a time is optional on every lookup by id.

## The problem

Our ClickHouse tables are partitioned by time but looked up by id. A read with a time range prunes
to its weeks and is cheap. A read **by id alone** (open a trace, follow a link from an evaluation,
a span arriving, an experiment run page, replaying an aggregate) has no time, so ClickHouse
consults every partition, cold S3 parts included. Today's workarounds:

| Workaround                                      | Where                                                            | Cost                                       |
| ----------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------ |
| Anchored ladder (3, 7, 21, 30 days back)        | trace summaries, coding sessions                                 | up to 5 queries; misses older than 30 days |
| Recent probe (35 days), then `"unbounded"` scan | spans, trace derivation, evaluation runs, simulation runs, logs  | an old id = a full cold scan               |
| No time predicate at all                        | `experiment_runs` by `RunId`, `event_log` replay without a bound | every read is a full scan                  |

## The shape

One index table per source table, filled by a materialised view on insert. It maps
`(TenantId, id)` to the time range the id's rows live in.

```
INSERT ──► <source>                  (partitioned by week or month)
              │ materialised view, fires inside the same insert
              ▼
           <source>_id_index         TenantId, <id…> → FromAt, ToAt, _retention_days
                                     AggregatingMergeTree · ORDER BY (TenantId, <id…>)
                                     no PARTITION BY · TTL from retention · never tiers cold

read by id:  1. index: (FromAt − 1 day, ToAt + 1 day)
             2. source: WHERE TenantId, id AND <partition column> BETWEEN bounds  → 1–2 partitions
```

### The table (template, shown for `trace_summaries`)

Amended 2026-10-11: `FromAt`/`ToAt` keep the source's own type (`DateTime64(3)`; `UInt64` ms for
`event_log`), not `DateTime`, and bounds are computed in TypeScript (Implementation plan §1, §4).

```sql
CREATE TABLE IF NOT EXISTS ${CLICKHOUSE_DATABASE}.trace_summaries_id_index
(
  TenantId        String,
  TraceId         String,
  FromAt          SimpleAggregateFunction(min, DateTime),
  ToAt            SimpleAggregateFunction(max, DateTime),
  _retention_days SimpleAggregateFunction(max, UInt16)
)
ENGINE = ${CLICKHOUSE_ENGINE_AGGREGATING:-AggregatingMergeTree()}
ORDER BY (TenantId, TraceId)
TTL IF(_retention_days BETWEEN 1 AND 65534,
       ToAt + toIntervalDay(_retention_days + 7),
       toDateTime('2106-01-01')) DELETE
SETTINGS index_granularity = 8192${CLICKHOUSE_STORAGE_POLICY_SETTING}  -- local_primary: the data disk
```

```sql
CREATE MATERIALIZED VIEW IF NOT EXISTS ${CLICKHOUSE_DATABASE}.trace_summaries_id_index_mv
TO ${CLICKHOUSE_DATABASE}.trace_summaries_id_index
AS SELECT
  TenantId,
  TraceId,
  min(toDateTime(OccurredAt)) AS FromAt,
  max(toDateTime(OccurredAt)) AS ToAt,
  max(if(_retention_days = 0, 65535, _retention_days)) AS _retention_days
FROM ${CLICKHOUSE_DATABASE}.trace_summaries
GROUP BY TenantId, TraceId
```

Each choice, and why:

- **Key: `ORDER BY (TenantId, <id…>)`, nothing joined.** The tuple is already unique. It doubles
  as the AggregatingMergeTree's group key, so every row for one id merges into one.
- **No partition.** Not by time (that is the problem) and not by tenant (thousands of tiny
  partitions). Merges keep the table to a handful of parts.
- **No skip indexes, plain `String` tenant.** A bloom filter or `set` index on `TenantId` or the
  id adds nothing: both lead the primary key, so the sparse index already lands on the right
  granule. `LowCardinality(TenantId)` buys little once the column is sorted first (long runs
  compress to almost nothing) and would need a cast against the source's `String`. Keep the
  source's types exactly so the view and the reads never convert.
- **A range, not one instant.** A trace's spans arrive over days, and an aggregate's events
  span weeks. `min`/`max` merge to the right answer whatever the insert order: late rows, a
  replay re-inserting the same ids, and the backfill overlapping the view all converge. No
  dedup to reason about.
- **`DateTime`, seconds (4 bytes).** Partitions are weeks or months, so seconds are more than
  enough, and the id string dominates the row anyway. Reads widen by a day each side, which
  absorbs clock skew and anchor differences (ADR-087).
- **`index_granularity` stays at the default** (8,192). A point lookup reads one granule,
  about 0.5 MB for these narrow rows. Phase 1 measures it, and drops to 2,048 if lookups are
  read-bound.

### Retention

- **Copied, with "keep forever" made sticky.** The source's `_retention_days` uses `0` for keep
  forever. Under `max`, a `0` would lose to any finite value, so the view writes `0` as `65535`
  and the TTL treats both as forever.
- **The TTL runs off `ToAt` plus 7 days of slack.** The index row outlives every source row it
  points at, and an index row that outlives its data only costs a read that finds nothing. A
  source whose own TTL anchors on another column (`evaluation_runs` expires on `UpdatedAt`) is not
  covered by the slack: its index keeps `max(UpdatedAt)` as `RetainAt` and expires on that
  (corrected 2026-10-11).
- **Retention changes reach the index through the existing mutation, raise-only.** Views never
  see mutations, and data-retention's retroactive change is one, an `ALTER TABLE … UPDATE`
  of `_retention_days` (`clickhouse.retroactive-retention.repository.ts:123`). Corrected 2026-10-11:
  the index tables must **not** join `RETENTION_TABLE_CATEGORY_MAP` itself, since every table in it
  must be in `TABLE_TTL_CONFIG` and carry `_size_bytes` (`retention-ttl.unit.test.ts:135`,
  `PRODUCTION_STORAGE_METER_TABLES`). They get their own map, `RETENTION_ID_INDEX_TABLES` (index to
  source). An index row aggregates rows of different retention (an aggregate's events are kept
  forever or not per event type, `event-store.clickhouse.ts:141`, and the index has no
  `EventType`), so a rewrite of an index only ever **raises**: it adds
  `AND _retention_days < X` to the tenant's `UPDATE`, with `0` written as `65535`. A shortened retention leaves
  the index row longer-lived than its data, which only costs a read that finds nothing.
  `event_log`'s index joins `EVENT_TABLES` and `EventLogRetention.tables`.
- **Sources with a fixed TTL** (`gateway_spend`: 13 months) get the same fixed TTL on `ToAt`.
  Sources with no TTL get none.
- **Stays out of `TABLE_TTL_CONFIG`.** The reconciler rewrites the whole TTL clause of the tables
  it lists and adds `TO VOLUME 'cold'`. The index must never tier to S3, so its TTL lives in its
  migration only (the `usage_trace_meter` precedent, 00106).

### Replays, deletes and everything else that writes

| Path                                                | Does the view see it? | What we do                                                                  |
| --------------------------------------------------- | --------------------- | --------------------------------------------------------------------------- |
| Normal insert, async insert                         | yes, on flush         | nothing                                                                     |
| Projection replay (`defineProjectionReplayStep`)    | yes: plain inserts    | nothing: same ids re-merge; a corrected time only widens the range          |
| Retention change (`ALTER UPDATE _retention_days`)   | no                    | raise-only rewrite via `RETENTION_ID_INDEX_TABLES` / `EVENT_TABLES` (above) |
| TTL expiry                                          | no                    | index has its own TTL, never earlier than the source                        |
| `EXCHANGE TABLES` rebuilds (00058, 00064–66, 00069) | no                    | only rollup tables do this, and rollups get no index                        |
| Governance erasure (`ALTER DELETE`)                 | no                    | only cost rollup tables; their indexes (if any) join the erasure            |
| Tenant purge of ClickHouse rows                     | no                    | none exists (audit 2026-10-11); a future purge lists the indexes too        |

A range that's too wide only costs a slightly larger read. A range that's too narrow loses rows.
Every path above can only widen a range or leave it unchanged. The one exception is a
half-finished backfill (see "Readers").

### `event_log`: an aggregate index; event ids use the KSUID

- **`event_log_id_index`**: `(TenantId, AggregateType, AggregateId) → FromAt, ToAt`. Bounds aggregate
  replay and `getEventRecords`. The view skips `EventOccurredAt = 0` rows (`WHERE
EventOccurredAt > 0`); otherwise `FromAt` would become 1970 and the bound would cover all of
  history. Reads keep today's `OR EventOccurredAt = 0` arm for those rows.
- **Lookup by event id: no index, the KSUID is a hint** (Alex, 2026-10-11). Event ids are pure
  KSUIDs (`packages/eventing/src/domain/types.ts:46`). The read decodes the id's time in
  TypeScript and first tries `id time ± 7 days`, which covers 2–3 weekly partitions. On a miss it
  falls back to today's path. The fallback is needed because `EventOccurredAt` is producer
  business time, unbounded into the past (`record-span.commands.ts:245`). An event-id index can
  be added later if the fallback rate shows up on the metric.

**The same hint for other ids.** Any id that's a server-minted KSUID gives a free first window
before the fallback. Phase 0 notes which tables' ids qualify.

## Which tables

Native tables only. The `*_pg` tables are Postgres-engine mirrors, and stay out. The audit of
2026-10-11 narrowed the first list: an index is built only where a read by id without a required
time exists today, and only on a table something still writes. The final list, with owners, keys
and the read sites that switch, is "Implementation plan" §1. Corrections to the first list:
`stored_log_records`, `stored_metric_records`, `langy_messages` and `automation_audit` have no
writer; `evaluation_analytics` is analytics's, `trace_analytics` trace's; `suite_runs` is read by
`BatchRunId` alone, so its key is `BatchRunId`; `log_records`, `metric_*`, `instant_eval_judgments`,
`session_metric_series`, `simulation_run_metrics`, `langy_analytics_events` and the governance tables
have no unbounded read by id.

**Left out, with reasons** (each is cheap to add later):

- **Rollups** (`trace_analytics_rollup`, `evaluation_analytics_rollup`, `metric_time_rollups`,
  `gateway_budget_scope_totals`, `governance_cost_rollup_1d`, `simulation_run_metrics_rollup`,
  `governance_kpis`): keyed by time buckets, with no entity id. They're always read by range,
  and some are rebuilt by `EXCHANGE TABLES`, which a view would miss.
- **Already unpartitioned** (`instant_eval_runs`, `governance_cost_rollup_restatement_index`,
  `lwql_api_key_tenant_map`, `goose_db_version`): a lookup is already one read.
- **Billing meters** (`billable_events`, `usage_trace_meter`, `metric_usage_estimates`,
  `log_usage_estimates`): keyed by organisation and month, and read that way.

## Migrations

- **One goose file per owning module** (the "one owner per file" rule). Each file holds that
  owner's index tables and views, one statement per `StatementBegin` block, all with `IF NOT
EXISTS`. That's 9 files, `00110` to `00118`, claimed as one block (`00107` to `00109` are taken
  on other branches, 2026-10-11).
- **Order inside a file: table, then view.** Never `POPULATE`: it rewrites history at deploy and
  races inserts. The view catches every insert from the moment it exists, and the backfill covers
  everything before that. The upgrade runs background steps only after the image's goose files,
  so the two sets meet with no gap. Overlap is harmless under `min`/`max`.
- **Old releases are covered.** The view is server-side, so a previous release still running
  during a rolling deploy fires it on every insert. The change is expand-only, with no contract
  step and no `needsOldWritersGone`.
- **Down blocks stay commented**, per the house rule.
- **Every target.** Goose already applies to the shared target and to each private-route
  organisation's ClickHouse. The backfill must visit the same targets, the way data-retention's
  step does (`clickhouse.privateRoutes()`).

## Backfill: one background step per owner

```
deploy (pnpm task upgrade)
 1. goose 00107…: CREATE TABLE <source>_id_index, then CREATE MATERIALIZED VIEW … TO it
    └─ from this instant every insert, replay or old-release write fills the index
 2. serve: readers find no marker row (or write it over an empty source), so they keep today's lookups
 3. worker: background step <owner>:fill-id-indexes, under the upgrade lease
    for each ClickHouse target (shared, then each private-route organisation)
      for each source table this owner indexes
        for each partition, newest first (system.parts, active parts)
          for each batch: the whole partition, or a TenantId range of about R source rows
            INSERT INTO index SELECT TenantId, id, min(t), max(t), max(retention)
              FROM source WHERE _partition_id = p AND TenantId in range GROUP BY TenantId, id
            checkpoint.save({ cursor: target, table, partition, afterTenantId })
      data-retention raises the target's index retention to every tenant's current value
      write each index's marker row on this target (TenantId '', keys '__fill_complete__')
 4. (folded into 3: the re-apply runs per target, before that target's marker)
 5. readers find the marker (in memory, re-checked every 60 s until found) and switch to the index
```

### Why the fill is a step and not SQL inside goose

The fill is plain SQL we write ourselves, but ClickHouse has no stored procedures. The only
server-side async work a goose file may start is a **mutation** (`MATERIALIZE …`, `ALTER …
UPDATE`), which a background step then watches (the `-- background step:` note, 00103). An
`INSERT … SELECT` isn't a mutation: it runs as long as its client holds the query. So:

| Option                                                     | Why not                                                                              |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `POPULATE` on the view                                     | refused by the guard: blocks the upgrade, and drops inserts during the fill          |
| One `INSERT … SELECT … GROUP BY` over all history in goose | blocks the upgrade for hours, can't resume, holds all of history in one GROUP BY     |
| A projection (`ADD PROJECTION` + `MATERIALIZE`)            | is a mutation, but lives inside each partition's parts, so it can't prune partitions |
| A refreshable materialised view used once                  | runs on a schedule, not once; no checkpoint, no ledger, no progress                  |
| **Per-partition `INSERT … SELECT`, driven by a step**      | resumable, bounded memory, visible in the ledger, doesn't block serving              |

So goose stays DDL only (table, then view), and the step is a thin driver around one SQL
template per index. Each index's SQL is written once, in a declaration beside the step:

```ts
// modules/trace/process/src/migrations/id-indexes.trace.migration.ts
export const traceIdIndexes = [
  { source: "trace_summaries", index: "trace_summaries_id_index", key: ["TraceId"], time: "OccurredAt" },
  { source: "stored_spans", index: "stored_spans_id_index", key: ["TraceId"], time: "StartTime" },
  // …
] as const;

.withMigrations(({ app }) => [
  defineMigrationStep({
    id: "trace:fill-id-indexes",
    kind: "data",
    mode: "background",
    description: "Fills the trace tables' id indexes from rows written before their views existed.",
    run: ({ checkpoint, dryRun, signal }) => app.fillIdIndexes({ checkpoint, dryRun, signal }),
  }),
]);
```

The partition walk is one shared function, `fillIdIndexes({ client, indexes, checkpoint, dryRun,
signal })`, in `packages/clickhouse-client`. It knows nothing of the upgrade system, because
`@langwatch/upgrade` already depends on `process-stores` and so on `clickhouse-client`, and
importing the step definer there would make a cycle. Each owner's repository calls it with its
declaration, and the owner's module wraps that in its own `defineMigrationStep`. Per index it
renders `INSERT INTO {index} SELECT TenantId, {key}, min(toDateTime({time})),
max(toDateTime({time})), max(if(_retention_days = 0, 65535, _retention_days)) FROM {source} WHERE
_partition_id = {p} GROUP BY TenantId, {key}`. A unit test reads each goose file and asserts that
its index columns and view `SELECT` match the declaration, so the two can't drift.

### Clusters: nothing special

- **DDL.** With `CLICKHOUSE_CLUSTER` set, the migration runner creates the database as a
  Replicated database and every engine as Replicated (`${CLICKHOUSE_ENGINE_AGGREGATING}` and the
  rest), which is SharedMergeTree on ClickHouse Cloud. The `CREATE TABLE` and `CREATE MATERIALIZED
VIEW` statements therefore reach every replica with no `ON CLUSTER`. Unset, it's one node.
  Same files either way.
- **Views.** Every replica has the view, and it fires on whichever replica takes the insert. The
  index table is replicated, so its rows reach every node. There are no `Distributed` (sharded)
  tables in the schema, so there's no shard fan-out to think about.
- **Fill.** Each `INSERT … SELECT` runs on the one replica the client lands on. The SELECT reads
  that replica's full copy, and the written parts replicate. The upgrade lease means one worker
  drives the fill, so no two replicas fill the same partition at once. If they did, it would only
  cost work: `min`/`max` merge.
- **Replicated insert dedup.** A retried replicated insert is deduplicated, and by default the view
  is skipped with it. Every writer sets `deduplicate_blocks_in_dependent_materialized_views = 1`
  (Readers).
- **Private routes.** An organisation with its own ClickHouse is its own target. Goose already
  applies to each target, and the step loops them (`clickhouse.privateRoutes()`, as
  data-retention's step does). Each target gets its own marker rows.

### In the upgrade system

```
release manifest (this image)
  schema     clickhouse:00110 … clickhouse:00118   (blocking, before the worker's gate opens)
  blocking   –                                     (nothing here: serving is never held)
  background trace:fill-id-indexes, experiment:fill-id-indexes, …   (worker, after schema)

ledger row per step:  pending → running → done | failed
  report  { cursor, targetsDone[], done, total, batches, retries }   (Implementation plan §3)
          shown on the Ops Upgrades console as progress; retryStep re-runs a failed one
```

- **Any jump works.** No release is a required stop: an install three releases behind still
  applies 00110–00118, then runs the fill steps.
- **A step runs once per install.** Once `done`, the ledger never re-runs it. An index added later
  gets a new step id (`trace:fill-id-indexes-2`). A fresh install marks `data` steps `not-needed`
  (`plan-upgrade.ts:28`); its readers find every source empty at boot and write the marker themselves.
- **Planning and recovery.** `pnpm task upgrade plan` lists the steps, and a dry run reports
  partitions and estimated rows. The generated code-step ids file is regenerated after the steps
  land, coordinated with the owner of `packages/upgrade`.
- **Rollback.** Rolling the image back leaves the views and indexes in place. Older code never
  reads them, and the views keep them filled, so rolling forward again just finds them ready.

- **No gap, double-counting is harmless.** The upgrade runs background steps only after the
  image's goose files, so every row is either older than the view (the backfill reads it) or
  newer (the view writes it). A row in both just merges under `min`/`max`.
- **Newest first** fills the ranges people actually open first. A partition is one weekly or
  monthly bucket. Its `GROUP BY` is sliced by tenant hash so a big week of `stored_spans` fits in
  memory, and phase 1 picks N from the measured partition sizes. Each insert is a normal
  background-priority query with `max_threads` capped, so serving reads keep the cluster.
- **The checkpoint** is a cursor, `{ target, table, partition, afterTenantId, slice }`, saved after
  each batch through the ledger (`checkpoint.save`). That throws if the lease is lost or the
  deadline (15 minutes per sweep) passed, so two workers never fill at once. A crash, redeploy or
  deadline resumes from the cursor, and a batch caught half done is simply redone.
- **Level-triggered and idempotent.** It's safe on any install, at any version, any number of
  times. `dryRun` reports partitions and estimated rows without inserting. `signal` is checked
  between partitions and slices.
- **The "complete" signal is a marker row** (Alex, 2026-10-11, superseding a day of feature flags):
  one row per index per ClickHouse target, written by the step once every table of that owner is
  filled there, or by a reader over an empty source (Implementation plan §2).
- **The retention race.** A retention change mid-backfill updates the index rows that exist when
  the mutation starts. Rows the backfill inserts afterwards can carry the old value. If that value
  is shorter, an index row could expire while its data lives. So once a target is filled, and
  before its marker is written, the step asks data-retention (through its `*Api`) to raise that
  target's index rows to each tenant's current retention (`… AND _retention_days < X`). That's a
  no-op wherever the value is already right.
- **A shared partition walk.** No existing step walks partitions, so the target, partition and
  batch loop becomes one helper in `packages/clickhouse-client`. Each owner supplies only its
  table list and `GROUP BY` columns.
- **Generated step ids.** After adding the steps, regenerate the code-step ids
  (`packages/upgrade/scripts/image-code-steps.ts`). That's a generated file in a package another
  agent owns: coordinate, don't edit it by hand.

## Readers

- **One primitive: `indexedRead`** in `packages/clickhouse-client`, beside `windowedRead`. Given
  the index table, its key and the source's partition column, it returns a bounded fragment or
  a miss.
- **Two new outcomes** on `clickhouse_windowed_read_total`: `index_hit` and `index_miss`.
- **Once a table's backfill is done, a miss means "not found"** after one probe of the recent
  35 days (hot partitions only, never unbounded), as the spec says; the probe guards a view that
  failed silently. A materialised
  view is an insert trigger, not a refresh: it runs on the same block, inside the same insert
  (and the same async-insert flush), so a source row can't become readable before its index
  row. A failed view fails the insert loudly. Insert retries must not drop the view's block:
  every writer sets `deduplicate_blocks_in_dependent_materialized_views = 1`, which phase 1 checks.
- **Readiness lives in process memory, so it costs no I/O per lookup.** `IdIndexReadiness` keeps
  one boolean per target, answers synchronously, and re-checks a target not yet ready in the
  background at most every 60 s, never again once ready (Implementation plan §2).
- **Until a table's backfill is done, its readers keep today's fallback.** A half-filled index
  can give a too-narrow range for an id whose rows straddle a partition the step hasn't
  reached. Once the backfill is done, the index is trusted and that table's ladder and
  `"unbounded"` fallbacks are deleted.

## Risks

- **A broken view breaks ingestion.** A view runs inside the source's insert, so an error there
  fails the insert. Keep every view a plain projection plus `GROUP BY`, with no lookups, joins or
  casts that can throw.
- **Insert cost on the hottest tables** (`event_log`, `stored_spans`). Phase 1 measures it.
- **Storage.** Roughly 40–70 bytes compressed per id, on the hot volume. Per-table indexes repeat
  a trace id up to six times (summaries, spans, logs, metrics, analytics, coding sessions). That
  buys exact ranges per table and independent backfills. One shared trace index fed by several
  views would save that space.

### 2. Readiness: a marker row, and how readers get it

Ruled by Alex, 2026-10-11, replacing the morning's feature flags: every id index says it is ready
with a **marker row**, so readiness lives beside the data it describes and needs no other module.

- **The marker.** One row in each `<source>_id_index` on each ClickHouse target: `TenantId = ''` (no
  tenant has an empty id), every key column `'__fill_complete__'`, the time columns at their zero
  value, `_retention_days = 65535` (kept forever, so the TTL never takes it). Every index read binds
  a real tenant, so no lookup ever matches it.
- **Ready, per owner and target.** Ready when every index of the owner holds its marker there.
  Otherwise an index whose source holds no row (`SELECT 1 FROM <source> LIMIT 1`, under the
  declaration's filter) gets its marker written by the reader: a fresh install, with nothing to fill
  and a view, created by goose before serve, that already catches every row. Otherwise not ready,
  re-checked in the background at most every 60 s until ready, then never again.
- **Checked at boot.** Each owner's readiness checks `shared` and every private-route organisation
  when the process composes it (`watch`), before a fresh install's first row can land; a target
  first asked later is checked on that ask. A lookup reads only an in-memory boolean.
- **Who writes it.** `fillIdIndexes` writes a target's markers after its batches finish and after
  `beforeMarker` (the retention raise) succeeds. Writing it twice merges into one row.
- **One implementation:** `IdIndexReadiness` in `packages/clickhouse-client/src/idIndexReadiness.ts`
  satisfies `IdIndexFlags` (`{ isOn({ target }): boolean }`). The marker statements skip the tenant
  guard with `SKIP_TENANT_CHECK` and a stated reason; the empty-source probe also skips the
  cold-scan check, since it stops at the first row.
- **Modules.** Each owner's ClickHouse fill repository builds one `IdIndexReadiness` over its own
  declarations and exposes it as `readiness`; the app hands it to services as `idIndex`, the
  optional parameter of each switched repository read (absent reads as not ready). Analytics builds
  it inside its evaluation repository. Memory twins answer never ready.
- **Eventing.** `eventLogIdIndexReadiness({ clickhouse })` (eventing server) answers
  `EventLogIndexReadiness` for every aggregate type at once from `event_log_id_index`'s marker;
  `create-members.ts` hands it to `buildEventing`, and ops' live registry to
  `LiveReplayRuntimeRepository`. No pipeline declares anything.
- **Target:** inside the repository, `ClickHouseQueryClient.targetOf({ tenantId })` for the
  project's own tenant (never a shared grant's project; a tenant set routes to one organisation,
  `connection.ts:100`): `"shared"` with no I/O when no private route exists, else the tenant
  router's cached answer (`tenancy.ts:191`), which the routed query pays anyway.

### 3. The backfill

**Why this shape.** Alex's shape (big batches, a cursor, back off on failure, finish fast, then set
the marker) stays, but a batch is a (partition, tenant range) unit sized in source rows, not 1,000 ids.
A keyset cursor over ids (`WHERE (TenantId, id) > cursor ORDER BY … LIMIT 1000`) opens every part of
every partition for every batch, since each part is sorted on its own: thousands of S3 reads per
thousand ids on a cold table, and millions of batches. Walking partition by partition reads each
partition once, newest first, with the server doing the work in one `INSERT … SELECT` per batch and
no rows in Node. Where the key is a sort-key prefix (§1), `optimize_aggregation_in_order` streams the
`GROUP BY` in bounded memory; the five tables without it (`trace_analytics`, `evaluation_analytics`,
`coding_agent_sessions`, `suite_runs`, `gateway_budget_ledger_events`) spill through
`max_bytes_before_external_group_by`. A `TenantId` range uses the primary key, unlike a
`cityHash64 % N` slice that rereads the partition N times. The 15-minute deadline per sweep
(`packages/upgrade/src/background/background-steps.service.ts:66`) makes a per-batch cursor necessary.

**Helper** `fillIdIndexes({ statements, targets, indexes, checkpoint, signal, batchRows,
beforeMarker })` in `packages/clickhouse-client/src/idIndexFill.ts`, called from the fill step the
framework builds for each module's `.withIdIndexes(...)` (`packages/process/src/migration/id-index-fill-step.ts`). `statements` is a port (`query`/`command` with `organizationId`,
`SKIP_TENANT_CHECK`, `SKIP_COLD_SCAN_CHECK`), so the helper knows nothing of `@langwatch/upgrade`.

**Targets.** `shared`, then private routes, de-duplicated by URL as goose does
(`apps/tasks/src/upgrade.ts:146`): one fill per URL, whose markers answer for every organisation on that URL.
A target that fails is recorded and skipped; the others carry on; the step throws at the end if any
failed, and the retry resumes only the unfinished targets. Within a target: the owner's tables in
declaration order, partitions in descending `partition_id`, from

```sql
SELECT partition_id, sum(rows) AS rows
FROM system.parts
WHERE database = currentDatabase() AND table = {source:String} AND active
GROUP BY partition_id ORDER BY partition_id DESC
```

A partition of at most `R` rows (default 5 million) is one batch. A larger one reads its tenant
counts, which touches only the sorted `TenantId` column,

```sql
SELECT TenantId, count() AS rows FROM {source} WHERE _partition_id = {partition:String}
GROUP BY TenantId ORDER BY TenantId
```

and packs consecutive tenants into ranges of about `R` rows. A tenant above `R` is split one of two
ways, chosen at run time from the source's `sorting_key` in `system.tables`. Where the sort key starts
with `TenantId` and the index key, the split is by key range: each batch reads the next `R` keys,
found with `ORDER BY {key} LIMIT 1 OFFSET R-1`, so every source row is read once. On any other
table the tenant gets `ceil(rows / R)` hash slices of its last key column. Each batch:

```sql
INSERT INTO {index} (TenantId, {key}, FromAt, ToAt, [RetainAt,] _retention_days)
SELECT TenantId, {key}, min({time}) AS FromAt, max({time}) AS ToAt,
  [max({retentionAnchor}) AS RetainAt,] max({retention}) AS _retention_days
FROM {source}
WHERE _partition_id = {partition:String}
  AND TenantId > {afterTenantId:String} AND TenantId <= {throughTenantId:String}
  [AND ({key}) > {afterKey} AND ({key}) <= {throughKey}]          -- key-range split
  [AND cityHash64({lastKey}) % {slices:UInt32} = {slice:UInt32}]   -- hash split
  [AND {filter}]
GROUP BY TenantId, {key}
SETTINGS optimize_aggregation_in_order = 1, max_threads = 4, max_execution_time = 600,
  max_bytes_before_external_group_by = 2000000000
```

`{retention}` is `if(_retention_days = 0, 65535, _retention_days)` or `toUInt16(65535)`. A whole
partition passes `afterTenantId = ''` and no upper bound. Partitions created after the snapshot were
written after the view existed, so the descending cursor may skip them.

**Checkpoint** (the step's `report`, replaced whole on each `save`, a few hundred bytes):

```ts
{
  targetsDone: string[];                  // URL keys whose markers are written
  targetsFailed: { target: string; error: string }[];
  cursor: { target: string; table: string; partition: string; afterTenantId: string;
            throughTenantId: string; slice: number; slices: number;
            throughKey?: string[] } | null;  // last committed batch; throughKey mid key-range split
  done: number; total: number;            // partitions, shown as ledger progress
  batches: number; retries: number;
}
```

**Failure.** A failed batch retries in place, backing off from 1 s doubling to 30 s, five times; a
memory-limit error (code 241) halves `R` for that partition first. Then that target is marked failed
and the walk moves on; the step throws at the end, and the ledger's ladder (5 attempts, 1 to 15
minutes, `background-steps.service.ts:59`) resumes from the cursor. An aborted `signal` returns at
the next batch boundary.

**Per target, when every table of the owner is filled:** `beforeMarker` asks data-retention to raise
that target's index rows to each tenant's current retention (open question 4), then the fill writes
each index's marker row on the target, then the target joins `targetsDone`. Owners call it through
`fillOwnerIdIndexes`, which supplies the targets and the raise over the copied-retention indexes.

**Steps,** all `kind: "data"`, `mode: "background"`, `needsOldWritersGone: false` (old releases fire
the server-side view too): `trace:fill-id-indexes`, `evaluation:fill-id-indexes`,
`analytics:fill-id-indexes`, `experiment:fill-id-indexes`, `scenario:fill-id-indexes`,
`suite:fill-id-indexes`, `coding-agent:fill-id-indexes`, `gateway:fill-id-indexes`, and
`ops:fill-event-log-id-index` (the fill is eventing's surface,
`packages/eventing/src/server/tables/event-log-id-index.ts`; ops hosts operator work over the event
tables, ARCHITECTURE.md §7). They are chained with `after` (`packages/upgrade/src/step/migration-step.ts:99`)
in that order, so one fill runs at a time; `after` takes `CodeStepId`, so the chain is added once the
code-step ids are regenerated (coordinator, §5).

**Private routes added later.** A private route configured after a step is `done` is never filled:
a new server with empty sources is marked ready by its first check; one holding rows has no marker,
so its reads keep today's path, which is correct but slow. Open question 7 covers it.

**Insert setting, once.** `vendorClickHouseSettings`
(`packages/process-stores/src/clickhouse-member.ts:53`) adds
`deduplicate_blocks_in_dependent_materialized_views: 1` to the client-level settings every vendor
client is built with, so it covers both insert paths: the routed member (`routingDriver.ts:44`) and
the vendor-shaped writers (`evaluation-run-write.repository.ts:160` → `vendorClient.ts:162`).
Per-request settings merge over it. The admin client (`store-targets.ts:33`) writes only the LWQL key
map, which has no index.

### 4. Reads

`indexedRead({ client, idIndex, tenantId, owner, index, key, ids, hintMs?, fallback, onMiss, isEmpty, run })`
in `packages/clickhouse-client/src/indexedRead.ts`, built on `queryWindowed`:

1. **A time was given:** today's hinted read, unchanged. If it is empty and the index is ready,
   step 3 replaces the widening; otherwise today's fallback.
2. **No time, index not ready** on the project's target: today's fallback, unchanged.
3. **No time, index ready:** one point read of the index,

   ```sql
   SELECT count() AS n, toUnixTimestamp64Milli(min(FromAt)) AS fromMs, toUnixTimestamp64Milli(max(ToAt)) AS toMs
   FROM {index} WHERE <tenant predicate, open question 2> AND {key} IN ({ids:Array(String)})
   ```

   `n = 0` is a miss (`min`/`max` over no rows answer 1970, not `NULL`). A hit computes the bound
   in TypeScript, `max(0, fromMs − 1 day)` to `min(Number.MAX_SAFE_INTEGER, toMs + 1 day)`, runs
   `run` with that fragment and counts `index_hit`. A miss counts `index_miss` and runs `onMiss`:
   one probe of the recent 35 days for every table except `event_log`, which takes today's
   unbounded path (a fold reads an aggregate's whole history, `event-repository.clickhouse.ts:233`,
   and rows with no occurred time are not in the index).

`WindowFragment.sqlFor(column)` goes into the inner dedup subquery as well as the outer scope:
`trace_analytics :300`, `evaluation_analytics :171`, `coding_agent_sessions` and
`coding_agent_trace_sessions` leave the inner one unbounded today. The ladders and `"unbounded"` arms
stay for the not-ready path, deleted in a later change once every install reports its indexes ready.

**Existence.** The gateway ledger's idempotency probes read the index alone: the ledger has no TTL,
so "seen" is exact. Trace existence (`trace-existence.repository.ts:31`, used by annotations) reads
the index for the bound, then confirms on the source, because an index row outlives its data by the
7-day slack plus TTL merge lag and would report an expired trace as present for a week or more.

**`event_log`.** Once ready: aggregate reads take `EventOccurredAt >= fromMs` (and `<= toMs` where the
read has no upper bound of its own), keeping the `OR EventOccurredAt = 0` arm; replay's
`getAggregateOccurredAtBounds` reads the index; the 45-day rehydration rule applies to every
aggregate type. **By event id:** `eventReadWindow` (`packages/eventing/src/stores/eventReadSeat.ts:87`)
widens from ±2 to ±7 days of the KSUID's time; on a miss the read takes today's path and counts the
fallback; a non-KSUID id takes today's path. `AbstractEventStore.getEvent`
(`abstractEventStore.ts:107`) gets the same window. Open question 6.

**No time from callers.** Every by-id time hint on the wire is already optional (`occurredAtMs` on
the trace tRPC inputs, `traces.trpc.ts:174`, `:442`; `trace.queries.ts:12`, `:35`, `:61`, `:90`;
`codingAgentTrpcTraceScopeSchema`; `startedAtMs` on the coding-agent lookup; REST and MCP send none),
so no contract changes. The browser keeps sending a time when it has one; what changes is that the
drawer stops waiting for one (`hintReady`, `modules/trace/browser/src/…/use-trace-query-args.ts:40`)
and the header stops back-filling `drawer.t` (`model/traces/trace-occurred-at-backfill.ts`). This
lands only once open question 3 is settled, since an install whose indexes stay unready would lose the
hint's speed. Contract comments saying "omitting it walks every partition"
(`features/list/trace-explorer.contract.ts:24`) are corrected.

### 6. Questions, ruled

Alex, 2026-10-11: all seven approved as recommended. Later the same day the flag gave way to a
marker row per index and target (§2), so questions 1 and 3 below are superseded.

1. **How readers get the flag.** Each owner builds a `FeatureFlagLatch` from its own `FeatureFlagApi`
   and passes `idIndex` into its repository reads; eventing takes it per pipeline through
   `.withEventLogIndex(flags)`, the way `withRetention` takes data-retention's resolver. Adds a small
   class to the feature-flag contract and one builder method to eventing. _Recommend yes._
2. **The fenced index read.** Trace and evaluation reads go through `AuthorizedClickHouse`, which
   refuses a hand-written `TenantId` predicate and any marker outside `OccurredAt`, `StartTime`,
   `ScheduledAt`, `Timestamp` (`packages/clickhouse-client/src/authorized-reads.ts:108`,
   `packages/clickhouse-markers/src/index.ts:6`). Options: (a) a fence-owned
   `reader.indexBounds({ index, key, ids })` that binds the proof's tenant set itself (as
   `{{tenantSet}}` does) and returns only `{ n, fromMs, toMs }`, never rows, while the source read
   keeps its windowed `{{tenantScope:<col>}}` marker, so a shared grant's window still filters what
   is returned; (b) add `ToAt` as a marker column, which applies a grant's window to one end of an
   interval and refuses ids that straddle it; (c) a named `SKIP_TENANT_CHECK` exemption, a bypass.
   _Recommend (a)._
3. **Fresh installs never run `data` steps** (`packages/upgrade/src/plan/plan-upgrade.ts:28`), so
   their flags stay off and reads stay on today's path for good. _Recommend_ asking the owner of
   `packages/upgrade` for a per-step `runsOnFreshInstall: true`; the fill over empty tables takes
   seconds. Slice 8 waits on this.
4. **A new `DataRetentionApi` operation:** raise one target's index rows to each tenant's current
   retention, called per target before its flag is set, closing the race where a retention
   lengthened mid-fill leaves short-lived index rows. _Recommend approve._
5. **The narrowed list,** 16 tables, not 30 (no write-only tables, no tables without an unbounded
   read by id, no legacy `stored_objects`). _Recommend agree._
6. **Event id with the flag on.** Every `getEventRecord` names its aggregate, so the aggregate index
   bounds it exactly; the KSUID ±7 days would serve only while the flag is off. _Recommend_ the
   aggregate index first.
7. **Private routes added after the fill.** Their flags stay off, so they are correct but slow.
   _Recommend_ accepting that for now, and adding an ops action, "fill id indexes on this target",
   when the first route is added after rollout.

Built on `feat/id-index`, slices 1 to 7, each with its integration test passing against a native
ClickHouse. Differences from the plan above:

- **15 index tables, not 16.** `experiment_run_items` has no id-only read (every read carries the
  run's time), so it has no index.
- **Declarations live in each owner's ClickHouse fill repository**, not under `migrations/`. The
  layout lint accepts only import migrations there, and `rules/` is for decisions.
- **Every goose statement ends with `;`.** The table-ownership policy reads a view's body up to `;`.
- **The fills are chained** with `after`: trace, evaluation, analytics, experiment, scenario,
