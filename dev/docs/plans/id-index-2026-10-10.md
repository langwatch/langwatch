# Id indexes: one exact read for any lookup by id (2026-10-10)

Status: spec, ready to build. Supersedes the parked trace-index note. Scenarios:
`specs/clickhouse/id-index-reads.feature`. Lands in the refactor PR as new ClickHouse migrations.

## The problem

Our big ClickHouse tables are ordered by `(TenantId, <id>)` but partitioned by time
(`toYearWeek(OccurredAt)` and similar). A read with a time range prunes to its weeks and is cheap. A
read **by id alone** (open a trace, a link from an evaluation or alert, a span arriving, an experiment
run page, replaying an aggregate's events) has no time, so ClickHouse consults every partition's
index, cold S3 parts included. Today we work around it three ways, all imperfect:

| Workaround                                      | Where                                                                  | Cost                                       |
| ----------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------ |
| Anchored ladder (3, 7, 21, 30 days back)        | trace summaries                                                        | up to 5 queries; misses older than 30 days |
| Recent probe (35 days), then `"unbounded"` scan | spans, trace derivation, evaluation runs, simulation runs, log records | an old id = a full cold scan               |
| Nothing: no time predicate at all               | `experiment_runs` by `RunId`, `event_log` aggregate replay             | every read is a full scan                  |

## The design

A small, unpartitioned **id index** per looked-up table: id → the time range its rows live in. A
materialised view fills it on every insert into the source. A read asks the index first, then
reads the source with an exact time bound, so it touches one or two partitions.

```
source table ──(materialised view, on insert)──► <name>_index
(partitioned by week)                            TenantId, <id> → FromAt, ToAt, RetentionDays
                                                 AggregatingMergeTree, ORDER BY (TenantId, <id>)
                                                 NO PARTITION BY, TTL by retention
```

```sql
CREATE TABLE IF NOT EXISTS ${CLICKHOUSE_DATABASE}.trace_index
(
  TenantId        String,
  TraceId         String,
  FromAt          SimpleAggregateFunction(min, DateTime),
  ToAt            SimpleAggregateFunction(max, DateTime),
  _retention_days SimpleAggregateFunction(max, UInt32)
)
ENGINE = ${CLICKHOUSE_ENGINE_AGGREGATING:-AggregatingMergeTree()}
ORDER BY (TenantId, TraceId)
TTL IF(_retention_days > 0, ToAt + toIntervalDay(_retention_days), toDateTime('2106-01-01')) DELETE
```

Why each choice:

- **No partition at all.** Not by time (that is the problem) and not by tenant (thousands of tiny
  partitions). Merges keep it to a handful of parts.
- **`ORDER BY (TenantId, <id>)`.** The pair is already unique, so there is no `tenant:id` column. The
  sparse primary index (one mark per 8,192 rows) sits in memory: a lookup is a binary search in RAM
  and one granule read. A billion ids is about 122k marks.
- **A range (`FromAt`, `ToAt`), not one instant.** One trace's spans and logs spread over time, and
  an aggregate's events span weeks. `min`/`max` in an AggregatingMergeTree get this for free:
  re-inserts, late spans and a backfill overlapping the view all merge to the right answer. The
  table is idempotent by construction, so there is no ReplacingMergeTree dedup to reason about.
- **`DateTime` (4 bytes, seconds).** Partitions are weeks, so second precision is more than enough
  to prune and `Date` would save nothing worth having next to the id string. Readers widen by one
  day each side, which absorbs clock skew and anchor differences (ADR-087's storage anchor).
- **Retention.** The view copies the source row's `_retention_days`; the TTL runs off `ToAt`, so
  the index row outlives every source row it points at and expires with the last one. No clean-up job.
- **Hot storage.** The index stays on the hot volume; it must never tier to S3.
- **One owner per index.** Each index belongs to the module that owns its source table (record:
  "A ClickHouse table has one owner"). There is no shared cross-module id table.

### The read

```sql
WITH (SELECT min(FromAt) - INTERVAL 1 DAY, max(ToAt) + INTERVAL 1 DAY
      FROM trace_index
      WHERE TenantId = {tenantId:String} AND TraceId = {traceId:String}) AS bounds
SELECT … FROM trace_summaries
WHERE TenantId = {tenantId:String} AND TraceId = {traceId:String}
  AND OccurredAt BETWEEN bounds.1 AND bounds.2
```

Scalar subqueries are folded to constants before index analysis, so partition pruning is certain.
`OccurredAt IN (subquery)` likely prunes too, but the scalar form doesn't depend on it. If the
proof (below) shows it doesn't fold, it's two round trips: index first, then the source.

**A miss** (no index row) means "not there" once the backfill is done: the view writes in the
same insert as the source, so an existing row always has its index row. A miss runs one probe of
the hot recent window (35 days, catching anything mid-insert) and never an unbounded scan.
`clickhouse_windowed_read_total` counts it as a new outcome, `index_miss`. The other new outcome is
`index_hit`.

**One primitive.** `packages/clickhouse-client` gains an `indexedRead` beside `windowedRead`:
given the index table, its key and the source's partition column, it returns the bounded fragment
or a miss. Repositories call it; none hand-roll the subquery.

## Which tables

**Tier 1: id-only reads exist today (verified in code).**

| Index                  | Owner      | Fed from (view)                   | Serves                                                                 | Today                        |
| ---------------------- | ---------- | --------------------------------- | ---------------------------------------------------------------------- | ---------------------------- |
| `trace_index`          | trace      | `stored_spans` (`StartTime`)      | `trace_summaries`, `stored_spans`, `stored_log_records`, `log_records` | ladder / unbounded           |
| `aggregate_index`      | eventing   | `event_log` (`EventOccurredAt`)   | `event_log` replay and `getEventRecords` by aggregate                  | full scan unless bounded     |
| `experiment_run_index` | experiment | `experiment_runs` (`StartedAt`)   | `experiment_runs`, `experiment_run_items`, `dspy_steps` by `RunId`     | full scan                    |
| `evaluation_index`     | evaluation | `evaluation_runs` (`ScheduledAt`) | `evaluation_runs` by `EvaluationId`                                    | 35-day probe, then unbounded |
| `scenario_run_index`   | scenario   | `simulation_runs` (`StartedAt`)   | `simulation_runs`, `simulation_run_metrics` by `ScenarioRunId`         | windowed fallback            |

`trace_index` is fed from spans, not summaries: spans land first, so a span lookup for a trace whose
summary isn't projected yet still hits, and the summary's anchor falls inside the span range plus a
day. `aggregate_index` is keyed `(TenantId, AggregateType, AggregateId)`. `event_log` rows with
`EventOccurredAt = 0` sit in the 1970 partition; the replay keeps its `OR EventOccurredAt = 0` arm.

**Tier 2: candidates, audit before building** (phase 0 confirms whether an id-only read exists):
`suite_runs` (`BatchRunId`), `langy_messages` (`ConversationId`), `coding_agent_sessions` (`SessionId`,
ordered time-first), `coding_agent_session_events`, `governance_ocsf_events` (`EventId`),
`gateway_spend` (`GatewayRequestId`), `stored_objects` (`id`), thread/conversation lookups on traces.

**Not needed:** tables already unpartitioned (`instant_eval_runs`, `lwql_api_key_tenant_map`,
`governance_cost_rollup_restatement_index`), rollups and analytics tables (always read by time range),
`billable_events` and usage meters (read by org and month).

## Build order

0. **Audit.** For each tier-2 table, find id-only reads (no partition-column predicate). Promote or drop.
1. **Prove on `trace_index`** against a cloud-sized dataset: (a) the scalar bounds prune partitions
   (`EXPLAIN indexes = 1`); (b) the view's cost on `stored_spans` inserts is negligible (insert
   p99 before/after); (c) index size per million traces.
2. **`indexedRead` primitive** in `packages/clickhouse-client`, with the two new metric outcomes.
3. **Per index, one owner's slice:** a migration (table + view, separate `StatementBegin` blocks,
   `IF NOT EXISTS`, next free `clickhouse:<NNNNN>`, no `POPULATE`); a background `.withMigrations`
   backfill step (`<module>:fill-<name>-index`) that inserts `min`/`max` grouped by id, one source
   partition per checkpoint, newest first; the repository reads switched to `indexedRead`.
4. **Expand/contract the fallback.** Until its backfill step completes, a reader keeps today's
   ladder (a half-filled index can return a too-narrow range for an id straddling a partition the
   step hasn't reached). Once complete, the index is authoritative and the ladders and `"unbounded"`
   fallbacks for that table are deleted in a later release.

## Open points

- How a repository learns "the backfill step is complete" (an upgrade-ledger read through the
  upgrade module's `*Api`, or a config leaf flipped by the step). Check the upgrade skill first.
- Whether `aggregate_index`'s view cost on `event_log`, the highest-volume insert, passes proof 1(b).
  If not, the eventing replay keeps its `occurredAtFromMs` bound and skips the index.
