## 0. Summary

1. **One model for both deployments.** A step's identity is its id; what ran is the ledger, keyed by
   step id (and target for ClickHouse). Releases are manifests that group ids. Safety is a
   _window_: every schema at or above the LTS floor serves every release at or above the floor,
   checked when the PR is written, not when it is deployed. Version enters only where a version
   exists: self-hosted stepping across releases and the refusal below the floor. Cloud has no
   version; it is keyed by step id plus **presence**, the build each live process reports, which
   answers "is any old writer still serving" without ordering builds (section 3).
2. **Cloud is the degenerate case of self-hosted.** Each cloud deploy is one virtual release
   (rethink 6.3), the pre-roll runs `upgrade` with no operator, new pods refuse until it is done,
   old pods keep serving because nothing they read is removed, and background steps finish when
   presence shows no old build left. Nothing in the mechanism branches on "cloud".
3. **Thirteen lanes**, nine of them startable now (section 5), each with a manifest in
   `.claude/manifests/mig-*.md`. Real dependencies only: the ledger widening before the runner and
   the gate; the runner and the gate before the entry points are repointed.
4. **Eleven design deltas** (section 4), each held for Alex. The largest: SQL migrations stay in the
   two central directories but are attributed to their owning module by table ownership (D3), and
   presence replaces the manual drain assertion (D2).

may run after it**, **refuse destructive changes until no supported version reads the thing**, and

adds the liveness signal cloud needs (D2) and the lock-safety half of the guard (D6).

## 3. What "version-aware" means on both sides

### 3.1 The one model

| Concept                | Key                                                                        | Self-hosted                                                                                                     | Cloud                                                                                    |
| ---------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| What a step is         | step id, never reused (rethink 6.1)                                        | same                                                                                                            | same                                                                                     |
| What ran               | ledger row per step id, plus per target for ClickHouse (Q-U1 a; D4)        | same                                                                                                            | same                                                                                     |
| Order                  | release manifests; unreleased steps form one virtual release (rethink 6.3) | steps release by release when jumping several (rethink 6.4)                                                     | always one virtual release per deploy: no jump, nothing to step                          |
| Window                 | `[LTS floor, head]`, declared in the tree                                  | an install below the floor is refused by `upgrade`; an image below the ledger's floor refuses to serve (Q-U5 1) | never trips: every cloud build is newer than the newest release, so newer than the floor |
| Destructive step       | allowed only if what it removes is unread from the floor up (rethink 6.12) | checked at PR time against the declared floor                                                                   | the same PR-time check; cloud contracts wait for the floor like self-hosted (D8)         |
| "Am I current"         | every blocking step my image declares is `done` or `not-needed`            | new pods refuse until the pre-roll or the compose `migrate` service ran                                         | the same; the deploy's pre-roll runs first                                               |
| "Are old writers gone" | **presence**: every live process declares step S (D2)                      | after a Helm rolling update or a compose restart                                                                | after a gradual rollout, however long it takes                                           |

**Why cloud needs no version.** The safety predicate (nothing an older supported build reads is
removed) is evaluated in CI against the declared floor, so the deploy-time question is only "which
ids are not yet in the ledger", which is version-free. The two runtime questions that _do_ depend on
what is running are "is this process current" (answered by the image's own declared step list) and
"has every old writer stopped" (answered by presence). Neither orders builds, so `git-<sha>` images
need no number.

**What presence is** (D2). Each serving process (api, worker) writes one row when it starts and
refreshes it on an interval: process id, role, image (release or `git-<sha>`), and the ids of the
background and tenant steps its image declares. A row not refreshed within a lease is dead. "Old
writers gone for step S" is true when every live row declares S. That replaces today's manual
`assertSystemMigrationLegacyWritersDrained`, where an operator types a `minimumWriterGeneration` by
hand (`modules/ops/contract/src/ops-system-migration.ts:44-46`,
`modules/ops/process/src/services/system-migrations.service.ts:195-200`), with a predicate both
deployments compute the same way; the operator assertion stays as an override for a process that
cannot report.

### 3.2 Self-hosted: floors, stops and refusals

- The LTS floor is a file in the tree (`packages/upgrade/releases/lts-floor.json`, D9), named every
  six months (`.claude/coordinator/rulings-2026-10-05.md:221`). Which release is the first floor is held (D10).
- `upgrade` reads the ledger's installed release. Below the floor it refuses before touching
  anything: "this installation is on 3.16.0; upgrade to 3.20.1 (LTS) first, then to this image".
  That is GitLab's required stop and Sentry's hard stop, with exactly one stop per LTS.
- The ledger records the highest floor any runner applied with. A serving image whose release is
  below it refuses to start (Q-U5 1, default taken): a destructive step that floor allowed may have
  removed what it reads.
- A rolled-back image at or above the floor serves (UI 6.1.6); the next `upgrade` marks the
  level-triggered background steps `pending` again (Q-U5 2, default taken).

### 3.3 Cloud: automatic, side by side

- **Deploy contract** (what the private deploy repository must do; F17): run `pnpm task upgrade`
  from the new image, to completion, before any Deployment rolls, and never on a rollback. The
  chart's pre-roll Job already has that shape (`charts/langwatch/templates/app/migrate-pre-roll-job.yaml:63,74-75,112-113`); if the
  deploy uses the chart, nothing changes on that side beyond the command. Research gap: whether it
  does (section 7).
- **During the rollout** old pods serve on the new schema (window rule); new pods start because the
  ledger is current; background steps start on the first new worker and, where a step needs every
  old writer gone, finish when presence says so.
- **Pacing** of tenant steps stays on enrolment (rethink 6.8); a gated step is `gated`.
- **No operator page drives cloud.** The region's `/ops/upgrades` is read-mostly; alerts (U7) go to
  metrics and Slack. A failed `upgrade` fails the deploy before any pod rolls, which is the
  behaviour a gradual rollout wants.
- **The per-PR gate is the N-1 test**: the base branch's code against the head-migrated schema
  (ADR-155's still-to-land job, F16). On cloud the base branch's build is the one still serving
  during a deploy, so this job is the direct proof of "safe side by side". The floor-image job runs
  nightly (CI lane).

### 5.3 Interfaces fixed now, so the parallel lanes meet

Names are the target; a lane that finds a reason to differ records it in its handoff and keeps the
shape.

- **Step id**: `prisma:<folder>`, `clickhouse:<5-digit version>`, `<module>:<kebab-name>`.
- **Manifest** (`packages/upgrade/releases/<version>.json`, `mig-s2-manifests`): `{ release, previous,
cutAt, steps: [{ id, kind, mode, owner, description }] }`, steps in rethink 6.3's order.
- **Floor** (`packages/upgrade/releases/lts-floor.json`, `mig-s2-manifests` writes it first):
  `{ release, namedAt }`.
- **Ledger additions** (`mig-ledger-widen`): step columns `owner`, `description`; tables
  `_langwatch_upgrade_target (step_id, target, status, version, last_error, updated_at)`,
  `_langwatch_upgrade_lease (name, owner, image, host, heartbeat_at, expires_at)`,
  `_langwatch_upgrade_presence (process_id, role, image, release, steps jsonb, started_at,
heartbeat_at)`; run column `floor`.
- **Declared step** (`mig-declare`, `packages/upgrade/src/step/`): `{ id, kind, mode, description,
run({ checkpoint, dryRun, signal }), needsOldWritersGone? }`; collected as tasks are, with an
  `isMigrationStep` guard so `packages/process` takes `unknown[]` exactly as `withTasks` does.
- **Reader** (`mig-u1-reader`): `UpgradeReader` with `status()`, `listReleases()`, `listSteps({ release?,
mode?, status? })`, `getStep({ id })`, `listRuns({ cursor? })`, `getRun({ id })`, schemas in
  `packages/upgrade/src/reader/reader.schema.ts`, written first.
- **Package entry**: `mig-ledger-widen` adds one wildcard subpath export to
  `packages/upgrade/package.json` in its first step, so each lane exports from its own
  `src/<area>/index.ts` and no lane but it edits `src/index.ts`.

## 6. Lane rules every manifest repeats

No new foreign key or `@relation` (Alex, 2026-10-06). Additive migrations only. Never read `.env`.
No git writes; stage nothing. Paths other lanes own today, forbidden to every `mig-*` lane:
`modules/usage`, `modules/entitlement`, billing's usage imports, `modules/catalogue.json`, the
generated module lists (`apps/*/src/*-modules.generated.ts`), `pnpm-lock.yaml`, `packages/api`,
`*.rest.ts` families, `modules/trace`, `modules/coding-agent`, `packages/eventing`, `modules/project`,
`modules/data-privacy`, `modules/organization`, `modules/audit-log`; and, from the live roster,
`packages/system-migrations/**`, `specs/migration/**`, `specs/self-hosting/**`, `specs/worker/**`,
`specs/tooling/**`, `modules/authz/**` (`parity-rulings-misc`) and the feature files `bind-platform`
lists. A new workspace dependency is a shared-file request (the lockfile), never `pnpm install`.

## 7. Research gaps

- **No web access**: section 2 is from knowledge, confidence stated per row, nothing re-checked.
- **Cloud's deploy is private** (`langwatch/langwatch-saas` is not reachable from this session): how
  cloud applies the chart, whether the pre-roll Job runs there, and how long a rollout keeps old pods
  are unknown. `mig-cloud-presence` writes the contract the deploy must meet instead of assuming it.
- **No release tags locally** (`git tag -l 'langwatch@v3.*'` is empty): manifests since the LTS
  must be backfilled after a tag fetch (`mig-s2-manifests` step 1).
- **Prisma behaviour unproved**: deploy over subset directories with out-of-order keys, the
  client's default select against an older table, and Prisma's own advisory lock. `mig-s4-stepping-proof`
  proves or refutes each before the runner relies on it.
- **No production timings**: how long the largest blocking step or index build takes on cloud is
  unmeasured; the guard's lock-heavy rules are shape rules, not size rules.

## 8. Risks

- `mig-serving-gate` switched on before `mig-entry-points` makes every boot refuse (nothing writes the
  ledger yet). The two land in one commit; the gate lane's manifest says so.
- Presence adds one write per process start and one refresh per interval; a crashed process looks
  alive until its lease lapses, which delays "old writers gone" by at most that lease.
- D3's attribution leaves "no central list" half-met for SQL; if Alex wants files per module, that
  is a move of 463 files and a goose table per owner.
- Contract steps waiting for the LTS on cloud (D8) keep dead columns up to six months.
- Lanes in `packages/upgrade` run side by side; they share only the package root, guarded by the
  wildcard export and per-area folders.
