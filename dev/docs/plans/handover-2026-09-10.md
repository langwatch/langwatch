## 1. North star

Four processes compose modules. A module is one folder with three packages:

```
modules/<m>/
  contract/src/  <m>.api.ts      interface <M>Api and its moduleApi<...>("<m>") token
                 <m>.trpc.ts     defineTrpcContract("<ns>") per namespace
                 schemas and HandledError subclasses; no abstract service class
  server/src/    <m>.server.ts   defineModule("<m>").withRepositories(registry).withApp(<M>App).withTransports(...)
                 app/<m>.app.ts  one class implements <M>Api; static dependencies name peer APIs
                 services/       private classes the app composes
                 repositories/   <x>.repository.ts (interface), prisma/, memory/, <m>-repositories.registry.ts
                 transport/      <ns>.trpc.ts (defineTrpcRouter) and <family>.rest.ts (defineRestRouter), flat
  web/src/       model/ behavior/ ui/{elements,blocks,sections}; flat entry files the catalogue points at
apps/api/src/features/<m>/<m>.composition.ts   installApi<M>: createApp(...).withModule(server, {infrastructure}).boot({role: "api"})
apps/worker, apps/tasks                        boot the same server with their own infrastructure
packages/api/                                  the one runtime: rest/*, trpc/*; every declaration mounts through runtime.mount
```

Rules that hold everywhere: one runtime per transport; annotation is the
reference module; no refusing twins (a process installs a module or does not);
persistence is `repositories/{prisma,memory}` behind an interface, never
`ports/` or `adapters/` (those two folders are for genuinely external things:
eventing, metrics, HTTP, flags); no `try*` names (nullable only on `find*`);
config schema-driven, `process.env` only at boot; ksuid ids; `{ ok, error }`
banned; folders of at most twelve files; every scenario bound by `@scenario`.

The wire is pinned to origin/main. Procedure and route names, paths, inputs,
outputs, statuses and permissions do not change. A status collapsed to 200, a
setting that stopped being configurable, or a validation widened is a
regression, not a delta. Each unavoidable delta is recorded with its reason.

Definition of done for the branch: every baseline row closed, every REST
family in `api-rest.doors.ts` mounted, no file imports a legacy transport
builder, `pnpm typecheck` clean for the three applications, the stack boots
under haven, main folded, and the wire deltas recorded in one file.

## 5. How to do this work: the lane prompt

Paste this into any coding agent (Claude, Codex, Kimi) with the task line
filled in. The brief it names is the digest; the exemplars it names are the
recipe. Nothing else needs explaining.

```
Read dev/docs/plans/lane-brief.md first and follow every rule in it.

Task: <one module or one rule, named as baseline keys, for example
"close hosted-mcp|nested-transport and hosted-mcp|installer-not-booted">.

Method:
1. Print the baseline rows for your task from
   packages/architecture-enforcer/src/feature-shape-baseline.json and the
   exemplar files the brief names for each rule. Read each exemplar once.
2. Find the wire on origin/main before touching anything:
   git grep -n "<name>" origin/main -- platform/app/src/server/api/routers
   Names, paths, inputs, outputs, statuses and permissions are pinned.
3. Change the module to the exemplar's shape with targeted edits. Delete the
   old file in the same step that repoints its last importer
   (git grep -n "<export>" -- apps enterprise modules packages first).
   Declare and install a new dependency before its first import.
4. After each landed step: haven logs backend --since 2m --agent. A
   SyntaxError, ERR_MODULE_NOT_FOUND or fatal boot failure naming your files
   is your defect; fix it before the next step.
5. Check once at the end: VITEST_MAX_WORKERS=2 pnpm --filter <package>
   test:unit <paths you touched>, then pnpm typecheck:one <package dir>.
6. Do not edit the shared files the brief lists; write the exact lines the
   coordinator must add to them into your report instead.

Budget: 120 tool calls or 90 minutes. One shell call runs several commands.
Read a file once. When the budget is reached, stop and report.

Report (as the last message): files changed by package; exact lines for each
shared file; namespaces and families served with counts versus origin/main;
wire deltas with reasons; scenario bindings kept; test and typecheck results
per package; baseline rows to drop as rule|path keys; unfinished items,
numbered.

Never: git add, commit, stash, checkout, reset, restore, mv; pnpm typecheck,
pnpm lint, pnpm format, tsc -p; reading any .env file; printing a secret;
running vitest in the background; re-exports; as unknown as; as never;
ctx: unknown; non-null !; inline import(); try* names; { ok, error } returns;
em dashes; comments over five lines.
```

Model choice: design work (a new shape, a wire question) goes to the strongest
model at high effort; exemplar-following (this prompt) runs well on a
mid-tier model; pure file moves run on the cheapest. Cost is quadratic in the
number of turns, so a lane that batches its shell calls at 60 turns costs a
quarter of one that takes 120.

### The coordinator's loop

1. Pick tasks that touch disjoint files. Two lanes never share a module.
2. Spawn each with the prompt above. Inspect every 15 minutes with the lane
   status script; at 45 minutes demand a status; at the cap stop it and start
   a fresh lane from its report (never resume: a resumed lane pays its full
   context on every further turn).
3. On report: read the diff of the files it names, run the same package
   check once, apply the shared-file lines by hand, drop the baseline rows it
   names, commit by pathspec (a temp index; never `git add -A`, never stash).
4. Read `haven logs backend --since 2m --agent` after every commit. A crash
   naming a file is fixed before the next spawn.
5. Every 30 minutes print the counters beside the previous tick with a verdict
   of closer, same or further. Two flat ticks means the approach changes.

## 7. Proving the wire: apidiff and visualdiff

Two Go tools in `cmd/` prove that the branch serves what main serves. Both
boot main and the branch as two haven stacks under run-scoped slugs, in their
own worktrees, never in the invoking checkout, and both tear those two slugs
down themselves. Neither is run by a lane; the coordinator runs them and feeds
the findings to a triage agent.

### apidiff: the REST surface

```bash
go run ./cmd/apidiff run -dry-run                 # prints both refs, both slugs, every command; starts nothing
go run ./cmd/apidiff run -keep -report .apidiff/report.json -ledger .apidiff/ledger.json
go run ./cmd/apidiff probe -a <branch-url> -b <main-url> -json   # two instances already up
```

It fetches each side's `/api/openapi.json`, diffs the specs, then probes the
union of operations in lockstep (candidate first, then base, so both databases
stay in the same state), masks ids, timestamps and secrets, and reports status
class, response shape, validation envelope and mutation outcome differences.
The `-report` file is the evidence; the `ledger.json` beside it is the
worklist, grouped by root cause; `-ledger-baseline <previous ledger>` makes a
run fail only on a cause the previous run did not name. Findings stream to
`<work-root>/findings.jsonl` one line per operation as they are decided, with
a `run-complete` line last. Exit 0 no differences, 1 differences, 2 the run
could not complete. Gateway routes are excluded by default (they egress to
real providers). Same-class status differences (400 versus 422) are
suppressed unless `-exact-status`.

The last full run at `e28c2e6cb2` probed 280 of a 604-operation union and
found 39 routes main serves that this branch answers 404; those are the
`families_absent` counter from the other side.

### visualdiff: every screen

```bash
go run ./cmd/visualdiff run -dry-run             # plan and flow list only
go run ./cmd/visualdiff run -keep -agent         # stacks stay up when the run ends
go run ./cmd/visualdiff recapture -run <run-id> -routes /{slug}/analytics,/{slug}/settings
haven destroy visualdiff-<run-id>-base visualdiff-<run-id>-candidate   # when done
```

Routes and flows come from `visualdiff.yaml` at the repo root (add a route
there; `{slug}` is substituted). Each screen pair is classified: `regression`
(the candidate throws or fails a step where main does not), `restore-gap` (the
candidate 404s an `/api/` call main answers), `intended-restore`, `noise`
(under 2 percent, no errors) and `changed`. Only the first two count as
findings. The run writes `report.html`, `findings.md` and `findings.json` at
the end and streams `.visualdiff/<run-id>/findings.jsonl` while running, each
line carrying the route, kind, best-guess owning module, evidence paths and a
message.

### The triage loop

A full run takes 20 to 40 minutes, so nobody waits for the report. Start the
run with `-keep`, then hand `findings.jsonl` to one persistent triage agent:

```
Tail .visualdiff/<run-id>/findings.jsonl (or .apidiff/<run-id>/findings.jsonl).
For each line whose kind is not identical or noise: group by module; fix
web-side and api-side items yourself under the lane brief's rules; write
server-side items into a list for the coordinator with the route, the kind and
the evidence path. After each fix run
  go run ./cmd/visualdiff recapture -run <run-id> -routes <the routes you touched>
and confirm the new line says identical. Stop at the run-complete line and
report: fixed routes, routes handed over, routes still differing with reasons.
```

The agent stays alive across batches (SendMessage, not a new spawn per batch),
and the coordinator destroys the two slugs when the list is empty.

**Come back early.** A run that finds the same error on many screens, or
simply a flood of findings, is one defect, not a hundred: a missing mount, a
broken layout shell, a dead endpoint every page calls. Feeding all of it
into triage buries the cause under its symptoms and overloads the agent with
feedback it cannot act on. So the rule for both tools is:

- The triage agent stops reading the stream as soon as one error signature
  (same console message, same failing `/api/` path, same step) appears on
  more than five screens, or the finding count passes twenty. It reports the
  signature and the count, fixes that one cause, recaptures three of the
  affected routes, and only then reads on.
- visualdiff itself should do the same: stop the capture when one signature
  repeats past a threshold or the total passes a cap, write `run-complete`
  with `reason: "early-stop"` and the signature, and leave the stacks up
  with `-keep` so a recapture can continue from there. That flag
  (`-stop-after <n>` and a per-signature `-stop-repeat <n>`) is queued
  tooling work; until it lands the triage rule above is what prevents the
  flood.
