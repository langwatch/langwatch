## 0. Summary

The upgrade system is well built in its shape (ledger, lease, stepping, gate, roster, background
steps, replay steps, upcasts, guards), but this PR cannot ship on it safely yet. Three groups of
findings:

1. **Two first-deploy outages from data no step fills.** `origin/main` never recorded project
   lifecycle facts (`lw.project.*` appears nowhere on main), and the branch's new copies of project
   placement are filled only from those facts. On the first deploy to any existing installation:
   - data-retention's `DataRetentionProjectScope` stays empty, `getResolvedForProject` throws
     `ProjectNotFoundError` for every existing project, and every trace projection retries and then
     dead-letters (`data-retention.service.ts:81-83`, `trace-processing-runtime.pipeline.ts:133-135`,
     `projectionRouter.ts:2290-2300`);
   - data-privacy's `DataPrivacyProjectScope` stays empty, so the trace viewer hides captured
     content for every existing project (fail-closed, `trace-viewer-protection.service.ts:110-127`),
     and ingest sends every span of those projects to the analysis service instead of the native
     pass (`pii-redaction-policy.service.ts:251-261`): native secrets redaction is skipped, the
     analysis service takes all of that load, and in production without `LANGEVALS_ENDPOINT` the
     redaction throws and the span is not stored (`:377-381`).
     The facts come only from manual tasks (`backfill-project-created`,
     `backfill-project-department-assigned`) that no entry point runs and no operator doc names.
2. **Defects in the built system that this PR's steps would hit at once.** The serving roster
   declares no steps in production (`serving-upgrade-gate.ts:246` reads the image tree with no code
   steps), so every `needsOldWritersGone` step waits forever and every pod admitted after an upgrade
   reopens every done unreleased background step with its checkpoint cleared. A step that returns
   on abort is recorded `done`. A failed background step is never retried. Pre-roster images
   (`origin/main`, 3.20.1) are invisible to the roster, so "old writers gone" is true while they
   still serve on the first deploy.
3. **Fills, drains and checks that are missing or wrong** for specific changes: Slack connection
   claims for existing triggers, report schedules, coding-assistant billing facts, the Instant Evals
   judge, nurturing's "first" signals, the trace meter seed at cloud scale, moved queue lanes, an
   AuditLog unique index built in place, and a migration-compat N-1 job that judges nothing for this
   PR because `origin/main` has no live api suite.

Inventory (section B): **82 rows: 39 OK, 29 flagged, 12 pending, 2 not verified.** Work (section D):
**18 new lanes plus 2 already in flight, in four waves, all before merge**; D.2 lists what may
follow. Decisions (section E): **8 questions**.

## E. Decisions for Alex

Each is a question no ruling answers. The recommendation is first.

**E1. Copies of project placement made before round 40.** Round 40 made shares the rule ("never a
copy, unless a ruling names a reason"). Data-retention's and data-privacy's project-scope folds and
the Instant Evals judge's project table were ruled before it (Q151, DP1, ADR-174), and they are
what breaks the first deploy (R01 to R03): they fill only from project facts main never recorded,
and miss any project an old image creates.

- (a) **Recommended.** Convert all three, and presence's Redis fold, to declared Postgres shares of
  project's `Project` and team rows (every placement column exists there: `teamId`, `isPersonal`,
  `departmentId`, `archivedAt`, `presenceEnabled`, and the team's `organizationId`); delete the
  folds, their branch-only tables and S07 before merge. No fill, no window, no rollback gap.
  Nurturing's guard reads the organisation's creation the same way, so no consumer is left needing
  the project facts backfill.
- (b) Keep the folds; on a fold miss read the share; add the facts step. Two sources of truth for a
  while, and the fallback must be kept until the folds are complete.
- (c) Keep the folds; rely on the facts step alone. A window of failed ingestion and hidden content
  on every deploy from an image without facts, and after any rollback to one.

**E2. Old writers that predate the roster.** `origin/main` and 3.20.1 write no roster row, so on the
first deploy "old writers gone" is true while they serve, and a rollback to them is invisible.

- (a) **Recommended.** A rollout-complete marker: Helm runs `pnpm task upgrade rollout-complete` as a
  `post-upgrade` hook, the cloud deploy contract adds the same call after the rollout, compose and
  npx already stop old processes first. NOWG steps wait for the marker on an installation whose
  roster history starts at this run; the rollback runbook names the command that reopens
  level-triggered steps after a rollback to a pre-roster image.
- (b) A fixed grace (for example 30 minutes) after the first roster-era run, then run; reopen
  level-triggered steps once at the next upgrade. No new hook, but a slow rollout beats the grace.
- (c) Accept: run at once, and rely on the next upgrade's reopen. Gaps last until the next deploy
  (hours on cloud, months on self-hosted).

**E3. Seeding the trace meter at cloud scale.** S08 replays every `span_received` since 2026-09-01
for every tenant; discovery is all in memory and reads only the shared ClickHouse.

- (a) **Recommended.** Keep the replay step, and make replay discovery per tenant, streamed and
  routed (MIG-REPLAY-SCALE), with NOWG and a trailing pass. One mechanism, and every later replay
  step benefits.
- (b) Replace the replay with a SQL backfill from trace's `trace_summaries` through a declared
  shared table (one insert per routed target and month). Fast, but a second way to fill a meter.
- (c) Seed only the current and previous month (`since` computed at deploy as the first day of the
  previous month). Smaller, still large on cloud, and still blind to private dataplanes.

**E4. Jobs queued on lanes that moved at this release.** Rounds 25 and 38 accepted losing "at most
one window" of three moved lanes' jobs, and round 25 ruled out handover machinery. Old api pods keep
staging main's lane names for the whole rollout; once the last old worker stops those jobs are
unroutable (`eventSourcing.ts:874`), so the loss is the rollout tail, not one window. The existing
`.withUpcasts` drain cannot carry these moves: it is keyed by one former pipeline and keeps the job
type (`eventSourcing.ts:772-805`), while `trace_processing`'s lanes moved to four modules as peer
subscribers. MIG-LANES lists every moved lane.

- (a) **Recommended.** Accept the rollout tail for lanes whose work is advisory or re-derivable, and
  for alerts (`triggerMatch`, `graphTriggerActivity`) and evaluation triggers widen the existing
  drain so a former `(pipeline, lane)` may name any current lane, for one release (a narrow
  exception to round 25, removed by UP-5's lint).
- (b) Accept the tail for every moved lane, round 25 kept whole; the deployment notes say alerts and
  online evaluations for spans ingested in the tail are not run.
- (c) Order the rollout so workers roll after the api (chart and deploy contract), keeping an old
  consumer while old producers live. Hard to guarantee on every deployer.

**E5. The new foreign key on `slack_connection_claim`.** W-01 forbids new foreign keys; this one
(`ON DELETE RESTRICT` to `SlackIntegration`) passed only because the scanner's marker exempts this
branch's earlier migrations. The migration is not on main, so it may still change.

- (a) **Recommended.** Drop the `FOREIGN KEY` clause from the unmerged migration; the claim check in
  slack's service already refuses deleting a claimed connection.
- (b) Keep it as a grandfathered exception and record it beside W-01's baseline.

**E6. Dropping `RoleBinding`'s unique indexes inside the window.** The drop (P17) enables duplicate
bindings (ruled 2026-09-30), but 3.20.1 and main rely on those indexes for idempotent writes, and
their UI revokes one of several duplicate bindings, so access can survive a revoke on a rolled-back
image. The floor rule was not applied to the drop because the scanner does not treat `DROP INDEX`
as destructive.

- (a) **Recommended.** Keep the drop; the rollback runbook carries a statement that removes
  bindings differing only by id, to run before a rolled-back image serves; the scanner learns that
  dropping a unique index is destructive, for the future.
- (b) Defer the drop and the duplicate-binding behaviour until the floor is at or above this release.

**E7. `annotation:record-existing-facts` after round 40.** The step existed so trace could fold
annotations (round 24); round 40 removed that fold and round 41 keeps annotation's facts. The step
now appends one fact per existing annotation for no consumer.

- (a) **Recommended.** Remove the step until a consumer needs history; a future consumer declares
  its own fill.
- (b) Keep it, so annotation's log is complete from this release.

**E8. How a drain's age is measured (UP-5).** Round 16 ruled a lint for drains older than one
release, but a drain records no release.

- (a) **Recommended.** Derive it: the earliest release manifest naming any of the declaration's
  `upcast:<pipeline>:<type>` step ids is the drain's release; the lint fails when the newest
  manifest is two releases past it.
- (b) A required `since: "<release>"` field on `drain`, written by hand.
- (c) No lint; review by hand.

## F. Verification plan

The proof is a rehearsal of the real upgrade, from real images, over seeded data, with old and new
processes overlapping, then a rollback and a re-upgrade. It lives in `dev/scripts/upgrade-rehearsal/`
(compose with two image tags; haven serves the head stack where convenient) and runs as
`.github/workflows/upgrade-rehearsal.yml` on dispatch and nightly. The deterministic pieces also
run as service-backed integration tests in CI.

**Origins.** Run everything twice: from the published 3.20.1 image (self-hosted at the floor) and
from a `origin/main` head image (cloud's predecessor, which also carries main's four unreleased
migrations). Once more from an empty database (fresh install).

**Phase 0, seed through the old image's own surfaces.** Organisations with teams, departments,
personal and archived projects; users active, deactivated, unconfirmed and never signed in; a
data-privacy policy with secrets redaction on and a custom retention policy; annotations with
scores; topics; workflows with versions and HTTP agents with inline credentials; Slack connections
used by active and paused triggers; scheduled reports; a licence on an organisation; an SSO
connection; open suite and scenario runs; pulled-usage events; a coding-assistant source; OTLP
traces, spans and logs in the current and previous month; evaluations and an Instant Evals query;
one organisation on a private ClickHouse route (a second ClickHouse target). Leave jobs in flight:
pause the old worker and ingest, so main's lanes hold queued jobs at the cut.

**Phase 1, upgrade with overlap.** Run head's `start:prepare:db` while the old api and worker
serve; keep a load generator writing through the old api during and after (spans, projects, user
deactivations, Slack trigger saves, licence changes). Start head's api and worker beside the old
ones; stop the old api first and the old workers last; repeat with the reverse order (E4).

**Phase 2, assertions.**

- Ledger: every Prisma folder and goose version `done` on both ClickHouse targets; blocking steps
  `done`; every background step `done` within a bound, none `waiting` once the marker (E2) is set;
  restarting every head pod twice reopens nothing.
- One check per inventory row: retention, privacy and the judge resolve for old projects on the
  first request (R01 to R03); captured content visible (R01); no trace job dead-lettered (R02);
  presence on (R05); coding-assistant source billed (R06); claimed connections refuse deletion
  (R07); reports fire on schedule (R08); deactivated users recorded (P01); licences copied and
  reconciled (S06); meter count equals trace count for both months and the private-route
  organisation (S08); scim view complete (S09); log records readable from both tables (O01); no
  "first" signal for existing organisations in analyticssim (R04); governance drift reports zero
  (C02); LangWatchQL key map rows for old projects (R10).
- Queues: `gq_jobs_unroutable_total` and ops' blocked groups match MIG-LANES's classification; no
  dead-letter beyond the accepted list.

**Phase 3, rollback.** Stop head; start the old image on the upgraded schema with no upgrade run (a
Helm rollback). Run the HTTP smoke of MIG-COMPAT-CI; write through it (projects, deactivations,
annotations, licence changes, a Slack deletion, a binding revoke). Expect P16 and P17's documented
behaviour and nothing else.

**Phase 4, re-upgrade.** Run head's upgrade and roll head again. The writes of phase 3 are
reconciled by level-triggered steps (per E2); no duplicates; no step re-runs from the start unless
its kind requires it.

**Phase 5, failure drills.** SIGKILL and SIGTERM a worker mid-step (resumes from its checkpoint and
is never `done` early); a transient ClickHouse refusal (retried); two workers on one step (one
runs); lease loss inside `upgrade` (the blocking step stays resumable); a second `upgrade` run (a
no-op).

**Phase 6, scale.** A synthetic large tenant set (for example 20,000 projects, 200,000 users,
5 million spans in 500,000 traces, one private route): record each step's duration, peak worker
memory and replay discovery memory against fixed bounds; time the `AuditLog` index and the 00103
mutation on a cloud-sized copy of the schema with synthetic rows.

**Phase 7, stored-event compatibility.** Export `event_log` after phase 0 and parse every row with
head's schemas and upcasts: zero refusals. Fresh install: every data step `not-needed` or `done`,
and a second run is a no-op.

**In CI on every PR that touches migrations or steps:** the Prisma and ClickHouse scanners,
`migration-order`, `migration-owners`, `rerunnable-migrations`, the `packages/upgrade` integration
suites (Postgres), the replay integration tests (ClickHouse), MIG-COMPAT-CI's floor and main-head
smoke, and the rehearsal's phases 0 to 2 from 3.20.1 when the images are available.

**Pass criteria for merge:** every phase green from both origins; every FLAG row in section B fixed
or its decision ruled and applied; the report attached to the PR.
