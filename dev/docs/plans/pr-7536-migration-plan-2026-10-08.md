## 0. Summary

The upgrade system is well built in its shape (ledger, lease, stepping, gate, roster, background
steps, replay steps, upcasts, guards), but this PR cannot ship on it safely yet. Three groups of
findings:

1. **Two first-deploy outages from data no step fills.** `origin/main` never recorded project
   lifecycle facts (`lw.project.*` appears nowhere on main), and the branch's new copies of project
   placement are filled only from those facts. On the first deploy to any existing installation:
   - data-retention's `DataRetentionProjectScope` stays empty, `getResolvedForProject` throws
     `ProjectNotFoundError` for every existing project, and every trace projection retries and then
     dead-letters (`data-retention.service.ts:81-83`, `trace-processing-runtime.pipeline.ts:133-135`,
     `projectionRouter.ts:2290-2300`);
   - data-privacy's `DataPrivacyProjectScope` stays empty, so the trace viewer hides captured
     content for every existing project (fail-closed, `trace-viewer-protection.service.ts:110-127`),
     and ingest sends every span of those projects to the analysis service instead of the native
     pass (`pii-redaction-policy.service.ts:251-261`): native secrets redaction is skipped, the
     analysis service takes all of that load, and in production without `LANGEVALS_ENDPOINT` the
     redaction throws and the span is not stored (`:377-381`).
     The facts come only from manual tasks (`backfill-project-created`,
     `backfill-project-department-assigned`) that no entry point runs and no operator doc names.
2. **Defects in the built system that this PR's steps would hit at once.** The serving roster
   declares no steps in production (`serving-upgrade-gate.ts:246` reads the image tree with no code
   steps, and the api builds no steps at all), so every `needsOldWritersGone` step waits forever,
   and while steps are unreleased (continuously on cloud) every pod admitted after an upgrade reopens
   every done background step with its checkpoint cleared. A background step that returns on abort
   is recorded `done` (latent on the blocking runner). A failed background step is never retried.
   The trace meter seed cannot survive a worker stop and restarts from its `since` after every
   deploy. Pre-roster images (`origin/main`, 3.20.1) are invisible to the roster, so "old writers
   gone" is true while they still serve on the first deploy. Whether head workers process the jobs
   main queued before the cut at all is unproven (head's job envelope differs).
3. **Fills, drains and checks that are missing or wrong** for specific changes: Slack connection
   claims for existing triggers, report schedules, coding-assistant billing facts, the Instant Evals
   judge, nurturing's "first" signals, the trace meter seed at cloud scale, a floor rollback over
   main's unreleased `DEVELOPER` seat value, an AuditLog unique index built in place, and a
   migration-compat N-1 job that judges nothing for this PR because `origin/main` has no live api
   suite.

Inventory (section B): **85 rows: 39 OK, 32 flagged, 12 pending, 2 not verified.** Work (section D):
**17 new lanes plus 2 already in flight, in five waves of at most six, all before merge**; D.2 lists
what may follow and D.4 the operator tasks. Decisions (section E): **8 questions**.

The LTS floor is the newest release at merge (ADR-173, D10): 3.20.1 today, and it moves if main
cuts a release before this PR merges (U02).

## E. Decisions for Alex

Each is a question no ruling answers. The recommendation is first.

**E1. Copies made before round 40.** Round 40 made shares the rule ("never a copy, unless a ruling
names a reason"). Several read models ruled before it copy another module's stored data, and each
needs a fill that main's data cannot give: data-retention's and data-privacy's project scopes
(Q151, DP1), presence's settings fold, the Instant Evals judge's `InstantEvalJudgeProject`,
`InstantEvalJudgeUsageBilling` and `InstantEvalJudgeSpend` (ADR-174), nurturing's `NurturingProject`
(its `seeded` flag is set on insert only), trace's `TraceIngestSourceBilling` (Q82) and authz's
`AuthzUserStanding`. The first two are what break the first deploy (R01, R02).

- (a) **Recommended.** Convert every copy whose source is a table to a declared Postgres share of
  that table (project placement: `teamId`, `isPersonal`, `departmentId`, `archivedAt`,
  `presenceEnabled` and the team's `organizationId` all exist on `Project` and `Team`; the judge's
  billing and spend from their owners; the user's standing from `User`). No fill, no window, no
  rollback gap. The migration folders stay (`20261006170527` is the scanner's `NEW_RULES_FROM`
  marker) and the unused tables retire later with a contract at the floor.
- (b) Keep the copies; on a miss read the share; add the facts and catch-up steps. Two sources of
  truth until the copies are complete.
- (c) Keep the copies; rely on fill steps alone. A window of failed ingestion and hidden content on
  every deploy from an image without facts, and after any rollback to one.

**E2. Old writers that predate the roster.** `origin/main` and 3.20.1 write no roster row, so on the
first deploy "old writers gone" is true while they serve, and a rollback to them is invisible.
ADR-173 (`:88`) already keeps "the operator assertion ... as an override for a process that cannot
report"; it is not wired to background steps.

- (a) **Recommended.** Implement that override: wire ops' `assertSystemMigrationLegacyWritersDrained`
  into `oldWritersGoneFor`, so on an installation whose roster history begins at this run a NOWG
  step waits for the assertion, with a grace fallback (a configurable bound after the run finished)
  for installations where nobody asserts. Callers: the cloud deploy contract after its rollout; an
  optional Helm `post-upgrade` hook, which must wait for the rollout itself as
  `stored-objects-serialize-upgrade.yaml:22-36` does, and so needs RBAC and a service-account token,
  which is off by default; compose recreates the app and the workers independently, so it relies on
  the grace. The rollback runbook names the command that reopens level-triggered steps after a
  rollback to a pre-roster image.
- (b) The grace alone (for example 30 minutes after the first roster-era run), then reopen
  level-triggered steps once at the next upgrade. Nothing new to wire, but a slow rollout beats it.
- (c) Accept: run at once, and rely on the next upgrade's reopen. Gaps last until the next deploy
  (hours on cloud, months on self-hosted).

**E3. Seeding the trace meter at cloud scale.** S08 replays every `span_received` since 2026-09-01
for every tenant; discovery is all in memory, reads only the shared ClickHouse, and a worker stop
sends it back to `since`.

- (a) **Recommended.** Keep the replay, starting from the first of the current month at deploy
  (smaller; the previous month stays as counted today, and limits are soft), with NOWG and a
  trailing pass; MIG-REPLAY-SCALE scopes down to per-tenant routed discovery plus a cursor.
- (b) Keep `since` at 2026-09-01 (both months the enforcement reads) on the same per-tenant replay;
  larger, and longer to finish on cloud.
- (c) Replace the replay with a SQL backfill from trace's `trace_summaries` through a declared
  shared table (one insert per routed target and month). Fast, but a second way to fill a meter.

**E4. Jobs queued on lanes that moved at this release.** Rounds 25 and 38 accepted losing the jobs
of three moved lanes. On main the workers, not the api, stage subscriber lanes after the fold, so
jobs for main's lane names stop appearing once the last old worker stops: the loss is the worker
rollout's tail, close to what those rounds accepted. Q02's lanes (alerts, simulation metrics,
lifecycle syncs, origin resolution) are unruled.

- (a) **Recommended.** Accept the tail for every moved lane, as rounds 25 and 38 did, and have the
  rehearsal measure it (phase 2) so the deployment notes state a number.

## F. Verification plan

The proof is a rehearsal of the real upgrade, from real images, over seeded data, with old and new
processes overlapping, then a rollback and a re-upgrade. It lives in `dev/scripts/upgrade-rehearsal/`
(compose with two image tags; haven serves the head stack where convenient) and runs as
`.github/workflows/upgrade-rehearsal.yml` on dispatch and nightly. The deterministic pieces also
run as service-backed integration tests in CI.

**Origins.** Run everything twice: from the published 3.20.1 image (self-hosted at the floor) and
from a `origin/main` head image (cloud's predecessor, which also carries main's four unreleased
migrations). Once more from an empty database (fresh install).

**Phase 0, seed through the old image's own surfaces.** Organisations with teams, departments,
personal and archived projects; users active, deactivated, unconfirmed and never signed in; a
data-privacy policy with secrets redaction on and a custom retention policy; annotations with
scores; topics; workflows with versions and HTTP agents with inline credentials; Slack connections
used by active and paused triggers; scheduled reports; a licence on an organisation; an SSO
connection; open suite and scenario runs; pulled-usage events; a coding-assistant source; OTLP
traces, spans and logs in the current and previous month; evaluations and an Instant Evals query;
one organisation on a private ClickHouse route (a second ClickHouse target). Leave jobs in flight:
pause the old worker and ingest, so main's lanes hold queued jobs at the cut.

**Phase 1, upgrade with overlap.** Run head's `start:prepare:db` while the old api and worker
serve; keep a load generator writing through the old api during and after (spans, projects, user
deactivations, Slack trigger saves, licence changes). Start head's api and worker beside the old
ones; stop the old api first and the old workers last; repeat with the reverse order (E4).
Restart an old api and an old worker mid-rollout: main's `scripts/start-runtime.sh` re-runs
`start:prepare:db`, LangWatchQL provisioning and its system-migrations pass on every pod start, over
head's schema and ledger (S01's re-finalize case).

**Phase 2, assertions.**

- Ledger: every Prisma folder and goose version `done` on both ClickHouse targets; blocking steps
  `done`; every background step `done` within a bound, none `waiting` once the marker (E2) is set;
  restarting every head pod twice reopens nothing.
- One check per inventory row: retention, privacy and the judge resolve for old projects on the
  first request (R01 to R03); captured content visible (R01); no trace job dead-lettered (R02);
  presence on (R05); coding-assistant source billed (R06); claimed connections refuse deletion
  (R07); reports fire on schedule (R08); deactivated users recorded (P01); licences copied and
  reconciled (S06); meter count equals trace count for both months and the private-route
  organisation (S08); scim view complete (S09); log records readable from both tables (O01); no
  "first" signal for existing organisations in analyticssim (R04); governance drift reports zero
  (C02); LangWatchQL key map rows for old projects (R10).
- Queues: every job left in flight at the cut is processed by head or classified by MIG-LANES
  (Q09); `gq_jobs_unroutable_total`, ops' blocked groups and main workers' refusals of head-only
  types (Q08) are counted, giving E4 its number; no dead-letter beyond the accepted list.

**Phase 3, rollback.** Stop head; start the old image on the upgraded schema with no upgrade run (a
Helm rollback). Before stopping head, give one organisation a `DEVELOPER` membership and joiner role
(P31), on the 3.20.1 origin. Run the HTTP smoke of MIG-COMPAT-CI; write through it (projects,
deactivations, annotations, licence changes, a Slack deletion, a binding revoke). Expect P16, P17 and
P31's documented behaviour and nothing else.

**Phase 4, re-upgrade.** Run head's upgrade and roll head again. The writes of phase 3 are
reconciled by level-triggered steps (per E2); no duplicates; no step re-runs from the start unless
its kind requires it. Queue groups the rollback left blocked (head-staged jobs the old workers
refused) are listed in ops and redriven, and the redrive completes.

**Phase 5, failure drills.** SIGKILL and SIGTERM a worker mid-step (resumes from its checkpoint and
is never `done` early); SIGTERM during S08's replay (it stops within the shutdown deadline and
resumes from its tenant cursor, not from `since`); a transient ClickHouse refusal (retried); a
failed lease renewal (the holder stops); two workers on one step (one runs); lease loss inside
`upgrade` (the blocking step stays resumable); a second `upgrade` run (a no-op).

**Phase 6, scale.** A synthetic large tenant set (for example 20,000 projects, 200,000 users,
5 million spans in 500,000 traces, one private route): record each step's duration, peak worker
memory and replay discovery memory against fixed bounds; time the `AuditLog` index and the 00103
mutation on a synthetic table sized from D.4's measurement.

**Phase 7, stored-event compatibility.** Export `event_log` after phase 0 and parse every row with
head's schemas and upcasts: zero refusals. Fresh install: every data step `not-needed` or `done`,
and a second run is a no-op.

**In CI on every PR that touches migrations or steps:** the Prisma and ClickHouse scanners,
`migration-order`, `migration-owners`, `rerunnable-migrations`, the `packages/upgrade` integration
suites (Postgres), the replay integration tests (ClickHouse), MIG-COMPAT-CI's floor and main-head
smoke, and the rehearsal's phases 0 to 2 from 3.20.1 when the images are available.

**Pass criteria for merge:** every phase green from both origins; every FLAG row in section B fixed
or its decision ruled and applied; the report attached to the PR.
