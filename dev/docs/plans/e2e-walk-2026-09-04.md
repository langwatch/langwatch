## Findings

### F1 — the API process never puts a session on the tRPC context, so every signed-in page 401s. This is the blocker.

A caller whose cookie the same process verified a millisecond earlier is
anonymous to every packaged tRPC surface:

```
GET /api/auth/session                     200  {"session":{…},"user":{"id":"local-dev-admin-user",…}}
GET /api/trpc/organization.getAll?input=… 401  {"error":{"json":{"message":"UNAUTHORIZED","code":-32001,
                                                 "data":{"code":"UNAUTHORIZED","httpStatus":401,
                                                 "path":"organization.getAll",…}}}}
```

The whole path, from the composition to the throw:

1. `apps/api/src/app/api-production.composition.ts:795` composes the request
   policy: `ApiRequestPolicy.create({ authentication: AuthSessionApiAuthenticationAdapter.create(…), … })`.
2. `apps/api/src/api.process.ts:84` takes `options.requestPolicy?.asHttpOptions()`
   as the process's `createContext`.
3. `apps/api/src/api-request.policy.ts:106-126` — `createContext` returns
   `{ actor, can, authorize, authorizeScopeLineage }`. **No `session`, no
   `tryActor`, no `req`.** `session` is an optional member of
   `ApiRequestContext` (`apps/api/src/api.application.ts:69`) and nothing on this
   process ever supplies it.
4. `apps/api/src/api.application.ts:604` — `session: context.session ?? null`,
   so the context handed to every procedure carries `session: null` on **every**
   request, authenticated or not.
5. `packages/features/organization/server/src/transport/api-trpc/organization.api.ts:481-483`:

   ```ts
   function sessionUser(ctx: OrganizationTrpcContext): OrganizationTrpcSessionUser {
     const user = ctx.session?.user;
     if (!user) throw new TRPCError({ code: "UNAUTHORIZED" });
     return user;
   }
   ```

   The log line, verbatim:

   ```
   WARN (langwatch:trpc): trpc call {"path":"organization.getAll","type":"query","statusCode":401}
     error: TRPCError: UNAUTHORIZED
         at sessionUser (packages/features/organization/server/src/transport/api-trpc/organization.api.ts:482:20)
         at <anonymous> (…/organization.api.ts:624:26)
         at <anonymous> (packages/api/src/trpc/trpc-runtime-policy.ts:254:16)
   ```

The data is not missing — it is discarded. `AuthSessionApiAuthenticationAdapter.authenticate`
(`apps/api/src/app/api-auth.composition.ts:411-431`) resolves the **full** session
(`this.auth.tryResolveBrowserSession({ verified })`, which yields `session.user`)
and then returns `{ id: session.user.id }`, because `ApiAuthenticationPort.authenticate`
is typed `Promise<ApiActor | null>` and `ApiActor` is `Readonly<{ id: string }>`
(`apps/api/src/api.application.ts:46`).

Two consequences worth separating. The authorization chain is *fine* — `actor()`
answers, so `protectedProcedure` admits the caller; it is the rendering half
that finds nobody. That is why `organization.api.ts:477-478`'s docblock ("`protectedProcedure`
has already refused an anonymous caller, so this only narrows the type") is now
false: the narrowing is the only check that runs, and it is the one that fails.

Not fixed here. The fix is not local — it widens `ApiAuthenticationPort`'s return
or adds a second port, and touches `api-request.policy.ts`, `api-auth.composition.ts`
and `api-production.composition.ts`, all of which other agents are editing.

### F2 — a failed `organization.getAll` renders an empty document, with no error state anywhere

Every route inside the org-gated shell paints nothing: no error screen, no
console exception, no "something went wrong". `document.body.innerText` is the
empty string on 15 of the 21 steps above.

The mechanism is that the query's failure is never read.
`apps/ui/src/features/home/ui/sections/home-host.tsx:65`:

```ts
const organizations = homeApi.organization.getAll.useQuery({ isDemo: false });
```

`organizations.error`, `organizations.isError` and `organizations.status` appear
nowhere in that file, nor in
`apps/ui/src/features/organization/ui/sections/organization-host.tsx`. The host
exposes only `isLoading: () => organizations.isLoading` (line 105), which after a
401 is `false`. So every consumer is told the graph has settled and contains no
organization, and renders the "nothing to show" branch — which is nothing at all.
`apps/ui/src/features/evaluator/ui/sections/evaluator-host.tsx:25` has the same
shape.

This outlives F1: any future 401, 500 or network failure on that one query blanks
the whole application. It is also the surviving half of 09-03's F4 — the shell
now degrades correctly when the caller is *signed out* (it redirects to
`/auth/signin`) and still has no answer for the query *failing*.

### F3 — both trace-read routes 500 on an optional dependency nobody wires

```
GET /api/traces/walk0904178851406700000000000000  500  {"error":"Internal Server Error","message":"An unknown error occurred"}
GET /api/trace/walk0904178851406700000000000000   500  "TraceService requires EvaluationService for evaluation reads"
```

Both are the same throw, at
`packages/features/trace/server/src/services/trace-legacy-read.service.ts:711-714`:

```ts
private evaluations(): EvaluationService {
  if (!this.evaluationService) {
    throw new Error("TraceService requires EvaluationService for evaluation reads");
  }
  return this.evaluationService;
}
```

reached from `getEvaluationsMultiple` (line 661) on every single-trace read.

`evaluationService` is optional at construction
(`trace-legacy-read.service.ts:356`), and the API process never passes it.
`apps/api/src/app/api-trace-read-stack.composition.ts:594-602` builds the reader
with `...(options.evaluations ? { evaluationService: options.evaluations } : {})`,
and the one production call site —
`apps/api/src/app/api-production.composition.ts:2963-2990` — passes `prisma`,
`resolveClickHouseClient`, `authz`, `projects`, `plans`, `dataRetention`,
`topics`, `modelProviders`, `executionProxyBaseUrl`, `filterConditions`,
`ingest` and `processName`, and **no `evaluations`**. The escape hatch built for
exactly this, `connectEvaluations` (`trace-legacy-read.service.ts:373-378`,
docblocked "Completes the intentional Evaluation execution/read cycle at boot"),
has no caller anywhere in the repository.

The sibling reader on the same lines got this right —
`api-trace-read-stack.composition.ts:611` builds `TraceListService` with
`options.evaluations ?? this.refusingEvaluations()`, so the list path degrades by
name. The single-trace path has no such fallback, which is why it throws a plain
`Error` and lands as an unhandled 500.

This is the classic optional-dependency-nobody-supplies shape: the parameter is
optional, production never fills it, and the only signal is a runtime 500 on the
first read.

### F5 — one REST request writes up to 21 identical log lines

Every `request handled` record is emitted many times, same `traceId`, same
millisecond, distinct `spanId`:


16, 19, 20 and 21. Under haven the gateway's own health probe was logged **12
times** per request. The F3 500 above was written three times over.

`loggerMiddleware` is installed at `packages/api/src/rest/builder.ts:308`

mounts it on every family". Log levels are correct (200/204 at INFO, 401 at WARN,
500 at ERROR) — only the multiplicity is wrong. It makes the api log unreadable
and multiplies log volume by an order of magnitude in production.

### F7 — `system.backup_log` collection is on by default and warns on every local boot

```
WARN (langwatch:ops:storage-stats): failed to collect ClickHouse backup stats from
  system.backup_log (further failures suppressed until recovery) {"instance":"shared"}
```

`system.backup_log` does not exist on a ClickHouse that has never taken a backup —
confirmed against the host instance:

```
SELECT count() FROM system.tables WHERE database='system' AND name='backup_log'  →  0
```

The handler at
`packages/features/ops/server/src/services/storage-stats-collection.service.ts:241-252`
justifies warning rather than debugging with "only deployments that opted in
reach here and they care". They did not opt in: `collectsClickHouseBackupMetrics`
(`apps/worker/src/platform/config/worker.config.ts:1479-1490`) returns `true` for
an unset variable, and the type's own comment at line 670 reads "ON unless
deliberately off". The reasoning for the opt-OUT default is sound — live backup
alerts already depend on the gauges — but the comment at the log site describes
the opposite policy, so every stock local worker warns for a table it was never
going to find. Either the comment is wrong or the warning should be a debug on an
absent table.

### F8 — the OpenAPI document publishes a route this process deliberately does not mount

`GET /api/traces/{traceId}/transcript` appears in the live
`/api/openapi.json` (190 paths) and answers Hono's unmatched-route `404 Not
Found` — byte-identical to what `/api/definitely-not-a-route` returns.

The absence is deliberate and well argued:
`packages/features/trace/server/src/transport/api-rest/traces.api.ts:438-441`
registers the route only `if (readCodingAgentTranscript)`, and
`apps/api/src/features/trace/trace-rest.mount.ts:143-158` explains at length why
this process supplies no such port — the canonical log read it depends on is
refused by `composeApiTraceReadStack`, so the derivation would answer an empty
transcript for every trace ingested since the cutover, and "the route is left
unregistered and answers 404 instead."

The gap is that the *document* does not know. A route conditional at mount time
is unconditional in the published spec, so a customer generating a client from
it gets a method that 404s with no explanation. Minor, and the fix belongs with
whoever owns `openapi-document.checker.ts`.
