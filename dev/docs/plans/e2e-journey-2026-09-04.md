# Defects the browser product journey hit — 2026-09-04

Branch `feat/strict-feature-layout-v0`. Recorded by the Suite A lane of
[`e2e-platform-plan-2026-09-04.md`](e2e-platform-plan-2026-09-04.md) while
building `dev/tests/agentic-e2e/tests/journey/product-journey.spec.ts` and
running it against a stack on port 5600.

Each entry names the request, the status the product gave, and the file:line
that decides it. Nothing here was fixed by the lane: its remit stops at adding
an accessible name or a test id in the owning web package.

## D1 — the Prompt Studio crashes to the error boundary on load

Request: open `/{project}/prompts` as a signed-in member of a fresh project.
Status: the page renders "Something went wrong" instead of the studio, so a
prompt cannot be created from the browser at all.

The boundary shows the cause:

```
Error: Maximum update depth exceeded. This can happen when a component repeatedly
calls setState inside componentWillUpdate or componentDidUpdate.
  at forceStoreRerender (react-dom_client.js)
  at updateStoreInstance (react-dom_client.js)
```

and the ui lane names the component:

```
The above error occurred in the <PublishedPromptsList> component.
```

`packages/features/prompt/web/src/screens/prompt-studio/sidebar/published-prompts-list.tsx:19`

```ts
const { addTab } = useDraggableTabsBrowserStore(({ addTab }) => ({ addTab }));
```

The selector builds a **new object on every call**. `useSyncExternalStore`
compares snapshots by reference, so every store read is a change, and the
component re-renders until React gives up. Selecting the member itself —
`useDraggableTabsBrowserStore((state) => state.addTab)` — returns the same
function reference each time and ends the loop.

The journey's ported prompt leg fails with this reason by name rather than
working around it, and it runs last so nothing after it is blocked:
`product-journey.spec.ts`, scenario "Creating a workflow and a prompt from the
product surfaces".

## D2 — the workflow create dialog's submit button reads `Create StudioWorkflow`

Request: click the submit button of the "Create new workflow" dialog.
Status: the button works; its label names an internal type.

`packages/features/workflow/web/src/ui/sections/workflow-create-dialog-host.tsx:200`
renders `Create StudioWorkflow`, while the dialog heading one file over reads
`Create new workflow`
(`packages/features/workflow/web/src/ui/elements/workflow-create-dialog.tsx:207`).
The shape is a rename that swept the copy along with the type
(`Workflow` → `StudioWorkflow`), and user-facing copy that names an
implementation detail is what `dev/docs/best_practices/copywriting.md` forbids.

The journey matches `/^create (studio)?workflow$/i`, so the leg is not blocked
by it; the alternation comes out the day the label is fixed.

## D3 — a run's refusal reason is reachable only by hovering a disabled control

Request: open a run dialog on a project with no agent and read why the run is
refused.
Status: the reason exists and is correct, and only a mouse can get at it.

`runBlockedReason` produces `Choose an agent to run against.`
(`packages/features/scenario/web/src/ui/sections/agent-testing/run/run-dialog.tsx:81`),
and the footer renders it **only** as the tooltip of the disabled run button
(`.../run/run-dialog-footer.tsx:87-95`). A disabled button is not focusable, so
there is no keyboard route to the tooltip and a screen reader is never told why
the primary action is refused. The dialog does show the `run-dialog-setup-agent`
box beside it, which is the visual hint, but the sentence itself is
mouse-only.

Related, and the reason this scenario is the journey's last leg: the target
picker has no way to **un**-choose an agent —
`.../run/run-target-picker.tsx:173` wires `onClick` to `onSelect` and nothing
else — so a project that holds one agent can never show this refusal. The
journey deletes the project's agents first, which is the only route to it.

## D4 — the api process cannot boot while `app-trpc` is mid-refactor

Request: `GET /api/trpc/publicEnv` through the ui lane.
Status: `502`, because the api process exits on boot.

```
[langwatch:api] fatal boot failure: Cannot read properties of undefined (reading 'router')
  at createAppTrpcFeatures (apps/api/src/app-trpc/app-trpc.features.ts:684:23)
  at ApiTrpcFeaturesComposition.build (apps/api/src/app/api-trpc-features.composition.ts:276:12)
```

`app-trpc.features.ts:684` reads `composed.ops.router(mount)`; the member is
declared on the type (`apps/api/src/app-trpc/app-trpc.composed.ts:24`) and
`api-trpc-features.composition.ts` names `ops` only in a key union (`:353`),
with nothing building it. That is the half-landed shape a concurrent edit
leaves behind, and it recurred repeatedly during this lane while those files
were being written by another agent.

Recorded rather than fixed: `apps/api/src/app-trpc` and `apps/api/src/app` are
outside this lane's remit. Any run of the journey against a worktree in that
state fails in global setup, before the first test. The lane worked around it
by running the api and worker from their non-watch `start` scripts, which load
their source once.

The milder form of the same hazard is a lane restart mid-run rather than a
crash. Over the final runs, edits to `packages/api/src/rest/route-mounting.ts`
and then `packages/api/src/rest/v1-alias.ts` (twice in thirty seconds)
restarted the api and worker lanes, and the walk was bounced to
`/auth/signin?callbackUrl=/onboarding/product?projectSlug=journey-org-…` with
its organization and project already created. The suite now signs back in when
it finds itself on the sign-in page and carries on, which is what a person
would do.

## D5 — no model provider in this shell, so five legs skip

Request: run the model-provider, monitor, run, verdict and trace legs.
Status: skipped with the named reason `OPENAI_API_KEY not set`.

Not a product defect. The lane reads only `process.env`, and this shell carries
no `OPENAI_API_KEY`. It is recorded because the platform's behaviour behind it
is deliberate and worth stating: a self-hosted organization gets **no** provider
from the environment
(`packages/features/model-provider/server/src/adapters/registry.model-provider-catalog.adapter.ts:111-117`),
so those five legs cannot be made to pass without a real key on the shell that
runs the suite.
