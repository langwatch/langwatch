## D1 — the Prompt Studio crashes to the error boundary on load — FIXED

Request: open `/{project}/prompts` as a signed-in member of a fresh project.
Status: the page renders "Something went wrong" instead of the studio, so a
prompt cannot be created from the browser at all.

The boundary shows the cause:

```
Error: Maximum update depth exceeded. This can happen when a component repeatedly
calls setState inside componentWillUpdate or componentDidUpdate.
  at forceStoreRerender (react-dom_client.js)
  at updateStoreInstance (react-dom_client.js)
```

and the ui lane names the component:

```
The above error occurred in the <PublishedPromptsList> component.
```

`packages/features/prompt/web/src/screens/prompt-studio/sidebar/published-prompts-list.tsx:19`

```ts
const { addTab } = useDraggableTabsBrowserStore(({ addTab }) => ({ addTab }));
```

The selector builds a **new object on every call**. `useSyncExternalStore`
compares snapshots by reference, so every store read is a change, and the
component re-renders until React gives up. Selecting the member itself —
`useDraggableTabsBrowserStore((state) => state.addTab)` — returns the same
function reference each time and ends the loop.

Fixed: the list selects the member itself, and
`published-prompts-list.integration.test.tsx` renders it against the real tab
store and holds it to one render across a store update. The journey's prompt
leg no longer carries the crash guard it reported this through.

## D6 — the api process does not parse, so no stack can boot

Request: start the api lane.
Status: it exits on boot before it binds, so `GET /api/health` never answers and
the whole stack is unusable.

```
Error: Transform failed with 1 error:
apps/api/src/app/api-trpc-features.composition.ts:76:6: ERROR: Unexpected ">"
```

The type is valid TypeScript and `tsc` accepts it; the parser that runs at boot
does not. `apps/api/src/app/api-trpc-features.composition.ts:65-77` writes the
collaborators member as a leading-`|` union whose first arm is a generic with a
**trailing comma** in its type-argument list:

```ts
  collaborators:
    | ApiTrpcCollaborators<
        …,
        TWorkbenchState,     // ← this comma
      >
    | undefined;
```

Reduced to the smallest case that reproduces it, against the same esbuild the
`tsx` loader uses (0.28.1):

```
type A = Readonly<{ c: | B<X, Y,> | undefined }>;   →  Unexpected ">"
type A = Readonly<{ c: | B<X, Y> | undefined }>;    →  parses
```

So the trailing comma is what esbuild refuses, and only in this shape. Dropping
that one comma is the whole fix. Left to the owner: `apps/api/src/app` is
outside this lane's remit, and this is the reason the journey could not be run
end to end after the refactor landed.

`/api/traces/search`) with a project key, while the local ClickHouse accepted

`WriteBufferFromHTTPServerResponse::cancelWithException` in its error log). The
absence of a deadline is not.

## D11 — "Create Online Evaluation" is intermittently inert, and silent about it

**Status:** open, intermittent (roughly one run in two).

**Request:** browser, New Online Evaluation drawer, trace level, a code

**Evidence.** At the moment of the click the button is genuinely enabled —
`{"disabled":false,"aria":null,"dataDisabled":null}` — so this is not the
aria-disabled refusal of D3. The api log for a failing run carries every other
mutation of the walk (`user.register`, `onboarding.initializeOrganization`,
`modelProvider.update`, `agents.create`, `evaluators.create`) and no
`monitors.create`, so the click reaches `handleSave` and `handleSave` returns.

`packages/features/evaluator/web/src/ui/sections/evaluations/online-evaluation-drawer.tsx`
guards the same click twice, and the two guards are not the same:

```
:872  if (!selectedEvaluator || !project?.id || !name.trim()) return;
:874  if (hasPendingMappings) return;
:944  const canSave = !!level && !!selectedEvaluator && !!name.trim() && !isLoading && !hasPendingMappings;
```

`canSave` renders the button; `handleSave` decides whether to act. Their only
difference is `project?.id`, which `canSave` never checks — so whenever the
callback sees no project (or a stale closure over `name` / `hasPendingMappings`),
the product offers an enabled button that does nothing and says nothing. Whatever
the underlying race, the two conditions should be one, and a refusal a customer
can act on should say so.

**Journey impact.** `creates an online evaluation that runs the evaluator on
every trace` fails on it about half the time; the walk is serial, so the legs
behind it do not run on those runs. The walk clicks up to five times and reports
the button's own state in the failure rather than forcing anything.

## D19 — the worker's outbox drain cannot start a transaction, so ingestion stalls

Request: post a span with the SDK against a stack booted from the current tree
(`bash dev/scripts/dev-stack.sh` with `PORT=5610`), then read it back.
Status: `GET /api/v1/trace/{traceId}` answers `404 Trace not found.` for as long
as anything waits — three minutes in the suite, and still 404 after. Earlier the
same span was searchable two seconds after `shutdown()`.

The worker says why, at WARN, over and over:

```
[23:01:58.171] WARN (langwatch:event-sourcing:process-runtime):
  ProcessOutboxWorker drain failed; the next poll will retry
  error: PrismaClientKnownRequestError
    "Transaction API error: Unable to start a transaction in the given time."
```

118 of those in the first four minutes of a **freshly booted** stack, so it is
not a backlog this machine had accumulated: a stack that has just come up cannot
drain its own outbox. Postgres is not the constraint — `pg_stat_activity` shows
20 idle connections, one active, `max(now() - xact_start)` of zero and no
ungranted locks — so nothing is holding a transaction open; the wait is on the
client's own pool.

What it costs a suite: every leg that reads what it wrote through the pipeline
fails on time rather than on behaviour — traces (01), the evaluation on a span
(02), the simulation run (05) and the experiment run (06) — while everything
served straight from Postgres (prompts, datasets, evaluators, scenarios, test
suites, agents, the management families, every CLI leg) passes. Raising the
suite's own budget to three minutes (`E2E_POLL_TIMEOUT=180000`) changed nothing,
which is what separates this from a slow machine.

Reproduction:

1. `bash dev/scripts/dev-stack.sh` with `PORT=5610`, wait for `/api/health`.
2. Record one span with the SDK and `await handle.shutdown()`.
3. `grep "drain failed" ` the worker lane — the first failures land within a
   minute of boot.
4. `GET /api/v1/trace/{traceId}` stays 404.

Left to the owner: the event-sourcing runtime and the worker's Prisma pool sizing
are outside this lane's remit. It is recorded because it is what the SDK
journey's four ingest-dependent legs are red on today, and because a permanently
stalled pipeline announces itself only at WARN.
