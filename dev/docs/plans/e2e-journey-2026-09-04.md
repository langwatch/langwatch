## D1 — the Prompt Studio crashes to the error boundary on load — FIXED

Request: open `/{project}/prompts` as a signed-in member of a fresh project.
Status: the page renders "Something went wrong" instead of the studio, so a
prompt cannot be created from the browser at all.

The boundary shows the cause:

```
Error: Maximum update depth exceeded. This can happen when a component repeatedly
calls setState inside componentWillUpdate or componentDidUpdate.
  at forceStoreRerender (react-dom_client.js)
  at updateStoreInstance (react-dom_client.js)
```

and the ui lane names the component:

```
The above error occurred in the <PublishedPromptsList> component.
```

`packages/features/prompt/web/src/screens/prompt-studio/sidebar/published-prompts-list.tsx:19`

```ts
const { addTab } = useDraggableTabsBrowserStore(({ addTab }) => ({ addTab }));
```

The selector builds a **new object on every call**. `useSyncExternalStore`
compares snapshots by reference, so every store read is a change, and the
component re-renders until React gives up. Selecting the member itself —
`useDraggableTabsBrowserStore((state) => state.addTab)` — returns the same
function reference each time and ends the loop.

Fixed: the list selects the member itself, and
`published-prompts-list.integration.test.tsx` renders it against the real tab
store and holds it to one render across a store update. The journey's prompt
leg no longer carries the crash guard it reported this through.

## D3 — a run's refusal reason is reachable only by hovering a disabled control — FIXED

Request: open a run dialog on a project with no agent and read why the run is
refused.
Status: the reason exists and is correct, and only a mouse can get at it.

`runBlockedReason` produces `Choose an agent to run against.`
(`packages/features/scenario/web/src/ui/sections/agent-testing/run/run-dialog.tsx:81`),
and the footer renders it **only** as the tooltip of the disabled run button
(`.../run/run-dialog-footer.tsx:87-95`). A disabled button is not focusable, so
there is no keyboard route to the tooltip and a screen reader is never told why
the primary action is refused. The dialog does show the `run-dialog-setup-agent`
box beside it, which is the visual hint, but the sentence itself is
mouse-only.

Fixed: the footer prints the reason beside the refused control and names it on
the button through `aria-describedby`, so the tooltip is gone and the sentence
is read the same way with a mouse, a keyboard or a screen reader. The journey
asserts the visible sentence rather than staging a real mouse move.

Related, and the reason this scenario is the journey's last leg: the target
picker has no way to **un**-choose an agent —
`.../run/run-target-picker.tsx:173` wires `onClick` to `onSelect` and nothing
else — so a project that holds one agent can never show this refusal. The
journey deletes the project's agents first, which is the only route to it.

## D6 — the api process does not parse, so no stack can boot

Request: start the api lane.
Status: it exits on boot before it binds, so `GET /api/health` never answers and
the whole stack is unusable.

```
Error: Transform failed with 1 error:
apps/api/src/app/api-trpc-features.composition.ts:76:6: ERROR: Unexpected ">"
```

The type is valid TypeScript and `tsc` accepts it; the parser that runs at boot
does not. `apps/api/src/app/api-trpc-features.composition.ts:65-77` writes the
collaborators member as a leading-`|` union whose first arm is a generic with a
**trailing comma** in its type-argument list:

```ts
  collaborators:
    | ApiTrpcCollaborators<
        …,
        TWorkbenchState,     // ← this comma
      >
    | undefined;
```

Reduced to the smallest case that reproduces it, against the same esbuild the
`tsx` loader uses (0.28.1):

```
type A = Readonly<{ c: | B<X, Y,> | undefined }>;   →  Unexpected ">"
type A = Readonly<{ c: | B<X, Y> | undefined }>;    →  parses
```

So the trailing comma is what esbuild refuses, and only in this shape. Dropping
that one comma is the whole fix. Left to the owner: `apps/api/src/app` is
outside this lane's remit, and this is the reason the journey could not be run
end to end after the refactor landed.

## D7 — Picking a provider from "Add Model Provider" throws, so no provider can be added

**Status:** open, blocks the journey from leg 4 onward.

**Request:** browser, `/settings/model-providers` on a fresh organization.

**Reproduction**

1. Sign up, finish onboarding, open **Settings → Model Providers**.
2. Click **Add Model Provider** and pick **OpenAI** in the menu.
3. Nothing opens. The menu stays open and the console carries:

```
TypeError: Cannot read properties of undefined (reading 'write')
  at setQuery              apps/ui/src/behavior/ui-router-navigation.ts:71
  at openPlatformDrawer    apps/ui/src/features/model-provider/behavior/model-provider-open-platform-drawer.ts:34
  at openPlatformDrawer    apps/ui/src/features/model-provider/ui/sections/model-provider-host.tsx:99
  at openProviderEditor    packages/features/model-provider/web/src/screens/model-provider/model-providers.screen.tsx:214
```

**Evidence.** `apps/ui/src/features/model-provider/ui/sections/model-provider-host.tsx:104`
hands `openPlatformDrawer` the method itself:

```ts
          setQuery: route.setQuery,
```

`RouterUiRoute.setQuery` calls `this.write(next, options)`
(`apps/ui/src/behavior/ui-router-navigation.ts:71`), so an unbound reference has
no `this` and throws before the address is ever written. Twelve lines earlier the
same host object wraps the same method correctly
(`model-provider-host.tsx:92`: `setQuery: (next, options) => route.setQuery(next, options)`),
which is what the fix looks like. Every model surface in the product depends on
this drawer, so on a fresh organization no model provider can be configured at
all through the UI.

**Journey impact.** `adds OpenAI as a model provider` fails on it, and because
the walk is serial the six legs that need a model behind it never run.

## D7 — a trace read waits for ClickHouse for ever instead of giving up

Request: `GET /api/v1/trace/{traceId}` (and `/api/v1/traces/{traceId}`, and
`/api/traces/search`) with a project key, while the local ClickHouse accepted
TCP connections but answered no HTTP request.

Status: the request never returned. `curl -m 20` gave up three times over
without a status; the SDK's own read (`langwatch.traces.get`) hung until the
test's timeout, which is what turned a broken datastore into "the test is slow"
rather than "the datastore is down".

The api process bounds ClickHouse *concurrency* but not *time* — it logs

```
ClickHouse statement concurrency bounded {"instance":"shared","maxConcurrent":64,"maxQueued":512}
```

on boot, so a wedged server fills the queue and every caller waits behind it
with no deadline. A statement deadline would turn this into a named 503 the
client can act on. Reproduced by restarting the ClickHouse LaunchAgent
(`com.langwatch.clickhouse`), after which the same read answered
`404 {"message":"Trace not found."}` in 0.34 s and a fresh span was searchable
2 s after `shutdown()`.

The trigger was environmental (a ClickHouse wedged since 15:39 with
`WriteBufferFromHTTPServerResponse::cancelWithException` in its error log). The
absence of a deadline is not.
