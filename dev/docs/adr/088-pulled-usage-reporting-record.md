# ADR-088: pulled provider usage is a priced, per-item cost record written to the shared usage ledger under a non-enforcing scope

**Date:** 2026-08-06

**Status:** Accepted

**Relates to:** the shipped event-sourced pull pipeline (`platform/app/ee/event-sourcing/pipelines/ingestion-pull-processing/`), delivered by the June event-sourcing migration that dropped BullMQ and refactored into the one-declaration-per-pipeline model (#6051; restructure #6405). Mirrors the gateway spend pattern in `platform/app/src/server/event-sourcing/pipelines/gateway-spend-processing/` and, critically, the way the **Claude Code OTLP receiver already surfaces ingestion cost** through `gateway_budget_ledger_events` (`platform/app/ee/governance/services/personalUsage.clickhouse.repository.ts`). Depends on the scope-resolution consolidation (#6551). Provider grounding: an internal integration spike (Databricks Genie on Azure) and the audit-table husk finding.

> **One line:** each pulled usage item becomes a **priced, provider-agnostic event**; its cost is written to the **shared usage ledger under a dedicated non-enforcing scope** — the same table the "my usage" screens already read, marked so it shows in reporting but never trips a spending limit — attributed to the customer's real org/team/project, with restatement handled by a **stable-coordinate key that excludes cost**.

**In plain terms.** We pull the record of what a customer already spent directly with a provider, turn each usage chunk into one clean cost record, and put it where their usage screens already look — flagged so it shows up in reports but can never block anything. We keep it correct when the provider revises a number, and we're honest about which numbers are exact and which are estimates.

## Context

The pull framework already shipped and is event-sourced for **orchestration** (cron wake, cursor, run lifecycle). What is not on any stream is the **data**: `RUN_COMPLETED` carries only a count, and the puller effect direct-writes the usage rows and cost into `governance_ocsf_events` (`pullerWorker.ts:211-244`), an audit table, with cost buried in `metadata.extension.cost_usd`. So pulled cost is invisible to every usage screen and unattributed to a real tenant.

**There is no single "spend view" — this is the load-bearing fact.** Three customer-facing cost surfaces each read a *different* physical table:

- Gateway spend/billing → `gateway_spend` (`spendEvents.clickhouse.repository.ts:24`).
- Personal / Claude-Code usage (`/me/usage`) → `gateway_budget_ledger_events` **UNION** `trace_summaries` (`personalUsage.clickhouse.repository.ts`).
- Analytics cost dashboard (`metrics.total_cost`) → `trace_summaries` (`analytics/.../field-mappings.ts:222-225`).

And the pattern for *ingestion* cost already exists: the Claude Code OTLP receiver writes into `gateway_budget_ledger_events`, and `/me/usage` reads that cost through a scope-filtered query (`personalUsage.clickhouse.repository.ts`). So "reporting" and "enforcement" are **not separate tables** — they are the same ledger; enforcement is driven by which rows a *real budget* resolves to, not by a scope flag. Any design that lands pulled cost in a brand-new isolated table is read by nobody and fails its own visibility goal.

**Forcing function.** Databricks Genie on Azure is the first provider we want to connect.

**Locked constraints (Phase 1).** Build on the existing puller — no second pull system. Keep cost as its own clean record (a first-class cost row, not buried in the OCSF audit log). Reuse the existing pricing code.

**The boundary that matters.** Pulled money was spent *outside* our gateway and cannot be blocked; it must never drive enforcement. But — per the shipped Claude Code pattern — "don't enforce" is a **scope on the shared ledger**, not a separate store.

## Decision

**1. One priced event per pulled usage item, keyed by stable provider coordinates.** A provider-agnostic aggregate (`pulled_usage`), one event per usage chunk. The item's identity is the provider's **stable natural key**: for bucketed admin APIs (Anthropic usage/cost report) that is `(tenant, period, granularity, model, workspace, …group-by dims)` — there is no message id; for per-message providers (Genie) it is the message id. We reject bolting usage onto `RUN_COMPLETED` (per-run grain) and reject "aggregateId = message id" as universal (bucket APIs have none — the v1 error the red-team caught).

**2. Price once, at the ingest seam.** The command that mints the event stamps cost as an integer `costNanoUsd` (plus a `rateVersion` for the *computed* path only; `null` when the provider reported an exact cost); downstream copies it, never recomputes (as `gateway-spend-processing/schemas/commands.ts:120-155` does). Where the provider returns an exact cost (Anthropic `cost_report`) we carry it; where it returns only quantities (Anthropic `usage_report` tokens) we price once with `estimateCost()` (`tracer/collector/cost.ts`). The two-ways-to-get-Anthropic-cost seam is handled in Decision 6.

**3. Write cost to the shared usage ledger through a dedicated writer, under a structurally non-enforcing scope `"pulled"`.** Pulled cost is written to `gateway_budget_ledger_events` (the table `/me/usage` already reads) through a **dedicated writer** (`insertPulledUsageRows`) with a constant `Scope = "pulled"` and a **synthetic budget id** (the ledger's storage key requires one). Non-enforcement is **structural, not a flag**: enforcement resolves real `GatewayBudget` rows and sums only ledger rows whose `BudgetId`/`Scope` match a real budget — and no budget can carry `"pulled"` (it is not a `GatewayBudgetScopeType`), so no resolver ever reaches these rows. A **dedicated read** — mirroring the *read* shape of the existing principal-usage query (filter by `Scope`+`ScopeId`+tenant, **not** `BudgetId`) — surfaces pulled cost in `/me/usage`. Pulled rows are **excluded from the spend-rollup materialized view** so they can never leak into a budget total. We reject extending `GatewayBudgetScopeType` (a budget could then be created under `"pulled"`, breaking non-enforcement by construction), a separate isolated rollup table (invisible — the #1 red-team kill), and any enforcing-scope write. *(The earlier draft's `Scope='principal'` analogy was imprecise: principal rows carry real budgets and do enforce; only the read filter is what we mirror.)*

**4. Attribute to the customer's real org/team/project.** `IngestionSource` today carries `organizationId` (required) + `teamId` (optional) but **no `projectId`**, and all writers currently land under the hidden governance project (`pullerWorker.ts:204-208`). So this decision *requires explicit schema work*: (a) add a project scope to `IngestionSource`, and (b) reconcile the hidden-governance-project routing every writer uses. Until (a)+(b) land, attribute at **org/team** (which the model supports today) and treat project as unattributed rather than silently the governance project. Named-person attribution (Genie object-id) is deferred behind #6551.

**5. Corrections are a fresh record; newest wins; the key excludes cost.** A restated bucket is a new event whose identity key is the **stable coordinates from Decision 1 with cost and quantities excluded** — a dimension-only hash (the same shape PostHog's connector uses, and the shape our own research recommended). An unchanged re-pull produces the identical key → no-op; a corrected bucket produces the *same* key with a later **`observedAt`** (the monotonic time we pulled it) → latest-by-`observedAt` replaces. Ordering must be `observedAt`, **not** the bucket's business `occurredAt`: a restatement of period P keeps P's `occurredAt`, so versions cannot be ordered by it. We reject hashing cost into the key (the v1 error: a corrected cost would mint a new key and double-count) and reject relying on storage-engine merge order.

**6. Each record is flagged `exact` or `estimate`, and same-money supersede is a named reconciliation.** Anthropic `cost_report` → `exact`; Anthropic `usage_report`-priced and Databricks DBU → `estimate`. Two reconciliations, both deferred but named here (not Databricks-only, as v1 wrongly implied): (i) an `estimate` trued up to the invoiced number; (ii) the **same Anthropic spend arriving via both `usage_report` and `cost_report`** — per provider we either pull usage XOR cost, or define a supersede rule where `provider_reported` replaces `computed` for the same coordinates. Until a supersede rule ships, a provider adapter pulls **one** of the two, never both.

**7. Provider-agnostic by construction; Databricks is the first adapter.** The event, the ledger scope, and the reconciliation are provider-neutral; the puller's adapter registry already exists. Databricks is the first adapter; the second provider is only an adapter.

*Decisions 8–14 were added in v7 (2026-08-23): pulled Genie conversations additionally route into the trace explorer. Full trade-off record: the planning vault's `Plan Pre-Plan.md` (decisions D1–D12, all locked 2026-08-23; red-team re-asks locked same day). See Revisions.*

**8. (v7) Conversation-bearing pulled events also route through the standard trace door into a customer-chosen destination project.** When a source has a destination set, `writePulledEvents()` (`pullerWorker.ts:269`) additionally calls `handleOtlpTraceRequest` (`platform/app/src/server/app-layer/traces/trace-request-collection.service.ts:115`) — the same entry the OTLP route uses, so validation, dedup, journaling, redaction, and token estimation come for free. **Aggregate pulls never route** (Anthropic usage buckets are counts, not conversations). Provenance rides the existing origin attributes: `langwatch.source = "databricks_genie"` (`ingestKeyProvenance.utils.ts:47`; stamped via `ingestionRoutes.ts` `buildOriginAttrs`/`stampOriginAttrs`). This is deliberately a **second consumer of the same message** — the audit row stays; the single-source question (Open questions) remains open and is tracked separately.

**9. (v7) The destination is one nullable column that grants no access — and every write of it passes the same cross-org guard virtual keys use.** `IngestionSource.traceProjectId String?` — the `VirtualKey.traceProjectId` shape (`platform/app/prisma/schema.prisma:2853-2869`): null means don't route; a destination is **not** a scope row and confers no access to the source. Freely editable at any time, exactly as virtual keys do it (`virtualKey.service.ts:1050-1065`: untouched stays, named re-validated as create would, null re-derives; no lock). *Refuter correction:* the virtual-key precedent works because of a guard the plan never named — `assertTraceProjectBelongsToOrg` (`platform/app/src/server/gateway/virtualKey.authz.ts:397-409`, "a stray id would route another tenant's costs") — and the puller writes with a service-level Prisma client, so nothing downstream would catch a foreign-org id. The equivalent check is **required at IngestionSource create/update**, with a test asserting a foreign-org `traceProjectId` is rejected at write time. A destination later archived or deleted stops routing (skip + surface on the source screen, the `traceProjectFor` precedent — `scopeResolver.ts:219-240`) rather than failing the run or silently landing elsewhere. Routed history does not move on edit — migrating old traces to a new destination is deferred. **This column is not Decision 4's cost-attribution `projectId`** — pulled cost attribution stays org/team; the two must not be conflated.

**10. (v7) Trace identity is deterministic; a regenerated answer is a new attempt entry; order is `created_timestamp`.** Trace ids hash **`ingestion_source_id`** + `conversation_id` + `message_id`; span ids hash the same **plus `auto_regenerate_count`**; thread id = `ingestion_source_id` + `conversation_id`. The source namespace is not decoration: provider ids are unique within a Genie **workspace**, and one destination project can receive pulls from several sources, so an unqualified seed bets on two independent identifier domains never meeting — and loses silently in both directions (equal span ids dedupe the second source's conversation away permanently; an equal thread id interleaves two workspaces' turns into one rendered conversation). *Refuter correction:* the original "last-write-wins" was impossible — the event store is **first-write-wins** (`idempotencyKey = tenant:trace:span`, `eventStoreUtils.ts:120-137` keeps the first occurrence), so a regenerated answer re-sent under a content-stable span id would be silently discarded, the exact opposite of the intent. With the attempt count in the id, a regenerated answer lands as its **own span beside the original's** — and the conversation bubble shows the **latest** attempt for free: among multiple parentless spans in one trace, the latest-finishing root wins the trace output (`shouldOverrideOutput`, `trace-io-accumulation.service.ts:44-75`), so the current answer is the one rendered while prior attempts stay inspectable as spans; further attempt-collapse UI is polish, deferred. An unchanged re-pull stays a **durable** no-op through that same first-write idempotency — the Redis dedup gate (`span-dedupe.service.ts`: 1-hour TTL, fails open when Redis is down) is only a fast path, never the guarantee. Turn ordering is `created_timestamp` with `message_id` as tie-break: the API exposes no sequence field, and `last_updated_timestamp` moves on regeneration.

**11. (v7) The 31-day door stays; the door alone enforces it — the walk is untouched.** The door already rejects spans older than `SPAN_MAX_PAST_MS` (31 days — `trace-request-collection.service.ts:30`, enforced `:340`). *Review correction (2026-08-23):* the first draft mandated the walk skip old messages before fetching to save its 400-request budget (`databricksGenie.puller.ts:91`) — that mechanism was wrong: the walk serves the **audit ledger first**, which has no 31-day door and must keep every message the cursor admits, and routing rides the already-fetched events at **zero additional HTTP cost**. Skipping the fetch would silently drop audit rows to optimize a budget routing never spends. So: old messages (stale-cursor resume, deep `startFrom`) are still fetched and audited; the mapper maps them; the trace door drops their spans and the worker logs the rejected count. The UI states the promise in one sentence: "conversations from the last 31 days." A consequence to state plainly: a conversation thread that *started* more than 31 days ago renders partially — only the turns inside the horizon appear, older turns are dropped at the door, not stored. Widening to a year (door exemption + one-off backfill walk + destination-retention cap) is deferred; the one deferral risk is that Databricks-side Genie retention is unknown (research item).

**12. (v7) Rendering reuses explorer-v2 shapes; tokens are estimated; cost is never written to the trace.** The mapping (all counts from the 35-message capture): user bubble ← `content`; assistant bubble ← the `text` attachment with purpose `ANSWER` (wire value `TEXT_ATTACHMENT_PURPOSE_ANSWER` — matched by suffix; 35/35, refusals included); thinking block ← `attachments[].query.thoughts[]` (wire shape: `thought_type` key, enum-prefixed values `THOUGHT_TYPE_*`, text under `content`) flattened `UNDERSTANDING → DATA_SOURCING → STEPS` into the payload field the transcript parser already reads (`conversationView/ChatTurnRow.tsx:655-663`), with the `DESCRIPTION` thought dropped (byte-identical to `query.description`, 33/33 — it becomes the step-row label instead) and unknown thought types passed through; one step row per `query` attachment (label = `query.description`, body = SQL + `row_count`, **all** statement ids carried); the `viz` pointer (`{query_attachment_id}` only, 21/35) stored as a plain attribute, nothing rendered; `suggested_questions` (35/35) **dropped explicitly** — Genie's offered follow-ups, never something a person said. One UI change: the `TurnSteps` span-name filter (`features/traces-v2/components/TraceDrawer/conversationView/TurnSteps.tsx:21-22`) gains Genie's span name. **Tokens:** Databricks exposes no counts (verified in capture), so the answer span is typed `llm` and the existing estimator (`span-token-estimation.service.ts`) counts the text and stamps `langwatch.tokens.estimated = true` — generic tokenizer, since Genie's model is hidden; approximate on purpose and marked as such. The puller's literal zero token fields are dropped by the mapper, not copied. **Cost:** absent from the trace — Genie inference is `GENIE_FREE_USAGE` (v6 scope-out) and warehouse dollars live in the ledger, which restates itself; a dollar written onto a trace goes stale at the first correction. If the explorer ever shows dollars it looks them up at display time by statement id (`shareOf()` — `databricksWarehouseCost.ts:382`); the join key is stored from day one.

**13. (v7) Author is the raw numeric `user_id`; the destination project's redaction policy applies; failure degrades defensively.** The author is written as a string attribute carrying the provider's numeric id, nothing more; the person is resolved at **read time** by the identity stack (ADR-094; `ACTOR_ID_KIND_BY_PROVIDER` declares `databricks: "numeric_id"`), so a fixed link heals every past trace. No SCIM call at pull time — it would bake a resolution into an immutable trace and disagree with the audit row the identity branch writes. **Redaction:** the destination project's policy governs — but *not* by the mechanism first drafted. *Refuter correction:* every existing `handleOtlpTraceRequest` call site passes `DEFAULT_PII_REDACTION_LEVEL` (`"ESSENTIAL"`, `trace-processing/schemas/commands.ts:18`) and the real per-project enforcement happens **inside** the pipeline: `redactSpan` resolves the destination's cascaded data-privacy policy by tenant id (`span-pii-redaction.service.ts:231-261` → `getResolvedForProject`), and an explicit policy level always wins over the request level (`reconcilePiiLevel` `:164-170`). At the *essential* tier, however, a caller-passed level has **unchecked authority** — so the puller must never compute one. The routing call passes the destination project id as tenant plus the same `DEFAULT_PII_REDACTION_LEVEL` as every sibling, and the pipeline's own lookup is the sole source of truth. *Review correction (2026-08-23):* the mandated test was first worded as "hostile caller level → still not stored unredacted" — unsatisfiable: at the essential tier `reconcilePiiLevel` honors the caller's level **by design** (a `DISABLED` request level skips redaction, `span-pii-redaction.service.ts:164-170`), so the pipeline cannot defend there. The true, testable invariant is the caller side: the routing worker never computes a level and always passes `DEFAULT_PII_REDACTION_LEVEL` with the destination project id — pinned by unit test on `routeConversationsToTraceDestination`. The strict-policy case was never at risk (an explicit rule always wins). The source screen states the inheritance in one line. **Failure:** the mapping is defensive — unknown status or missing attachments still renders the user's question with a failure marker, never a false success; all 35 captured messages are `COMPLETED`, so the failure path is pinned by a synthetic fixture until a real one is captured. Per-message skip-and-count in the puller is deferred: today a poison message stalls its source via whole-window retry (`pullerWorker.ts:65-66`) but loses nothing — the cursor holds and a later pull catches up.

**14. (v7) Routed traces are first-class downstream — deliberately, and stated out loud.** The red-team confirmed that nothing reading `trace_summaries`/`stored_spans` filters by origin, so routed conversations flow into every consumer. Rather than special-case them, this is locked as the design: **(a) they count** toward plan trace limits, usage stats, usage-limit warnings, and `/me/usage` request counts (`billableEvents.clickhouse.repository.ts:87-107` `uniq(TraceId)`, no origin filter) — a routed conversation is a real trace consuming real ingestion and storage; how routed conversations are *monetized* is an open product question, deferred. **(b) They trigger** the destination project's monitors and evaluators like any other trace — a customer routing into a dedicated project controls exactly what evaluates there, and scoring Genie answers may be the point. **(c) Estimated tokens blend** into aggregate token dashboards (the estimated flag is per-span; aggregates don't read it) — accepted and documented, not filtered. **(d) Zero cost is a guard, not an accident:** cost enrichment runs unconditionally on `llm` spans and today yields nothing only because Genie's span carries no model attribute matching a price row; a fixture test pins that routed spans never resolve in the pricing table, turning the accident into an invariant.

## Assumptions

| Assumption | What breaks if false |
|---|---|
| One writer produces each usage record (the pull) | "priced once / newest wins" becomes ambiguous |
| A provider restates a bucket under the **same stable coordinates** | the correction can't match the original; both persist (silent double-count) |
| The tenant boundary is enforced upstream of the ledger write | pulled cost reported under the wrong customer |
| `IngestionSource` can be extended to carry the target project | Decision 4's project attribution has no home (named as required work, not assumed done) |
| *(v7)* `message_id` and `created_timestamp` are stable across re-pulls | dedup breaks → duplicate traces; ordering shuffles between pulls |
| *(v7)* `auto_regenerate_count` increments on every regeneration | a regeneration that keeps the count produces an identical span id → first-write-wins silently drops the new answer |
| *(v7)* A completed message carries an `ANSWER` text attachment (35/35 observed) | assistant bubble empty → defensive failure marker renders instead (degrades, doesn't break) |
| *(v7)* Databricks retains ≥31 days of Genie history | a fresh connection shows less than the UI promises; also the 1-year-widening deferral loses data permanently (research item) |

## Rejected alternatives

- **Separate isolated `pulled_usage_rollup` table** — read by none of the three spend surfaces; invisible. (The #1 red-team kill of v1.)
- **Write under an enforcing scope / debit budgets, or extend `GatewayBudgetScopeType`** — blocks money spent outside the gateway, double-counts gateway users, and (the enum route) lets a budget be created under the pulled scope, breaking non-enforcement by construction.
- **`aggregateId` = message id for all providers** — bucketed admin APIs have no message id.
- **Hash cost into the restatement key** — a corrected cost mints a new key → double-count instead of replace.
- **Report under the hidden governance project** — invisible to the customer.
- **Rely on ReplacingMergeTree merge order for restatement** — stale reads on a money number.
- **A second parallel pull system** — excluded by the Phase-1 constraint.
- *(v7)* **Pull-time SCIM resolution of the author** — bakes a mutable conclusion into an immutable trace and disagrees with the audit row; the read-time identity stack (ADR-094) heals every past trace with one fixed link.
- *(v7)* **Copying the puller's literal zero token counts** — a provider absence is not a measurement; estimate and flag instead.
- *(v7)* **Rendering the `DESCRIPTION` thought** — byte-identical duplicate of `query.description` (33/33); it becomes the step label, rendering it twice is noise.
- *(v7)* **Rendering the `viz` attachment** — it carries a pointer, not chart data; whether a chart is retrievable by that id is unproven (research item).
- *(v7)* **Widening the 31-day door now** — needs a door exemption, a one-off backfill walk, and a destination-retention cap, against an unknown provider retention window; deferred (Decision 11).
- *(v7)* **Per-message skip in the puller now** — deferred: defensive mapping makes odd messages non-poison, the retrofit is a mapping-loop change plus one field on the Completed event, and the interim cost (a true poison message stalls one source, loses nothing) is bounded.
- *(v7)* **A parallel render path off the audit table** — the audit copy is single-copy and not journal-backed; the trace door gives validation, dedup, journaling, redaction, and estimation for free.
- *(v7)* **A dollar written onto the trace** — goes stale at the first ledger restatement; one number, one owner (the ledger), display-time lookup by statement id if ever needed.

## Consequences

**Positive.** Pulled cost becomes visible in the screens customers already use (via the ledger they already read), attributed to org/team, correct under restatement, honest about exact-vs-estimate. Provider-agnostic — the second provider is an adapter. Reuses the shipped Claude Code ingestion-cost pattern rather than inventing one.

**Negative.** Pulled cost never drives enforcement (by design). Real-*project* attribution and both reconciliations (invoice true-up; Anthropic usage↔cost supersede) are named follow-ups, not in v1. Pulled + gateway cannot be safely summed into one "total AI spend" where the provider admin API omits a request id — a real, stated limit.

**Neutral.** The OCSF audit write is untouched by this ADR, but keeping it *and* the new event means two writers of the same data — see Open questions.

*(v7)* **Positive.** Genie conversations become readable where conversations are read — the trace explorer — through the existing door, journal-backed and rebuildable from day one, with one schema column as the entire new surface. **Negative.** The author renders as a bare numeric id until the identity stack (ADR-094) lands; token counts are estimates from a generic tokenizer, marked as such; routing deliberately writes a *second* copy of each message (audit row + trace spans) while the single-source question stays open; a poison message stalls its source until per-message skip ships. **Neutral.** The 31-day horizon is the door's existing rule kept on purpose, not a new restriction.
