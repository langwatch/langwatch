# ADR-088: pulled provider usage is a priced, per-item cost record written to the shared usage ledger under a non-enforcing scope

**Date:** 2026-08-06

**Status:** Accepted

**Relates to:** the shipped event-sourced pull pipeline (`platform/app/ee/event-sourcing/pipelines/ingestion-pull-processing/`), delivered by the June event-sourcing migration that dropped BullMQ and refactored into the one-declaration-per-pipeline model (#6051; restructure #6405). Mirrors the gateway spend pattern in `platform/app/src/server/event-sourcing/pipelines/gateway-spend-processing/` and, critically, the way the **Claude Code OTLP receiver already surfaces ingestion cost** through `gateway_budget_ledger_events` (`platform/app/ee/governance/services/personalUsage.clickhouse.repository.ts`). Depends on the scope-resolution consolidation (#6551). Provider grounding: an internal integration spike (Databricks Genie on Azure) and the audit-table husk finding.

> **One line:** each pulled usage item becomes a **priced, provider-agnostic event**; its cost is written to the **shared usage ledger under a dedicated non-enforcing scope** — the same table the "my usage" screens already read, marked so it shows in reporting but never trips a spending limit — attributed to the customer's real org/team/project, with restatement handled by a **stable-coordinate key that excludes cost**.

**In plain terms.** We pull the record of what a customer already spent directly with a provider, turn each usage chunk into one clean cost record, and put it where their usage screens already look — flagged so it shows up in reports but can never block anything. We keep it correct when the provider revises a number, and we're honest about which numbers are exact and which are estimates.

## Context

The pull framework already shipped and is event-sourced for **orchestration** (cron wake, cursor, run lifecycle). What is not on any stream is the **data**: `RUN_COMPLETED` carries only a count, and the puller effect direct-writes the usage rows and cost into `governance_ocsf_events` (`pullerWorker.ts:211-244`), an audit table, with cost buried in `metadata.extension.cost_usd`. So pulled cost is invisible to every usage screen and unattributed to a real tenant.

**There is no single "spend view" — this is the load-bearing fact.** Three customer-facing cost surfaces each read a *different* physical table:

- Gateway spend/billing → `gateway_spend` (`spendEvents.clickhouse.repository.ts:24`).
- Personal / Claude-Code usage (`/me/usage`) → `gateway_budget_ledger_events` **UNION** `trace_summaries` (`personalUsage.clickhouse.repository.ts`).
- Analytics cost dashboard (`metrics.total_cost`) → `trace_summaries` (`analytics/.../field-mappings.ts:222-225`).

And the pattern for *ingestion* cost already exists: the Claude Code OTLP receiver writes into `gateway_budget_ledger_events`, and `/me/usage` reads that cost through a scope-filtered query (`personalUsage.clickhouse.repository.ts`). So "reporting" and "enforcement" are **not separate tables** — they are the same ledger; enforcement is driven by which rows a *real budget* resolves to, not by a scope flag. Any design that lands pulled cost in a brand-new isolated table is read by nobody and fails its own visibility goal.

**Forcing function.** Databricks Genie on Azure is the first provider we want to connect.

**Locked constraints (Phase 1).** Build on the existing puller — no second pull system. Keep cost as its own clean record (a first-class cost row, not buried in the OCSF audit log). Reuse the existing pricing code.

**The boundary that matters.** Pulled money was spent *outside* our gateway and cannot be blocked; it must never drive enforcement. But — per the shipped Claude Code pattern — "don't enforce" is a **scope on the shared ledger**, not a separate store.

## Decision

**1. One priced event per pulled usage item, keyed by stable provider coordinates.** A provider-agnostic aggregate (`pulled_usage`), one event per usage chunk. The item's identity is the provider's **stable natural key**: for bucketed admin APIs (Anthropic usage/cost report) that is `(tenant, period, granularity, model, workspace, …group-by dims)` — there is no message id; for per-message providers (Genie) it is the message id. We reject bolting usage onto `RUN_COMPLETED` (per-run grain) and reject "aggregateId = message id" as universal (bucket APIs have none — the v1 error the red-team caught).

**2. Price once, at the ingest seam.** The command that mints the event stamps cost as an integer `costNanoUsd` (plus a `rateVersion` for the *computed* path only; `null` when the provider reported an exact cost); downstream copies it, never recomputes (as `gateway-spend-processing/schemas/commands.ts:120-155` does). Where the provider returns an exact cost (Anthropic `cost_report`) we carry it; where it returns only quantities (Anthropic `usage_report` tokens) we price once with `estimateCost()` (`tracer/collector/cost.ts`). The two-ways-to-get-Anthropic-cost seam is handled in Decision 6.

**3. Write cost to the shared usage ledger through a dedicated writer, under a structurally non-enforcing scope `"pulled"`.** Pulled cost is written to `gateway_budget_ledger_events` (the table `/me/usage` already reads) through a **dedicated writer** (`insertPulledUsageRows`) with a constant `Scope = "pulled"` and a **synthetic budget id** (the ledger's storage key requires one). Non-enforcement is **structural, not a flag**: enforcement resolves real `GatewayBudget` rows and sums only ledger rows whose `BudgetId`/`Scope` match a real budget — and no budget can carry `"pulled"` (it is not a `GatewayBudgetScopeType`), so no resolver ever reaches these rows. A **dedicated read** — mirroring the *read* shape of the existing principal-usage query (filter by `Scope`+`ScopeId`+tenant, **not** `BudgetId`) — surfaces pulled cost in `/me/usage`. Pulled rows are **excluded from the spend-rollup materialized view** so they can never leak into a budget total. We reject extending `GatewayBudgetScopeType` (a budget could then be created under `"pulled"`, breaking non-enforcement by construction), a separate isolated rollup table (invisible — the #1 red-team kill), and any enforcing-scope write. *(The earlier draft's `Scope='principal'` analogy was imprecise: principal rows carry real budgets and do enforce; only the read filter is what we mirror.)*

**4. Attribute to the customer's real org/team/project.** `IngestionSource` today carries `organizationId` (required) + `teamId` (optional) but **no `projectId`**, and all writers currently land under the hidden governance project (`pullerWorker.ts:204-208`). So this decision *requires explicit schema work*: (a) add a project scope to `IngestionSource`, and (b) reconcile the hidden-governance-project routing every writer uses. Until (a)+(b) land, attribute at **org/team** (which the model supports today) and treat project as unattributed rather than silently the governance project. Named-person attribution (Genie object-id) is deferred behind #6551.

**5. Corrections are a fresh record; newest wins; the key excludes cost.** A restated bucket is a new event whose identity key is the **stable coordinates from Decision 1 with cost and quantities excluded** — a dimension-only hash (the same shape PostHog's connector uses, and the shape our own research recommended). An unchanged re-pull produces the identical key → no-op; a corrected bucket produces the *same* key with a later **`observedAt`** (the monotonic time we pulled it) → latest-by-`observedAt` replaces. Ordering must be `observedAt`, **not** the bucket's business `occurredAt`: a restatement of period P keeps P's `occurredAt`, so versions cannot be ordered by it. We reject hashing cost into the key (the v1 error: a corrected cost would mint a new key and double-count) and reject relying on storage-engine merge order.

**6. Each record is flagged `exact` or `estimate`, and same-money supersede is a named reconciliation.** Anthropic `cost_report` → `exact`; Anthropic `usage_report`-priced and Databricks DBU → `estimate`. Two reconciliations, both deferred but named here (not Databricks-only, as v1 wrongly implied): (i) an `estimate` trued up to the invoiced number; (ii) the **same Anthropic spend arriving via both `usage_report` and `cost_report`** — per provider we either pull usage XOR cost, or define a supersede rule where `provider_reported` replaces `computed` for the same coordinates. Until a supersede rule ships, a provider adapter pulls **one** of the two, never both.

**7. Provider-agnostic by construction; Databricks is the first adapter.** The event, the ledger scope, and the reconciliation are provider-neutral; the puller's adapter registry already exists. Databricks is the first adapter; the second provider is only an adapter.

**8. (v7) Conversation-bearing pulled events also route through the standard trace door into a customer-chosen destination project.** When a source has a destination set, `writePulledEvents()` (`pullerWorker.ts:269`) additionally calls `handleOtlpTraceRequest` (`platform/app/src/server/app-layer/traces/trace-request-collection.service.ts:115`) — the same entry the OTLP route uses, so validation, dedup, journaling, redaction, and token estimation come for free. **Aggregate pulls never route** (Anthropic usage buckets are counts, not conversations). Provenance rides the existing origin attributes: `langwatch.source = "databricks_genie"` (`ingestKeyProvenance.utils.ts:47`; stamped via `ingestionRoutes.ts` `buildOriginAttrs`/`stampOriginAttrs`). This is deliberately a **second consumer of the same message** — the audit row stays; the single-source question (Open questions) remains open and is tracked separately.

**9. (v7) The destination is one nullable column that grants no access — and every write of it passes the same cross-org guard virtual keys use.** `IngestionSource.traceProjectId String?` — the `VirtualKey.traceProjectId` shape (`platform/app/prisma/schema.prisma:2853-2869`): null means don't route; a destination is **not** a scope row and confers no access to the source. Freely editable at any time, exactly as virtual keys do it (`virtualKey.service.ts:1050-1065`: untouched stays, named re-validated as create would, null re-derives; no lock). *Refuter correction:* the virtual-key precedent works because of a guard the plan never named — `assertTraceProjectBelongsToOrg` (`platform/app/src/server/gateway/virtualKey.authz.ts:397-409`, "a stray id would route another tenant's costs") — and the puller writes with a service-level Prisma client, so nothing downstream would catch a foreign-org id. The equivalent check is **required at IngestionSource create/update**, with a test asserting a foreign-org `traceProjectId` is rejected at write time. A destination later archived or deleted stops routing (skip + surface on the source screen, the `traceProjectFor` precedent — `scopeResolver.ts:219-240`) rather than failing the run or silently landing elsewhere. Routed history does not move on edit — migrating old traces to a new destination is deferred. **This column is not Decision 4's cost-attribution `projectId`** — pulled cost attribution stays org/team; the two must not be conflated.

**10. (v7) Trace identity is deterministic; a regenerated answer is a new attempt entry; order is `created_timestamp`.** Trace ids hash **`ingestion_source_id`** + `conversation_id` + `message_id`; span ids hash the same **plus `auto_regenerate_count`**; thread id = `ingestion_source_id` + `conversation_id`. The source namespace is not decoration: provider ids are unique within a Genie **workspace**, and one destination project can receive pulls from several sources, so an unqualified seed bets on two independent identifier domains never meeting — and loses silently in both directions (equal span ids dedupe the second source's conversation away permanently; an equal thread id interleaves two workspaces' turns into one rendered conversation). *Refuter correction:* the original "last-write-wins" was impossible — the event store is **first-write-wins** (`idempotencyKey = tenant:trace:span`, `eventStoreUtils.ts:120-137` keeps the first occurrence), so a regenerated answer re-sent under a content-stable span id would be silently discarded, the exact opposite of the intent. With the attempt count in the id, a regenerated answer lands as its **own span beside the original's** — and the conversation bubble shows the **latest** attempt for free: among multiple parentless spans in one trace, the latest-finishing root wins the trace output (`shouldOverrideOutput`, `trace-io-accumulation.service.ts:44-75`), so the current answer is the one rendered while prior attempts stay inspectable as spans; further attempt-collapse UI is polish, deferred. An unchanged re-pull stays a **durable** no-op through that same first-write idempotency — the Redis dedup gate (`span-dedupe.service.ts`: 1-hour TTL, fails open when Redis is down) is only a fast path, never the guarantee. Turn ordering is `created_timestamp` with `message_id` as tie-break: the API exposes no sequence field, and `last_updated_timestamp` moves on regeneration.

**11. (v7) The 31-day door stays; the door alone enforces it — the walk is untouched.** The door already rejects spans older than `SPAN_MAX_PAST_MS` (31 days — `trace-request-collection.service.ts:30`, enforced `:340`). *Review correction (2026-08-23):* the first draft mandated the walk skip old messages before fetching to save its 400-request budget (`databricksGenie.puller.ts:91`) — that mechanism was wrong: the walk serves the **audit ledger first**, which has no 31-day door and must keep every message the cursor admits, and routing rides the already-fetched events at **zero additional HTTP cost**. Skipping the fetch would silently drop audit rows to optimize a budget routing never spends. So: old messages (stale-cursor resume, deep `startFrom`) are still fetched and audited; the mapper maps them; the trace door drops their spans and the worker logs the rejected count. The UI states the promise in one sentence: "conversations from the last 31 days." A consequence to state plainly: a conversation thread that *started* more than 31 days ago renders partially — only the turns inside the horizon appear, older turns are dropped at the door, not stored. Widening to a year (door exemption + one-off backfill walk + destination-retention cap) is deferred; the one deferral risk is that Databricks-side Genie retention is unknown (research item).

**12. (v7) Rendering reuses explorer-v2 shapes; tokens are estimated; cost is never written to the trace.** The mapping (all counts from the 35-message capture): user bubble ← `content`; assistant bubble ← the `text` attachment with purpose `ANSWER` (wire value `TEXT_ATTACHMENT_PURPOSE_ANSWER` — matched by suffix; 35/35, refusals included); thinking block ← `attachments[].query.thoughts[]` (wire shape: `thought_type` key, enum-prefixed values `THOUGHT_TYPE_*`, text under `content`) flattened `UNDERSTANDING → DATA_SOURCING → STEPS` into the payload field the transcript parser already reads (`conversationView/ChatTurnRow.tsx:655-663`), with the `DESCRIPTION` thought dropped (byte-identical to `query.description`, 33/33 — it becomes the step-row label instead) and unknown thought types passed through; one step row per `query` attachment (label = `query.description`, body = SQL + `row_count`, **all** statement ids carried); the `viz` pointer (`{query_attachment_id}` only, 21/35) stored as a plain attribute, nothing rendered; `suggested_questions` (35/35) **dropped explicitly** — Genie's offered follow-ups, never something a person said. One UI change: the `TurnSteps` span-name filter (`features/traces-v2/components/TraceDrawer/conversationView/TurnSteps.tsx:21-22`) gains Genie's span name. **Tokens:** Databricks exposes no counts (verified in capture), so the answer span is typed `llm` and the existing estimator (`span-token-estimation.service.ts`) counts the text and stamps `langwatch.tokens.estimated = true` — generic tokenizer, since Genie's model is hidden; approximate on purpose and marked as such. The puller's literal zero token fields are dropped by the mapper, not copied. **Cost:** absent from the trace — Genie inference is `GENIE_FREE_USAGE` (v6 scope-out) and warehouse dollars live in the ledger, which restates itself; a dollar written onto a trace goes stale at the first correction. If the explorer ever shows dollars it looks them up at display time by statement id (`shareOf()` — `databricksWarehouseCost.ts:382`); the join key is stored from day one.

**13. (v7) Author is the raw numeric `user_id`; the destination project's redaction policy applies; failure degrades defensively.** The author is written as a string attribute carrying the provider's numeric id, nothing more; the person is resolved at **read time** by the identity stack (ADR-094; `ACTOR_ID_KIND_BY_PROVIDER` declares `databricks: "numeric_id"`), so a fixed link heals every past trace. No SCIM call at pull time — it would bake a resolution into an immutable trace and disagree with the audit row the identity branch writes. **Redaction:** the destination project's policy governs — but *not* by the mechanism first drafted. *Refuter correction:* every existing `handleOtlpTraceRequest` call site passes `DEFAULT_PII_REDACTION_LEVEL` (`"ESSENTIAL"`, `trace-processing/schemas/commands.ts:18`) and the real per-project enforcement happens **inside** the pipeline: `redactSpan` resolves the destination's cascaded data-privacy policy by tenant id (`span-pii-redaction.service.ts:231-261` → `getResolvedForProject`), and an explicit policy level always wins over the request level (`reconcilePiiLevel` `:164-170`). At the *essential* tier, however, a caller-passed level has **unchecked authority** — so the puller must never compute one. The routing call passes the destination project id as tenant plus the same `DEFAULT_PII_REDACTION_LEVEL` as every sibling, and the pipeline's own lookup is the sole source of truth. *Review correction (2026-08-23):* the mandated test was first worded as "hostile caller level → still not stored unredacted" — unsatisfiable: at the essential tier `reconcilePiiLevel` honors the caller's level **by design** (a `DISABLED` request level skips redaction, `span-pii-redaction.service.ts:164-170`), so the pipeline cannot defend there. The true, testable invariant is the caller side: the routing worker never computes a level and always passes `DEFAULT_PII_REDACTION_LEVEL` with the destination project id — pinned by unit test on `routeConversationsToTraceDestination`. The strict-policy case was never at risk (an explicit rule always wins). The source screen states the inheritance in one line. **Failure:** the mapping is defensive — unknown status or missing attachments still renders the user's question with a failure marker, never a false success; all 35 captured messages are `COMPLETED`, so the failure path is pinned by a synthetic fixture until a real one is captured. Per-message skip-and-count in the puller is deferred: today a poison message stalls its source via whole-window retry (`pullerWorker.ts:65-66`) but loses nothing — the cursor holds and a later pull catches up.

**14. (v7) Routed traces are first-class downstream — deliberately, and stated out loud.** The red-team confirmed that nothing reading `trace_summaries`/`stored_spans` filters by origin, so routed conversations flow into every consumer. Rather than special-case them, this is locked as the design: **(a) they count** toward plan trace limits, usage stats, usage-limit warnings, and `/me/usage` request counts (`billableEvents.clickhouse.repository.ts:87-107` `uniq(TraceId)`, no origin filter) — a routed conversation is a real trace consuming real ingestion and storage; how routed conversations are *monetized* is an open product question, deferred. **(b) They trigger** the destination project's monitors and evaluators like any other trace — a customer routing into a dedicated project controls exactly what evaluates there, and scoring Genie answers may be the point. **(c) Estimated tokens blend** into aggregate token dashboards (the estimated flag is per-span; aggregates don't read it) — accepted and documented, not filtered. **(d) Zero cost is a guard, not an accident:** cost enrichment runs unconditionally on `llm` spans and today yields nothing only because Genie's span carries no model attribute matching a price row; a fixture test pins that routed spans never resolve in the pricing table, turning the accident into an invariant.

**15. (v8) Copilot Studio conversations are read from the Dataverse `conversationtranscript` table, not from Microsoft Graph.** The shipped `copilot_studio` adapter polls `graph.microsoft.com/v1.0/auditLogs/directoryAudits` (`copilotStudio.puller.ts`) — the **Entra directory audit**, which records directory changes (user created, role assigned) and can never return a Copilot conversation. That is not a tuning problem; it is the wrong table. The conversation body lives in the Dataverse table **`conversationtranscripts`** (Web API path; no `msdyn_` prefix), whose `content` column is a JSON object with a single key `activities` holding an array of Bot Framework **activities**, joined to the **`bot`** table through the lookup column **`_bot_conversationtranscriptid_value`** (which equals `bot.botid`). Web API base is `<environmentUrl>/api/data/v9.2`. *(Red-team correction: the first draft named the join column `_bot_value`, a field that exists nowhere in the capture.)*

*(v10) Two more columns are load-bearing and the first draft ignored both.* **`name`** is the table's primary-name attribute and holds **`<conversationId>_<botId>`** — this is the only conversation identifier that exists anywhere in the data, because the activities themselves carry no `conversation.id` (verified null on every activity in both captures) and the table has **no `conversationid` column** (verified against the vendor's own entity reference). **`metadata`** is a JSON string holding `{BotId, AADTenantId, BotName, BatchId}`. **`BatchId` is the split counter**: `content` is a Memo capped at 1,048,576 characters, and the vendor documents that a conversation exceeding it is written across *several* rows. Those rows share a `name` and differ by `BatchId`. So a transcript **row** is a batch, not a conversation — see Decision 20's correction. `metadata.BotId` also duplicates the `bot` lookup, which gives the agent identity without the join when the join fails. Observed `schematype` is `powervirtualagents`, `schemaversion` `0.2.2`; the mapper records both and treats an unrecognised schema version as a reason to warn, not to guess. Grounding is live, not inferred: 18 scripts in the validated Copilot research set, **26 payload assertions** in `35_dv_payload_contract.sh`, and app-only auth proven **6/6** in `52_sp_connector_check.sh`. The Graph/Purview route is additionally dead in the test tenant (the `manage.office.com` service principal is disabled and Purview returns 403 to a Global Admin), so there is no fallback worth keeping.

**16. (v8) A new adapter id ships; the old one stays registered and stays in the catalog, but is filtered out of the picker.** New id **`copilot_studio_dataverse`**. The shipped `copilot_studio` adapter (`copilotStudio.puller.ts:76`) stays registered so existing `IngestionSource` rows keep resolving and no run starts throwing "unknown adapter". Being **unreachable in the picker** is the load-bearing part, and it is not the same as labelling it deprecated: the picker is the only place a source is born, and a caveat in a label is something a customer reads and clicks anyway. `SourceType` keeps `"copilot_studio"` (`ingestionSource.service.ts:56`) — the union describes rows that exist, not options offered. *Dissent recorded:* the recommendation was to replace in place — one id, swap the implementation, delete the dead code — and it lost, to avoid silently changing what an already-configured row does.

*Red-team correction (2026-08-26): the stated mechanism did not compile.* The first draft said to **delete** the catalog entry (`ingestionSourceCatalog.tsx:111-118`). That file carries a compile-time exhaustiveness guard both ways (`:169-178`): `Exclude<SourceType, (typeof SOURCE_TYPE_OPTIONS)[number]["value"]>` must be `never`. Keeping `"copilot_studio"` in the union *and* deleting its catalog row makes that resolve to `"copilot_studio"`, and `pnpm typecheck` fails — the two halves of Decision 16 contradicted each other. The guard is right and stays. A second break sat behind it: `SOURCE_TYPE_LABEL` is `Object.fromEntries(...)` force-cast to `Record<SourceType, string>` (`:180-182`), so a deleted entry yields `undefined` at runtime under a type claiming `string`, and `inventory.tsx:3382` reads it with **no fallback** — the post-rotate "here's your secret" panel, a workflow this decision explicitly preserves for existing rows, would render a blank badge (`:875` has `?? source.sourceType` and is fine). **So the entry stays in `SOURCE_TYPE_OPTIONS` and gains a `deprecated: true` field; the picker filters on it.** Exhaustiveness holds, labels keep resolving for existing sources, and the id is still unreachable to a customer creating one — which was the whole point.

**17. (v8) Auth is app-only `client_credentials` against the Dataverse environment; no delegated flow, no pasted user token, ever.** An Entra app registration, its client secret held in the existing credential store (`ingestionCredentials.ts`), token acquired for scope `<environmentUrl>/.default`. This is the **first puller using `client_credentials`** — every existing adapter carries a static bearer token (`claude_compliance`, `anthropic_admin`) or an S3 key (`openai_compliance`) — so token acquisition and refresh is new code, not a config value. Proven 6/6 live. A delegated (person-signs-in) flow is excluded by a Phase-1 constraint and is not a fallback: the puller runs unattended on a cron, and a mode that needs a human present is not a mode.

*(v10.2)* **The adapter is standalone; it does not extend `HttpPollingPullerAdapter`.** The ADR through v10.1 never said which, and the choice follows from this decision rather than from preference. `HttpPollingPullerAdapter.buildHeaders` (`httpPollingPullerAdapter.ts:249-263`) resolves credentials by substituting a stored secret into configured header templates — a fixed value, known before the run. `client_credentials` is not that shape: a token is exchanged for, cached, and refreshed on expiry, and there is no seam in that class for a pre-request acquisition step. Extending it therefore means adding token machinery to a base class that four shipped adapters run on, for a mode none of them use. The cost of standing alone is stated plainly: the paging and retry loop (`:163-229`, including `RETRY_DELAYS_MS`, the dual `AbortSignal`, and the 4xx-fails-fast / 5xx-retries split) is duplicated, roughly 80 lines. Accepted at n=1 under the same rule Decision 26 applies to the mapper — extract when a second caller needs it, not before. **This does not exempt the shared class from the redirect fix**: `followRedirects: false` at `:194-199` is a security floor for the four adapters already on that path, lands in its own commit, and is independent of where the Dataverse adapter lives.

**18. (v8) The environment URL — REOPENED by the red-team; the locked answer rested on two false premises.** The locked answer was "any `https` URL, and the scoped secret is the whole boundary", with the consequence stated plainly: **our server sends the customer's client secret to whatever host they typed.** *Dissent recorded at lock time:* the recommendation was a strict `https://<org>.crm<n>.dynamics.com` pattern, overruled because sovereign clouds (`.crm9.`, `.crm.microsoftdynamics.us`) and custom-domain environments would be locked out by a regex.

*Red-team correction (2026-08-26). Both halves of the locked answer are wrong on the facts, so the fork goes back to the captain rather than being quietly re-decided.* **(i) "Redirects are not followed" is false of the code this adapter is built on.** `CopilotStudioReferencePuller` extends `HttpPollingPullerAdapter` (`copilotStudio.puller.ts:75,89-98`), whose `fetchPage` calls `ssrfSafeFetch` with **no** `followRedirects: false` (`httpPollingPullerAdapter.ts:198-204`), and that helper's default is to **follow, up to 10 hops** (`src/utils/ssrfProtection.ts:505,663-709`). Three sibling call sites facing this exact scenario pass the opt-out explicitly (`providerValidation.ts:948`, `httpDestination.ts:170`, `realtimeSessionPoller.ts:90`). So the mitigation named in the Gates row would have been false the day it shipped, and the real floor was "that host, plus wherever it 302s to." **This half is not a fork — `followRedirects: false` is required, full stop.** **(ii) The rejected alternative was described too narrowly, and the objection to it does not survive.** The choice was framed as one regex versus nothing, but this ADR's own Genie decision already solved the identical problem with a **host-suffix allowlist** on the write path — `assertPullDestinationAllowed` (`activity-monitor/pullDestination.ts`, enforced at `ingestionSource.service.ts:552,630`), listing `.azuredatabricks.net`, `.cloud.databricks.com`, `.gcp.databricks.com` — and the Genie adapter says in as many words why `ssrfSafeFetch` alone was not enough: it rejects *private* destinations, "a different threat and no defence against an attacker-owned public host" (`databricksGenie.puller.ts:113-115`). A suffix list covers sovereign clouds by **listing** them, which is precisely the objection that sank the regex. **Re-asked and re-locked (2026-08-26, captain): extend the switchboard.** The Dataverse environment host gets a `copilot_studio_dataverse` case in `assertPullDestinationAllowed` carrying the Dataverse **host suffixes** (`.dynamics.com`, `.crm.microsoftdynamics.us`, and the sovereign equivalents), enforced on the write path exactly as Genie's is — so a bad host is rejected when the source is saved, before any secret is ever sent. `https`-only, `followRedirects: false` at every fetch site, and one secret per source all stand as well; they are the floor, not the boundary. The accepted cost, stated plainly so nobody is surprised by it later: **a customer on a custom-domain Dataverse environment cannot self-serve — we have to add their suffix and ship.** That is a support ticket, and it was chosen over sending a client secret to an unvetted host. No admin override ships; an override that lets someone point the secret anywhere is the hole the allowlist exists to close.

**19. (v8) The permission ask is the built-in `Service Reader` role, and the setup copy discloses its breadth.** Role id `494d392f-d3f4-42ba-af49-30c6f41e6093`: **561 read privileges across 561 tables, plus 2 SharePoint write privileges** — granted so the service account can read **2** tables. `Bot Transcript Viewer` is the trap and is rejected on evidence: its privileges are **Basic** depth, meaning *records the user owns*, and a service account owns none, so it returns zero rows rather than a permission error. The proper fix is a custom-role solution file scoped to `conversationtranscript` + `bot`, which **does not exist yet** and is named as follow-up work, not assumed done. *Dissent recorded:* the recommendation was to build the custom role before shipping; it lost on time-to-first-customer. The mitigation that does ship is honesty — the setup instruction states what `Service Reader` can read, in the customer's own words, rather than presenting it as a routine checkbox. **The grant itself is always the customer's to execute**; nothing in the product performs a role assignment.

**20. (v8, corrected in v10) A *conversation* is one trace; a message activity is one span; tool calls pair into step rows and the contentless remainder is dropped.** Each **conversation** — not each transcript row — becomes one trace and one thread; each `message`-type activity becomes one span (user bubble for `role 1`, assistant bubble for `role 0`). The captured transcripts are mostly not conversation: of **212 activities** in the large capture, `event` = 203, `message` = 7, `trace` = 2. Tool invocations arrive as `ToolCallTrace:Started` / `ToolCallTrace:Completed` event activities and are folded into one step row each — the same step-row shape Genie's query attachments already use (`ChatTurnRow.tsx`) — and every remaining contentless activity is dropped explicitly rather than rendered as empty turns.

*Red-team correction (2026-08-26): the pairing is **not** 1:1, and the ground truth already said so.* The large capture holds `Started` = **2** and `Completed` = **1**. The payload contract script asserts `STARTED >= DONE`, logs a `never-completed` count, and states in as many words that an unpaired `Started` is **normal** — a span builder must close it itself or drop it, never wait. So the rule is: **a `Started` with no `Completed` becomes a step row marked unfinished, and the mapper never blocks or buffers waiting for a partner.** The first draft called the pairing "matched", which stated the common case as the rule and would have shipped a mapper that either loses tool calls or hangs on them.

*(v10) The "one row = one trace" rule was wrong, and it fails silently on exactly the conversations customers care most about.* `content` is capped at 1,048,576 characters and the vendor documents that a longer conversation is split across **several rows**, which share a `name` (`<conversationId>_<botId>`) and differ by `metadata.BatchId`. Seeding the trace on `conversationtranscriptid` would therefore shatter one long conversation into N unrelated traces — and because both captures happen to be single-batch (`BatchId: 0`, two *different* conversation ids), no test built from them would ever catch it. **So the trace and thread seed is `name` + `conversationstarttime`, and the row id is not an identity input at all.** That pair is the vendor's own documented reassembly rule: records of one split conversation share `Name` and `ConversationStartTime` and differ by `Metadata.BatchId`, and you sort by `BatchId` to rebuild it. *(v10.1 correction: an earlier draft of this decision seeded on `name.split("_")[0]`, inferring that the prefix is a conversation id. The `<conversationId>_<botId>` shape is an observed value pattern, **not** a documented contract — the vendor says so explicitly — so parsing it would have made our identity depend on a format Microsoft never promised. Hash the whole `name`; it is opaque to us on purpose.)* Two mechanical consequences: `BatchId` must be sorted **numerically, not lexicographically**, or batch 10 orders before batch 2; and because `BatchId` lives inside a JSON `metadata` blob rather than a first-class column, it **cannot be filtered or ordered server-side** — the query pages by `createdon`, `conversationtranscriptid` (as the validated script already does) and the merge happens in our process. Two consequences are accepted rather than solved: a batch arriving in a later pull **extends an existing trace**, which the span pipeline handles (new span ids, appended) but which means a trace is not final when first written; and if retention purges some batches and not others, the merged conversation has **gaps** — the vendor says so directly. A conversation missing `BatchId: 0` is marked incomplete rather than presented as whole.

**21. (v8) The span seed is `ingestion_source_id` + transcript id + the activity's own GUID; a missing or non-GUID activity id is rejected, never invented.** Microsoft supplies no message id, but every conversational activity carries one. Evidence: in the large transcript **211 of 212** activities carry an `id`, all **211 unique, zero duplicates**, and **all 7 `message` activities** carry distinct GUIDs. The counter-example is what forces a reject rule rather than a fallback: the small transcript has 4 activities, 3 with ids, and **one of those ids is literally the string `"0"`**. Inventing a seed from an array index or a content hash fails in both directions — an index collides across re-pulls that fetch a different window, a content hash changes when the provider normalises whitespace — and each failure is *silent*. So: no GUID, no span; the activity is counted as skipped and surfaced, not guessed at. The `ingestion_source_id` namespace is kept for exactly the reason Decision 10 established it — Dataverse ids are unique within an **environment**, and one destination project can take pulls from several environments.

*Red-team correction (2026-08-26) — and this one corrects **v7's Decision 10**, not just this decision.* Both cite the event store's first-write-wins idempotency at `tenant:trace:span` (`eventStoreUtils.ts:120-137`) as the durable re-pull guarantee. **That file is not the span path.** Its `deduplicateEvents` runs at *read* time over one fetched page and governs the generic event-sourcing store (langy, suites, SSO); the write path has no dedup (`abstractEventStore.ts:24-26`). Spans go through `handleOtlpTraceRequest` → `SpanDedupService`, a Redis `SET NX` with `CONFIRMED_TTL_SECONDS = 3600` (`span-dedupe.service.ts:16-19`), into ClickHouse `stored_spans`, `ENGINE = ReplacingMergeTree(StartTime)` (`00002_create_schema.sql:44,116`). The repository documents the consequence itself as a **"KNOWN MISMATCH, pre-existing"** (`span-storage.clickhouse.repository.ts:1307-1310`): the version column is `StartTime`, not `UpdatedAt`, so a re-sent span is **last-written-wins before a merge and largest-`StartTime`-wins after one**, with every insert stamping `UpdatedAt: new Date()` (`:2448`) and single-span reads ordering `UpdatedAt DESC LIMIT 1`. So a re-pull more than an hour after the first sails past Redis and **rewrites** the row; the actual behaviour is TTL'd-lock, then last-write-wins, then `StartTime`-wins. Three things follow. **(a)** "An unchanged re-pull is a durable no-op" is wrong as a *mechanism* and survives only as an *outcome*: the row is rewritten with byte-identical content, so nothing observable changes — which is why this has not bitten anyone, and why it stops being true the moment the content differs (a rewritten transcript, or a mapper change between pulls) and the newest copy silently wins. **(b)** v7's reasoning for putting `auto_regenerate_count` in the span id was that first-write-wins would *drop* the regenerated answer. The premise was wrong; the decision was right anyway, and is now more clearly right — without the attempt in the id a regeneration would silently **overwrite** the original instead of dropping, which is worse. **(c)** `StartTime` is the merge tiebreak, so a mapper that ever falls back to wall-clock for a span's start makes the post-merge winner nondeterministic. Copilot activity timestamps are present and monotonic in both captures (epoch seconds), so the fallback must simply never fire: **a Copilot span with no usable source timestamp is rejected like a missing GUID, not stamped with `Date.now()`.**

**22. (v8) The author is the raw `aadObjectId`, resolved later — and v7's cited machinery for that does not exist.** The user's directory GUID is written as a string attribute and nothing else; **no Graph call at pull time** — which also means this adapter needs **no Microsoft Graph permission at all**, since the transcripts and the agent identity both come from Dataverse, shrinking the customer-facing app-registration ask to Dataverse only. In the captured data the shape is unambiguous, and the payload contract asserts it three ways: every activity carrying `aadObjectId` has `role 1`, no `role 0` activity carries one, and every human message carries one. **The trap, named here because the first draft omitted it:** every activity — agents included — also carries a `from.id`, which is GUID-shaped and looks exactly like a directory id. It is not. It is a **per-conversation channel id**, unstable across conversations, and the research set flags it explicitly as something never to join on. Only `from.aadObjectId` is the person. The mapper must read `aadObjectId` and must not fall back to `from.id` when it is absent — an absent `aadObjectId` means the turn is the agent's. **Correction to v7:** Decision 13 and the v7 rejected-alternatives entry both cite "ADR-094" and a constant `ACTOR_ID_KIND_BY_PROVIDER` declaring `databricks: "numeric_id"`. Neither exists — the identity work shipped as [ADR-101](./101-identity-pipeline-and-identifiers.md) ("Identity pipeline and the identifiers projection", **Status: Proposed**), and the constant appears nowhere under `platform/app`. Read-time author resolution is therefore a **dependency on unshipped work**, not machinery to lean on: both Genie and Copilot authors render as bare identifiers until ADR-101 lands. That is a consequence to state, not a reason to resolve at pull time — baking a mutable directory lookup into an immutable trace stays rejected.

**23. (v8) The agent's model is read at collection time from the `bot` row and stored with that row's `modifiedon`; it is marked unreliable when `modifiedon` post-dates the conversation.** The model is **not in the conversation payload** — a keyword sweep over every leaf path of all 216 captured activities returns zero matches for `model`, `token`, `cost`, `price`, or any billing term — and it drifts, since a customer can change their agent's model at any time and Dataverse keeps no history of it. The only place a model identifier exists is the `bot` row's `configuration.agentSettings.model.series`, observed as `"GPT56Reasoning"` — note that this is a **series name, not a version or deployment id**, so even a fresh read is coarse. So the mapper reads the joined `bot` row during the pull and stamps both that series value and the row's `modifiedon` onto the span. When `modifiedon` is **later than** the conversation's timestamp, the stored model is provably not necessarily the model that answered, and the span is marked as such rather than asserting a value we cannot support. Omitting the model was rejected: a right-most-of-the-time model with an honest marker is strictly more useful than none, and `KNOWN_AGENT_IDENTITIES` already carries `"microsoft/copilot-studio"` (`genieTraceMapper.ts:74`) as the agent identity that keeps Decision 14(d)'s zero-cost invariant true.

**24. (v8) Every conversation routes, including design-mode test chats, which are marked rather than dropped.** Copilot Studio's authoring canvas produces transcripts indistinguishable in shape from production ones. They route, carrying an attribute that says they came from design mode. *Dissent recorded:* the recommendation was to skip them — they are an author talking to themselves and they inflate the trace counts Decision 14(a) makes billable — and it lost, because a customer testing their agent is precisely the customer who wants to see the transcript, and a filter that silently hides traces is the harder failure to debug.

**25. (v8) The history promise is "the last 30 days", and the setup instruction tells the customer to cancel the Dataverse bulk-delete job.** Two horizons are in play and we promise the **smaller**: Dataverse ships a default **bulk-delete job that removes transcripts after 30 days**, and our own trace door rejects spans older than `SPAN_MAX_PAST_MS` = **31 days** (Decision 11). Promising 31 when the source keeps 30 would be a promise the provider breaks for us. The setup instruction names the bulk-delete job explicitly, because a customer who wants more than 30 days must cancel it **before** the data is gone — a fact that is worthless the day after they need it. One further timing fact belongs in the copy: Dataverse writes a transcript only after roughly **30 minutes of conversation inactivity**, so a conversation that just happened is expected to be absent.

*Red-team correction (2026-08-26): the two numbers are not equally solid, and the ADR presented them as if they were.* The **30-minute write delay is measured** — one live transcript, conversation start `19:14:35Z` to row `createdon` `19:45:12Z`, 30m37s (n=1). The **30-day bulk-delete retention is quoted, not verified**: it appears in the research set as an assertion with no vendor-documentation URL, no excerpt, and no live confirmation, unlike the neighbouring claims in the same notes which do cite exact documentation links — and a 30-day retention is not observable in a same-day capture. It was therefore **a customer-facing promise resting on an unsourced number**, which is exactly the shape of claim this project does not ship.

*(v10) Verified 2026-08-26 against vendor documentation, at the captain's instruction that this not stay an open question.* The number holds: the recurring job is named *Bulk Delete Conversation Transcript Records Older Than 1 Month*, and the documented way to keep transcripts longer is to cancel that job and create a replacement — which is exactly what the setup copy will tell the customer to do. Two further facts fell out of the same check and mattered more than the number did: a conversation exceeding the 1 MB `content` cap is **split across several rows** (which broke Decision 20 — see its v10 correction), and a partial purge leaves the merged conversation with **gaps** rather than removing it cleanly, so an incomplete conversation must be marked as such. Verifying a quoted number found a design defect that no amount of re-reading the ADR would have.

**26. (v8) The conversation mapper splits into a per-source mapper over a shared assembly — the scaffolding fork, taken at n=2.** PR 1 generalised four values; the rest of `genieTraceMapper.ts` is still Genie-shaped and would be **wrong** for Copilot rather than merely unused: span names, **seven** `databricks.genie.*` attributes (`:479-531`), an `identityNamespace` of `genie:<ingestionSourceId>` seeding trace **and** span ids (`:393-409`), an `unknown_conversation` fallback (`:373`), a `[Genie message …]` placeholder (`:444`), and `frameOf`/`mapMessage` parsing Genie payload keys. The split is taken at two callers rather than deferred to three because the standing rule's escape clause applies: the blast radius is customer conversation data and the differentiation is zero — nobody wins by seeding trace ids differently per provider. **Shared assembly owns** the trace/span/thread seeding *contract*, the estimator handoff and its `langwatch.tokens.estimated` flag, the `DEFAULT_PII_REDACTION_LEVEL` pin of Decision 13, and `KNOWN_AGENT_IDENTITIES`. **Per-source mappers own** payload parsing, span names, provider attributes, the settled/failed predicate, and placeholder copy.

*Red-team correction (2026-08-26), two claims died and the seam moved.* **(i) The settled-predicate claim was backwards, in the more dangerous direction.** The first draft said `isSettledForRouting` gates on `TERMINAL_MESSAGE_STATUSES`, which Copilot never emits, so naive reuse would route *nothing*. The code is `status === "" || TERMINAL_MESSAGE_STATUSES.has(status)` (`:359-363`) — a message with no status at all is routed as it stands, by documented intent. Copilot activities carry no Genie `status` field, so `status` resolves to `""` and **every Copilot message routes, unfiltered**. The failure mode is not an empty explorer that someone would notice; it is design-mode noise, contentless activities and failed turns all landing as successful conversations. So a per-source settled predicate is not a tidiness item — it is the thing standing between Decision 24's "marked, not dropped" and nothing being marked at all. **(ii) Seeding cannot simply move to the shared side, because the seed's *shape* is Genie's.** `frameOf` (`:365-418`) fuses identity with Genie payload extraction, and `spanSeed` (`:394`) is a four-field template `<namespace>:<conversation>:<message>:<regenCount>` — while Decision 21's Copilot seed is three fields and has no regeneration concept at all. There is no generic seed builder in the code today, only that one hardcoded string. So the shared assembly owns the *contract* — a source-namespaced seed, hashed one way, for trace, span and thread — and each mapper supplies its own ordered field list. Relocating the existing template would have imported Genie's arity into Copilot silently.

## Assumptions

| Assumption | What breaks if false |
|---|---|
| One writer produces each usage record (the pull) | "priced once / newest wins" becomes ambiguous |
| A provider restates a bucket under the **same stable coordinates** | the correction can't match the original; both persist (silent double-count) |
| The tenant boundary is enforced upstream of the ledger write | pulled cost reported under the wrong customer |
| `IngestionSource` can be extended to carry the target project | Decision 4's project attribution has no home (named as required work, not assumed done) |
| *(v7)* `message_id` and `created_timestamp` are stable across re-pulls | dedup breaks → duplicate traces; ordering shuffles between pulls |
| *(v7)* `auto_regenerate_count` increments on every regeneration | a regeneration that keeps the count produces an identical span id → first-write-wins silently drops the new answer |
| *(v7)* A completed message carries an `ANSWER` text attachment (35/35 observed) | assistant bubble empty → defensive failure marker renders instead (degrades, doesn't break) |
| *(v7)* Databricks retains ≥31 days of Genie history | a fresh connection shows less than the UI promises; also the 1-year-widening deferral loses data permanently (research item) |
| *(v8)* Activity GUIDs are stable across re-pulls of the same transcript | dedup breaks → the same turn lands twice as two spans, since the seed is the only thing the span id keys on |

## Rejected alternatives

- **Separate isolated `pulled_usage_rollup` table** — read by none of the three spend surfaces; invisible. (The #1 red-team kill of v1.)
- **Write under an enforcing scope / debit budgets, or extend `GatewayBudgetScopeType`** — blocks money spent outside the gateway, double-counts gateway users, and (the enum route) lets a budget be created under the pulled scope, breaking non-enforcement by construction.
- **`aggregateId` = message id for all providers** — bucketed admin APIs have no message id.
- **Hash cost into the restatement key** — a corrected cost mints a new key → double-count instead of replace.
- **Report under the hidden governance project** — invisible to the customer.
- **Rely on ReplacingMergeTree merge order for restatement** — stale reads on a money number.
- **A second parallel pull system** — excluded by the Phase-1 constraint.
- *(v7)* **Pull-time SCIM resolution of the author** — bakes a mutable conclusion into an immutable trace and disagrees with the audit row; the read-time identity stack (ADR-094) heals every past trace with one fixed link.
- *(v7)* **Copying the puller's literal zero token counts** — a provider absence is not a measurement; estimate and flag instead.
- *(v7)* **Rendering the `DESCRIPTION` thought** — byte-identical duplicate of `query.description` (33/33); it becomes the step label, rendering it twice is noise.
- *(v7)* **Rendering the `viz` attachment** — it carries a pointer, not chart data; whether a chart is retrievable by that id is unproven (research item).
- *(v7)* **Widening the 31-day door now** — needs a door exemption, a one-off backfill walk, and a destination-retention cap, against an unknown provider retention window; deferred (Decision 11).
- *(v7)* **Per-message skip in the puller now** — deferred: defensive mapping makes odd messages non-poison, the retrofit is a mapping-loop change plus one field on the Completed event, and the interim cost (a true poison message stalls one source, loses nothing) is bounded.
- *(v7)* **A parallel render path off the audit table** — the audit copy is single-copy and not journal-backed; the trace door gives validation, dedup, journaling, redaction, and estimation for free.
- *(v7)* **A dollar written onto the trace** — goes stale at the first ledger restatement; one number, one owner (the ledger), display-time lookup by statement id if ever needed.
- *(v8)* **Keeping the Graph/Purview route for Copilot** — `auditLogs/directoryAudits` is the directory audit; no tuning of it returns a conversation, and the route is additionally dead in the test tenant.
- *(v8)* **Replacing `copilot_studio` in place** — the recommendation, overruled: an existing row would silently start doing something different. New id instead, old one deprecated and removed from the picker.
- *(v8)* **Labelling the old adapter "deprecated" but leaving it selectable** — the picker is the only place a source is born; a caveat in a label is read and clicked anyway.
- *(v8)* **A strict `*.crm<n>.dynamics.com` host pattern** — the recommendation, overruled: locks sovereign clouds and custom-domain environments out of the product by regex. *(The red-team pass found a third option neither side considered — a host-**suffix allowlist** in the existing `assertPullDestinationAllowed` switchboard, which is how the Genie decision in this same ADR already solves it and which covers sovereign clouds by listing them. Decision 18 is reopened on that basis; this rejection stands only against the regex.)*
- *(v8)* **`Bot Transcript Viewer` instead of `Service Reader`** — Basic privilege depth means own records only; a service account owns none, so it returns **zero rows** rather than an error, which is the worst failure shape available.
- *(v8)* **Shipping the custom Dataverse role first** — the recommendation, overruled on time-to-first-customer; the solution file is named follow-up work and the breadth is disclosed instead.
- *(v8)* **Inventing a span seed when the activity has no GUID** — an array index collides across re-pulls with a different window, a content hash moves when the provider normalises whitespace. Both fail silently, and the red-team pass showed the failure is worse than first assumed: a colliding seed **overwrites** the earlier span rather than being dropped, because `stored_spans` is last-write-wins before a merge.
- *(v8)* **Resolving the author through Microsoft Graph at pull time** — same reason as v7's SCIM rejection, and it is what keeps the app-registration ask Dataverse-only (no Graph permission at all).
- *(v8)* **Omitting the agent model because it drifts** — a mostly-right model with an explicit unreliable marker beats no model; the marker is the honest part.
- *(v8)* **Skipping design-mode test chats** — the recommendation, overruled: the customer testing their agent is exactly the customer who wants the transcript, and a silent filter is the harder failure to debug.
- *(v8)* **Promising 31 days of Copilot history** — Dataverse's own bulk-delete job removes transcripts at 30; promising the door's number would be a promise the provider breaks for us.
- *(v8)* **Waiting for a third provider before splitting the mapper** — the standing n=3 rule's escape clause applies: customer conversation data, zero differentiation, and a Genie-shaped settled predicate that would route **every** Copilot activity unfiltered (see Decision 26's correction — the first draft had this backwards and claimed it would route nothing).
- *(v10.2)* **Extending `HttpPollingPullerAdapter` and teaching it `client_credentials`** — it would have saved ~80 duplicated lines of paging and retry, and it was the first shape considered. Rejected because the saving is paid for in the wrong currency: token acquisition, caching and expiry-refresh would enter a base class that `http_polling`, `claude_compliance`, `anthropic_admin` and the Copilot adapter being retired all run on, none of which needs it. A new code path in shared machinery, exercised by exactly one caller, is a worse trade than a duplicated retry loop that only one adapter can break. Revisit when a second `client_credentials` puller exists — extraction then is mechanical, and the shape will be known rather than guessed.
- *(v10.2)* **Blocking this PR on the multi-batch live query** — considered, since the merge path is the only part of the read path with no live evidence. Rejected because the deferral is cheap by construction rather than by optimism: identity keys on `name` + `conversationstarttime` and is correct under either answer, so no ingested trace can be stranded, and paging on `createdon` picks up a late batch unaided. What is left to be wrong is in-memory merge ordering. Blocking a PR on a query that can only change in-memory code is holding the work hostage to a question whose answer costs nothing to apply late. The condition attached: the fixture-only status is stated in the PR description, not left to be inferred.

## Consequences

**Positive.** Pulled cost becomes visible in the screens customers already use (via the ledger they already read), attributed to org/team, correct under restatement, honest about exact-vs-estimate. Provider-agnostic — the second provider is an adapter. Reuses the shipped Claude Code ingestion-cost pattern rather than inventing one.

**Negative.** Pulled cost never drives enforcement (by design). Real-*project* attribution and both reconciliations (invoice true-up; Anthropic usage↔cost supersede) are named follow-ups, not in v1. Pulled + gateway cannot be safely summed into one "total AI spend" where the provider admin API omits a request id — a real, stated limit.

**Neutral.** The OCSF audit write is untouched by this ADR, but keeping it *and* the new event means two writers of the same data — see Open questions.

*(v8)* **Positive.** Decision 7's promise ("the second provider is only an adapter") is now tested rather than asserted: Copilot Studio adds one adapter, one mapper, and **zero new tables or columns**. The customer-facing app-registration ask shrinks to Dataverse only — no Microsoft Graph permission at all — because attribution stays raw-id and the agent identity comes from the same environment. The mapper split turns the Genie fixture suite into a regression harness for every future provider.

*(v8)* **Negative — three of these are chosen costs, written down rather than mitigated away.** (a) **Our server sends the customer's client secret to whatever host they typed** (Decision 18); the boundary is that the secret is theirs, scoped to their environment, and per-source. (b) **To read 2 tables we ask the customer to grant a role that reads 561 and can write 2 SharePoint tables** (Decision 19); the custom-role solution file that fixes this does not exist. (c) **Two Copilot adapter ids exist**, one of which can never return a conversation and stays registered for already-configured rows (Decision 16). Beyond those: history is capped at 30 days by the provider's own delete job, and a customer who wants more must act before the data is gone; a conversation is invisible for ~30 minutes after it ends; the agent model can be wrong-but-marked; design-mode test chats count as billable traces under Decision 14(a); and Copilot authors render as bare directory GUIDs until ADR-101 ships — which v7 wrongly implied was already available machinery.

*(v8)* **Neutral.** The 212-activity capture is 96% non-conversation (`event`/`trace`); dropping that remainder explicitly is a mapping decision, not data loss. The Genie mapper's public behaviour is unchanged by the split — that is the gate on it.

*(v8, after the red-team pass)* **What the review cost and what it bought.** Five refutations were run against the committed draft; **all five landed**, and two of them killed claims that would have shipped as code. The draft asserted that a naive mapper reuse would route *nothing* for Copilot when the code does the opposite and routes *everything* unfiltered — an implementer following the ADR would have gone looking for a missing predicate instead of an absent filter. It specified a catalog change that does not compile, because the file carries a bidirectional exhaustiveness guard the draft never mentioned. It described tool-call activities as matched pairs when the only large capture holds `Started`=2 against `Completed`=1 and the grounding script says in as many words that an unpaired `Started` is normal. It named a join column (`_bot_value`) that exists nowhere in the data. And it inherited from v7 a durability guarantee belonging to a different subsystem entirely. The pattern is worth naming: **every one of these was a claim about code or data that already existed and could have been checked**, not a prediction about the future. The design forks — which are genuinely predictions — survived the pass; only one, the environment-URL boundary, was reopened, and it was reopened because a *third option* existed in this repository that neither side of the original fork had considered.

*(v7)* **Positive.** Genie conversations become readable where conversations are read — the trace explorer — through the existing door, journal-backed and rebuildable from day one, with one schema column as the entire new surface. **Negative.** The author renders as a bare numeric id until the identity stack (ADR-094) lands; token counts are estimates from a generic tokenizer, marked as such; routing deliberately writes a *second* copy of each message (audit row + trace spans) while the single-source question stays open; a poison message stalls its source until per-message skip ships. **Neutral.** The 31-day horizon is the door's existing rule kept on purpose, not a new restriction.

## Revisions

- **v11 (2026-08-26) — implemented. What building it found, and what it did not.** Decisions 15–26 shipped in the ladder v10.2 named, in that order, with no deviation from a locked decision. Recorded here because three of the findings were invisible from the design side and one correction belongs in the record.

  **(1) The mapper split held byte-identical, and can now be seen to.** The gate rung landed five whole-object assertions over the Genie fixtures before any structure moved; all five are unchanged after the split. Writing them found the hole v9 predicted and one it did not: `space_id` is the only provider attribute sourced from the adapter's `extra` fields rather than the payload, so every fixture in the suite omitted it and it stayed unpinned even in a whole-object assertion until a fixture was added that carries it. The seeding contract landed as v9 described — each mapper supplies ordered field lists for trace, thread and span; the assembly namespaces and hashes them — and the namespace moved into the routing profile, so neither mapper contains the string `genie:` or `copilot_studio_dataverse:` at all.

  **(2) The credential-egress fix was four times larger than the ADR knew.** v9 found `HttpPollingPullerAdapter` calling `ssrfSafeFetch` without `followRedirects: false`. Sweeping every such call in the governance services found **four more**, each sending a credential: the Anthropic admin key, a Databricks workspace bearer token, a warehouse-cost bearer token, and — worst — the Databricks OIDC token exchange, which carries the **client secret itself** rather than a token minted from it. The workspace host being pinned on the write path does not help there: a redirect issued by the real workspace still points wherever it likes. All five now opt out, and a refused redirect fails the run immediately rather than being retried as if transient, which it is not.

  **(3) Two defects the design could not have caught, both silent.** *(a)* Building the OData query with `URLSearchParams` encodes a space as `+`. That is form encoding; OData specifies percent-encoding, and a `$filter` whose spaces arrive as plus signs depends on how the server chooses to read them. The query is now assembled by hand and a test pins the encoding. *(b)* `PULL_ADAPTER_FOR_SOURCE` is a `Partial<Record<SourceType, …>>`, so a new pull-mode source with no entry compiles, resolves to no recommended cadence, and is created **with no schedule at all** — a source that looks configured, reports no error, and never polls. The new source would have shipped that way. A guard now fails when a non-deprecated pull-mode catalog entry has no cadence, and it was verified by removing the entry and watching it go red.

  **(4) A correction to the record.** The catalog's routing-declaration test asserted, in its own words, that Genie "is the one adapter emitting conversations". It passed while saying something no longer true. The worker's dispatch now pairs a source's profile with the mapper that reads its payloads in one registry entry, because choosing them independently fails quietly — the profile matches the action, the wrong mapper finds none of its fields, and the run reports success having routed nothing.

  **What is still not validated, unchanged from v10.2 and stated on the PR in these words: the batch-merge path is fixture-only.** Both captures are single-batch; the reassembly is vendor-documented and hand-fixtured, never observed. Everything else in the read path is pinned against captured payload shapes. The `Service Reader` breadth stays parked as ruled in v8. Captain: Sergio Esteban.
