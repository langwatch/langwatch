# ADR-159: The app owns the LangWatchQL access model — one definition, two emitters, delivered to every pod

**Date:** 2026-09-22 (updated 2026-09-23, tasks#889)

**Status:** Accepted

## Context

ADR-101 kept two owners of the LangWatchQL access model (`langwatch_lwql` user, `langwatch_profile` settings profile, row policies, grants, `lwql_postgres` named collection): a rendered-config copy for chart-managed/SaaS ClickHouse, and the application's SQL DDL for BYO ClickHouse. The rendered copy lived in `infra/clickhouse-serverless/internal/render/lwql.go` and was deployed by SaaS `render-config.sh` and the chart. The app's DDL lived in `platform/app/src/server/analytics/lwql/provisioning/` and ran on every boot.

Keeping two copies in sync was never stable. The rendered copies drifted from the app's catalog — the hand-vendored SaaS copy left roughly 113 of 129 production views returning 503, and the Go manifest needed parity tests just to stay in step with the app's definitions. Two owners of one model is a defect.

A first cut of this decision (PR langwatch/langwatch#8261, shipped 2026-09-22) made the app the single owner and provisioned it with SQL DDL on every boot. That DDL lands on one ClickHouse server only — the one the app's connection happens to reach. At `clickhouse.replicas > 1` every other pod never carries the user, profile, grants, row policies or named collection, so a tenant-filtered query fails or 503s depending on which pod answers it. Two routes to fix this at the ClickHouse layer were evaluated and rejected:

- **`ON CLUSTER` DDL.** The Keeper DDL task queue captures the cluster's host list at the moment the statement is enqueued. A host added after that moment (a rebuilt pod, a scale-up) never sees the statement, and there is no anti-entropy sweep to catch it up — `refreshEntities` reconciliation exists only for `<replicated>` access storage, which was rejected for this deployment shape in langwatch/langwatch#7331. `ON CLUSTER` would still leave replicas silently unprovisioned.
- **`<replicated>` access storage** (Keeper-backed, self-replicating). Rejected in #7331 for the same reason it stays rejected here: it demands a ClickHouse Keeper topology and access-storage migration the chart-managed and SaaS deployments do not carry, for a feature (LWQL) that a minority of installs enable.

Meanwhile SaaS renders the model as `users.xml` from a hand-vendored catalog copy on every pod — the exact two-owner drift this ADR exists to end.

## Decision

**One typed definition, two emitters, chosen by delivery mechanism, not by environment.**

The access model is defined once, as pure data, in `accessModelDefinition.ts` (`buildLwqlAccessModelDefinition`): the restricted user (password stored as `password_sha256_hex`, never plaintext), the settings profile with its per-setting constraints, the grant set derived from the catalog, both row policies (the key-map self filter and the per-view tenant predicate) with their predicates, the PostgreSQL named-collection fields, and the `custom_` settings prefix. Two emitters read this one definition and compute nothing themselves:

- **`accessModelDdl.ts`** — SQL DDL, for `sql` mode (BYO ClickHouse). Unchanged in shape from the #8261 DDL, now generated from the shared definition instead of describing the model a second time.
- **`accessModelUsersConfig.ts`** — `users.d` / `config.d` YAML, for `rendered` mode (chart-managed and SaaS ClickHouse, the default everywhere). `platform/app/src/tasks/renderLwqlAccessConfig.ts` is the task entrypoint: `pnpm run task renderLwqlAccessConfig --out <dir>` reads the same env the app reads for LWQL (`LWQL_CLICKHOUSE_PASSWORD`, `LWQL_POSTGRES_READER_PASSWORD`, `DATABASE_URL`, …) and writes `users.d/lwql-access.yaml` and `config.d/lwql-named-collection.yaml`.

A unit parity test (`__tests__/accessModelParity.unit.test.ts`) asserts both emitters name identical users, profiles, grants, row policies and named-collection fields, so the two can never drift — the bug this ADR exists to close.

`LWQL_ACCESS_MODEL_MODE` (`selfProvisioning.ts`, `lwqlAccessModelMode`) selects the emitter: `rendered` (default when unset) skips every access statement at boot — no user, profile, grants, row policies or named collection are provisioned by the app process itself — while still provisioning the Postgres reader role, the key-map table, the views, the postgres-engine tables, app functions and backfill. `sql` runs the pre-#8258 DDL path plus the AC9 cluster guard below. Chart-managed and SaaS installs run `rendered`; BYO installs that cannot mount `users.d`/`config.d` into their own ClickHouse set `LWQL_ACCESS_MODEL_MODE=sql`.

**Delivery to every replica, for `rendered` mode:** the chart runs the app image as a Kubernetes Job (`charts/langwatch/templates/clickhouse/lwql-access-render.yaml`), **main-phase on install and a `pre-upgrade`/`pre-rollback` hook on upgrade or rollback** (keyed on `.Release.IsUpgrade`, which Helm sets for both). The render inputs are `LWQL_CLICKHOUSE_PASSWORD`, `LWQL_POSTGRES_READER_PASSWORD` and `DATABASE_URL`. The two passwords and the Job's RBAC (ServiceAccount, Role, RoleBinding) are `pre-install,pre-upgrade,pre-rollback` hooks at a lower hook-weight (`-10`) than the Job (`5`), kept through the main phase (`before-hook-creation`, not `hook-succeeded`); both are **new** in this version, so on a first upgrade from a pre-LWQL release neither exists in the main phase yet when the pre-upgrade hook runs — as plain main-phase resources they would be reconciled only _after_ the hook, aborting the upgrade (missing RBAC) or failing the render with `LwqlRenderConfigMissingInputError` (the app Secret has no LWQL keys until the main phase heals it). As pre-install/pre-upgrade/pre-rollback hooks at a lower weight they are created first. The `pre-rollback` posture matters because `helm rollback` (and `--atomic` recovery) reverts the catalog annotation and rolls the pods, so it needs the same pre-hook render as an upgrade or the pods roll against a stale/absent access Secret. The passwords therefore live in their own chart-owned Secret (`<release>-lwql-passwords`, `templates/lwql-passwords-secret.yaml`, lookup-or-rand) on the autogen path, and the app Deployment reads them from there via `sharedEnv`; an operator's `secrets.existingSecret` (or a hand-created app Secret when autogen is off) pre-exists before any phase and is read directly.

Install stays main-phase because `DATABASE_URL` comes from the main-phase PostgreSQL Secret, which does not exist at pre-install — a pre-install Job was verified to fail on a first install (`failed pre-install ... Job Failed`). On install helm lays Secrets down before the Job and then waits on the Job and the ClickHouse StatefulSet concurrently: the Job renders and writes the access Secret while the ClickHouse pods sit in `ContainerCreating` (their required subPath mount has nothing to resolve yet — the kubelet retries a missing required Secret rather than hard-failing it), and once the Secret exists the kubelet re-syncs the volume and the pods start. On upgrade the previous revision's PostgreSQL Secret is still present, so the pre-upgrade hook has `DATABASE_URL` and writes the new access Secret before the StatefulSet roll (below).

The Job writes Secret `<release>-lwql-clickhouse-access` (keys `lwql-access.yaml`, `lwql-named-collection.yaml`) directly through the Kubernetes API, using its own ServiceAccount token — the app image carries node and curl but no `kubectl`, so the writer is a small inline node script (`fetch` against `https://kubernetes.default.svc`), not an extra tool or sidecar. Every chart-managed `clickhouse-serverless` pod mounts that one Secret unconditionally: the umbrella passes its name through `clickhouse.lwqlAccess.secretName` (`charts/langwatch/values.yaml`) and the subchart StatefulSet (`charts/clickhouse-serverless/templates/statefulset.yaml`) renders the two `subPath` volumeMounts at `/etc/clickhouse-server/users.d/lwql-access.yaml` and `/etc/clickhouse-server/config.d/lwql-named-collection.yaml`, so install, scale-up, and a rebuilt pod's disk all pick up the model at boot with no per-pod app action.

**Rolling an upgrade:** ClickHouse 25.10 hot-reloads `users.d` and `config.d` from disk within roughly 3 seconds of a file change (verified against `clickhouse/clickhouse-server:25.10.2.65` in Docker as part of this work). That reload does not help here, because a `subPath` mount is a bind-mount of a single key at pod-start time — Kubernetes does not propagate a Secret update into a `subPath` mount, so a running pod never sees a changed access model without a restart. The chart therefore carries a release-version pod annotation (`clickhouse.podAnnotations["langwatch.com/lwql-access-catalog"]`, bumped in lockstep with the chart version) on the ClickHouse pod template. Changing that annotation on `helm upgrade` rolls the StatefulSet, so every pod re-mounts the freshly rendered Secret. The annotation is a deliberate use of `subPath`'s no-live-update behaviour as the rollout trigger, not a bug worked around.

`lwql.enabled=false` still runs the Job, but writes two empty YAML documents (`{}`), so the pods' unconditional mount is always satisfiable and disabling the feature never wedges ClickHouse boot — `lwql.enabled` toggles the model's _content_, not the mount topology.

## AC8 deviations from existing patterns, and why

- **No `<replicated>` (Keeper-backed) access storage.** Rejected in langwatch/langwatch#7331 for the topology and migration cost it would impose on every chart-managed and SaaS install; standing rejection reaffirmed here, since it is the alternative that would have made `sql`-mode DDL safe on a multi-host cluster without this ADR's rendered path.
- **No `ON CLUSTER` DDL.** The Keeper DDL task queue snapshots the cluster's host list when a statement is enqueued; a host that joins later (scale-up, disk rebuild) is never caught up, and no anti-entropy sweep exists outside `<replicated>` storage. Discussed on the PR #8261 review thread; this is why delivery moved from DDL-everywhere to rendered config for chart-managed/SaaS.
- **DDL is kept, but only for BYO.** The app cannot render server config into a ClickHouse server it does not run, so `sql` mode (DDL against the app's own connection) is the only route available when the operator supplies their own ClickHouse.
- **The named collection needs a second `config.d` file, separate from the user file.** ClickHouse reads named collections from server config (`config.d`), not user config (`users.d`) — the two are different config trees, so the definition's single named-collection field is emitted twice, once per tree, not merged into one file.
- **The render Job writes a Secret directly, instead of the chart templating one from `values.yaml`.** The catalog (which views, which grants) lives in app code, not in chart values, so only the app image can render the file contents; chart templating only has access to values known at `helm template` time. Writing through the Kubernetes API is the only route from "app image computed this" to "every pod can mount it."
- **`sql` mode fails closed on multi-host clusters without replicated access storage (AC9).** Before any access statement, `assertLwqlSqlModeClusterSafe` (`sqlModeClusterGuard.ts`) queries `system.user_directories` and `system.clusters`. If no `replicated` user directory exists and any cluster the server belongs to (an `is_local = 1` cluster row) has more than one distinct host, provisioning aborts with `LwqlSqlModeUnsafeOnClusterError`, logging the host count and the replicated-directory count only — never statement text. ClickHouse Cloud and self-managed `<replicated>` storage both carry a `replicated` user directory and pass unchanged. The operator either points the app at replicated access storage or sets `LWQL_ACCESS_MODEL_SQL_SINGLE_NODE=true` to accept single-node scope. This is a refusal, not a warning — LWQL stays unavailable until the operator acts, per the epic's "fix it before merge, no warn-and-follow-up" decision.
- **The AC9 "one node provisions" e2e half proves permit + path-ran + yield, not a SQL-store user.** The epic's DoD asks the chart e2e to show `sql` mode provisioning on one node and refusing on a two-host cluster. On chart-managed ClickHouse the "provisions on one node" half cannot produce a SQL-store restricted user: rendered delivery always mounts `langwatch_lwql` into the read-only `users_xml` store, so the `sql`-mode `CREATE USER OR REPLACE` yields with a tolerated 495 (`ACCESS_STORAGE_READONLY`) rather than creating a `storage != 'users_xml'` twin — the app yields to the config-store copy by design (residual-risk section; the only escape, disabling rendered delivery, strips the app's LWQL connection). The single-node chart e2e (`charts/langwatch/tests/e2e.sh` `test_lwql`) therefore asserts the guard _permits_ (no refusal logged), the `sql` DDL path _actually ran_ (the captured converge shows the config-store yield), and the access model still answers a tenant-filtered query — not a SQL-store row. The literal SQL-store provisioning proof lives in the app integration suites: `configStoreSkip.integration.test.ts` proves the yield (a `users_xml`-owned name gets no SQL twin), and `tenantIsolation.integration.test.ts` provisions the whole access model as `sql` DDL on a bare server (no config-store owner) and enforces it. The cluster-refusal half (`test_lwql_replicas`) has no such limitation and asserts the refusal directly.

## Rationale / Trade-offs

One typed definition means one catalog and no cross-language parity tests against a second, hand-maintained model — the parity test that remains asserts two emitters over the _same_ in-process definition, not two independently maintained descriptions. The catalog is authoritative. BYO ClickHouse running `sql` mode must still grant the app administrative DDL rights to create these objects — `access_management`, `named_collection_control`, and the `custom_` settings prefix — unchanged from ADR-101's BYO path. The PostgreSQL reader role `lwql_ro` is converged by the app on whatever PostgreSQL database `DATABASE_URL` names in both modes; if those rights are not available, provisioning degrades to a logged, fail-closed refusal rather than a boot-time crash.

The cost of the rendered path is chart-side: a Job, a ServiceAccount, a scoped Role, a Secret and a `subPath`-mount rollout trigger where a single boot-time DDL statement used to suffice. That cost buys the thing DDL cannot: identical delivery to every replica regardless of which one the app's connection happens to reach.

## Consequences

- SaaS mirrors this Job-and-Secret shape in terraform (langwatch-saas#1253) rather than continuing to hand-vendor `lwql_catalog.json`; the SaaS rendered copy and its parity tests are deleted once the terraform change lands, the same order-independence ADR-101 originally allowed.
- The reconvergence watch described below (residual risk, unchanged from the prior version of this ADR) applies only to `sql` mode — `rendered` mode never runs SQL access statements, so there is nothing for the app process to reconverge; a `rendered`-mode upgrade's reconvergence is the chart's own pod-annotation rollout, not an app-side watch.
- The catalog stays an explicit, opt-in list (`LWQL_VIEW_CATALOG`) on both the ClickHouse and PostgreSQL halves — a new table or Prisma model is not queryable until it is added to the list — in both stores the definition can emit from.
- `LWQL_TENANT_PREDICATE_TEMPLATE` and `LWQL_KEY_MAP_SELF_FILTER_TEMPLATE` in `accessModelDdl.ts` remain the single source of truth for the row-policy predicates and key-map self-filters; `accessModelDefinition.ts` composes both emitters from them, so no third copy exists anywhere.

### Residual risk

A config-store-owned LangWatchQL entity (user, settings profile, row policy, named collection) is trusted as-is in `sql` mode — the app skips it by name and does not verify its substance (readonly setting, profile constraints, row-policy predicate, collection target). A wrongly defined config-owned entity can therefore widen or break tenant isolation, and the operator owns removing or correcting it. The app's boot-time WARN log names each such entity. A 495 (`ACCESS_STORAGE_READONLY`) error on an entity NOT found in the config-store inventory is treated as a failure, not a skip. This applies only to `sql` mode; `rendered` mode has no boot-time SQL access statements to skip or fail on.

`rendered` mode's own residual risk is the upgrade rollout window: between the render Job writing a new Secret and the pod-annotation-triggered StatefulSet roll completing, pods still running the old pod generation serve the previous release's access model (unchanged `users.d`/`config.d` content) until they restart. No pod is ever left with _no_ access model — the subPath mount source only ever moves forward from one rendered version to the next.
