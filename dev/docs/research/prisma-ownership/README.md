# Prisma ownership: day-one proposal

Research snapshot: 2026-09-07, branch `feat/strict-feature-layout-v0`, HEAD `0ac73e1e82` plus the shared working tree. This is an inventory and proposal, not an accepted ADR or an enforced migration. No production source or schema changed for this report.

## Recommendation

Keep one feature owner per physical model. Group the child tables that share a domain lifecycle under that owner. Retain existing feature boundaries and introduce narrow, named compatibility exceptions for existing joins and transactions; do not manufacture a giant tenant feature to legalize every current query. Claims should live on private repositories; `.withApp(...)` can collect inert metadata without a second Prisma table list on the installer.

All **125 models** are assigned once below: **40 existing feature owners and 3 platform owners**. Multiple repositories inside a feature may use the same model. A compatibility exception grants bounded access, never a second ownership claim. Platform persistence belongs to its existing framework, not a fabricated feature or an arbitrary Ops catch-all.

## What was inspected

The source scan covers **8,604 production TypeScript/JavaScript files** under `packages` and `apps`, excluding generated clients, dist, declaration files, tests, fixtures, storybooks, seeds and migrations. A TypeScript 6 parser already installed for architecture-lint supplied syntax traversal; no typechecker, LSP server or test run was needed. The application uses **Prisma 7.9.1**. Parser version is not the application's TypeScript version.

It found **239 files / 1,706 direct delegate-call expressions**, **462 repository-shaped files across all stores/ports**, including **189 with Prisma evidence**, and **24 files containing raw-query expressions**. **56 direct-query files are outside repository-shaped files**; these include legitimate platform adapters as well as feature adapters, services and process composition.

These are source observations, not a complete semantic or runtime call graph. Direct delegate syntax can be hidden behind dynamic dispatch, imported query builders, generic adapters or relation operations. The relation scan resolves some local variables and spreads but not arbitrary helper calls or imported query objects. Named class imports and relative imports establish source users, not proof of runtime construction. All files and query locations are retained so enforcement can be verified against real code rather than accepting counts as a security proof.

## Relations to keep, remove, or investigate

Keep internal child relations: Dataset → DatasetRecord; Prompt → versions/tags/assignments; Annotation → queue/score/member/item rows; Gateway → virtual-key/routing scopes and budget configuration; Organization → teams/groups/memberships. These support coherent domain behaviour and sometimes atomic writes.

Replace cross-feature author/profile lookups with batched UserApi operations first. Agent and evaluator history enrichment are candidates; avoid one User call per result. Keep foreign IDs as scalar values. Deleting a relation declaration is a later step after its query, output, pagination and delete semantics are replaced.

Project/Organization relation filters and Annotation membership joins are poor first deletion candidates: the query itself enforces tenant eligibility. Fetching unfiltered records and checking them later can change pagination or expose data. Scenario/Suite relations are also poor first candidates because row locking and transaction ordering matter.

The schema declares **`relationMode = "prisma"`**. This is not a schema where we can assume PostgreSQL foreign keys keep enforcing a removed relation. Prisma emulates some constraints and referential actions for client queries; raw SQL does not receive that emulation. There are **306 relation fields**, **220 crossing the proposed owners**, including **31 explicit cross-owner `onDelete: Cascade` declarations**. These are fields, not 306 distinct relationships; reverse fields are counted separately. Removing a relation can change runtime integrity or cascades even when migration SQL contains no foreign-key drop. Existing/manual database constraints were not inspected. See [Prisma's relation-mode documentation](https://www.prisma.io/docs/orm/prisma-schema/data-model/relations/relation-mode).

No direct delegate call was found for `Analytics`, `Invoice`, `InvoiceItem`, `PlatformToolPolicy`, `AiToolEntryTeam` or `GatewayBudgetLedger`. These are retirement-investigation candidates, not approved deletions. `TwoFactor` is different: the enabled Better Auth plugin uses generic storage. `RoutingPolicyScope` is actively used through nested operations. Do not label a table dead from the absence of `.table.method()` matches.

## Raw SQL and framework exceptions

The first ownership implementation cannot simply ban all current raw SQL without replacements. The inventory includes row locks, advisory locks, deduplication, maintenance sweeps and framework process/scheduler work. Keep named technical operations with fixed model scope; a declared table list alone is not proof that arbitrary SQL respects it.

Eventing's process/scheduled-job repositories and system migration state are framework persistence, not feature business data. Validate their ownership in the same manifest under explicit platform owners. Feature installers do not need to claim those tables just because they use a pipeline or migration. Root health checks such as `SELECT 1` do not claim a domain table.

## Implementation sequence

1. Approve the ownership map and resolve the provisional boundaries: Identity's legacy credential bridge, AuditLog/Core placement, and evaluation Cost/BatchEvaluation ownership. Webhook is agreed as core outbound delivery.
2. Generate a schema-checked ownership manifest from repository declarations. Reject two distinct owners, unknown models, and missing claims across the full catalogue, including feature sets not installed in one process. Reserve remaining models pending retirement proof; do not add dummy queries to make an unused table look active.
3. Introduce owner-scoped database capabilities and precise temporary exceptions. Validate declarations before construction at boot; retain scope inside interactive transactions. Ordinary feature code must not receive the unrestricted client.
4. Migrate simple private groups and batch foreign lookups first. Start with GitHub, Dataset, Prompt, Dashboard, Secret, StoredObject and policy tables, subject to the call-site exceptions in the CSV. Do not confuse a package's new App with completed API/worker caller migration.
5. Move duplicate Governance/Gateway and Agent/Workflow persistence behind the owner APIs, preserving existing responses and side effects.
6. Handle membership projection, provisioning, erasure and Scenario/Suite transaction boundaries deliberately. Remove each named exception only once replacement behaviour is characterized and verified.
7. Consider schema relation removals or table retirement after callers, referential behaviour and retained-data requirements are accounted for. No schema edits are part of this inventory.

Types can limit the capability a repository receives and validate model names. Whole-catalogue checks establish global ownership; boot checks the selected installation; a runtime query boundary enforces allowed operations. None of those alone proves arbitrary code executes only the intended SQL. Avoid a recursive type-level transformation of the entire Prisma graph without measuring compiler cost.

## Outbound webhooks are core

Outbound webhook delivery is a core feature used by multiple entrypoints, including Enterprise features. The proposed `webhook` owner therefore belongs at `modules/webhook`, not under Enterprise. It owns WebhookEndpoint and WebhookEndpointDelivery, outbound dispatch, signatures, retries, batching, delivery history and retention. The current implementation also supports SQS destinations; preserve that capability within the same outbound delivery owner.

Automation owns trigger evaluation and payload formation; Governance and other callers own their event selection and product policy. They submit through WebhookApi. Enterprise availability checks remain on the relevant product operations; they must not disable delivery for unrelated core consumers. The shared delivery engine still enforces destination safety, credential handling and tenant scope. Inbound GitHub/provider callbacks stay with their owning features.

The current catalogue, package locations, entitlement gate and implementations have not yet been migrated. Consolidation must preserve Automation's existing wire payloads, identifiers, retry behaviour and optional test-fire logging, alongside the platform channel's envelope/batching behaviour. AuditLog placement remains a separate recommendation.
